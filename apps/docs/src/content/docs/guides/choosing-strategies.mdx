Reactive Agents ships eight reasoning strategies. Picking the right one has a significant impact on token usage, latency, and answer quality. This is the one page that explains what each strategy does and how to choose between them. Other pages (the [Reasoning guide](../reasoning/), [Local Models](../local-models/), [Choosing a Stack](../choosing-a-stack/)) summarize and link here.

<Aside type="tip" title="If you don't want to think about it">
Use **Adaptive** — it auto-selects per task: `reasoning: { defaultStrategy: "adaptive" }` (declarative) or `.withReasoning({ defaultStrategy: "adaptive" })` (builder). Or use the default **ReAct** — it works for ~80% of agent workloads. Only switch to one of the others when you have a specific reason from the decision tree below.
</Aside>

<Aside type="caution" title="Pick by task shape, not by hype">
Tree-of-Thought is *not* always better than ReAct. It explores wide, suits **creative or open-ended** problems and uses 3-5× more tokens. Plan-Execute-Reflect suits **multi-step structured work** but burns budget on planning when the task is simple. Adaptive picks per task and is usually the safest choice when you do not know the workload.
</Aside>

## Decision Tree

```
What kind of task are you running?
│
├─ Single-step Q&A, no tools needed
│   └─ Use agent.chat() — direct LLM call, no ReAct loop overhead
│
├─ Multi-step with tools, general tasks
│   └─ ReAct (default)
│       .withReasoning()
│
├─ Decomposable, tool-heavy task whose full plan is knowable UP FRONT
│  (multi-file generation, static pipelines — no mid-course adaptation)
│   └─ Blueprint  ← cheapest: plan once → run tools (no LLM in loop) → solve
│       .withReasoning({ defaultStrategy: "blueprint" })
│
├─ Multi-step plan that must ADAPT mid-course (react to results, retry on
│  failure, fetch-then-decide, debug-until-passing)
│   └─ Plan-Execute-Reflect
│       .withReasoning({ defaultStrategy: "plan-execute-reflect" })
│
├─ Quality-critical, factual accuracy matters
│   └─ Reflexion
│       .withReasoning({ defaultStrategy: "reflexion" })
│
├─ Creative, exploratory, or ambiguous problem
│   └─ Tree-of-Thought
│       .withReasoning({ defaultStrategy: "tree-of-thought" })
│
├─ Mixed workload — task type varies per subtask
│   └─ Adaptive
│       .withReasoning({ defaultStrategy: "adaptive", adaptive: { enabled: true } })
│
└─ Unknown complexity, want automatic switching when stuck
    └─ Enable strategy switching
        .withReasoning({ enableStrategySwitching: true })
```

## Strategy Comparison

| Strategy | Avg Tokens | Latency | Iterations | Best For |
|---|---|---|---|---|
| ReAct | Low–Med | Fast | 3–10 | Tool-use tasks, API calls, lookups |
| Blueprint | **Low** | **Fast** | ~2 LLM calls | Static decomposable tasks (multi-file gen, parallel subtasks) |
| Plan-Execute-Reflect | Med–High | Medium | 5–15 | Observation-driven workflows that adapt mid-course |
| Reflexion | Medium | Medium | 3–8 | Factual Q&A, accuracy-critical |
| Tree-of-Thought | High | Slow | 5–20 | Creative writing, ambiguous problems |
| Adaptive | Varies | Varies | Varies | Mixed workloads, changing task types |
| Direct | **Lowest** | **Fastest** | 1 (no loop) | Simple questions, minimal latency, no tool use |
| Code-Action `@exp` | Low–Med | Fast | 1–3 sandbox runs | Multi-tool orchestration, pure computation |

> **Blueprint vs Plan-Execute-Reflect:** both decompose, but blueprint plans the
> whole tool-DAG once and executes it with **no LLM in the loop** (≈2 calls total,
> ~20× cheaper on its domain) — so it can't react to surprises. Use blueprint when
> the plan is knowable up front (generate these files, fetch these N independent
> sources); use plan-execute when steps depend on observing earlier results
> (debug-until-passing, branch-on-result, flaky I/O). Adaptive routes between them
> automatically.

## Strategy Deep Dives

### ReAct (Reason + Act)

The default strategy. Each iteration follows: Think → Act (tool call) → Observe (result) → repeat until the task is complete.

**Strengths:**
- Fast and token-efficient
- Works reliably on 4B+ models
- Best fit for tool-heavy tasks (API calls, file operations, lookups)

**How it works:**
1. **Think**: the agent reasons about the current state.
2. **Act**: if needed, it calls a tool through native function calling. Tool definitions go in the API parameter and the model returns structured `tool_use` blocks, with no text parsing.
3. **Observe**: `ToolService` runs the tool and the real result comes back as a `tool_result` message.
4. Repeat until the `final-answer` meta-tool is called or max iterations is hit.

Without a `ToolService` the agent degrades gracefully and returns descriptive messages instead of tool results. How tools reach the loop is covered in [Reasoning](../reasoning/#tools--reasoning-integration).

**Requirements:** Tools must be registered via `.withTools()`.

---

### Blueprint

A ReWOO-style strategy for **static, decomposable, tool-heavy tasks** whose full plan is knowable up front. Three phases:

1. **Plan** (1 LLM call) — produce the entire tool plan as a dependency graph (DAG) with `#E1/#E2` evidence references between steps. Schema/grammar-enforced so even small local models emit a valid plan.
2. **Verify** (no LLM) — validate the DAG (no cycles, required tools present, references resolve); repair fixable gaps; **degrade to ReAct** if the plan is unusable.
3. **Execute** (no LLM) — run the tools in dependency order, independent steps in parallel; then **Solve** (1 LLM call, skipped when a step already produced the deliverable).

**Strengths:**
- **~2 LLM calls total vs ~9 for plan-execute** — measured ~20× cheaper on its domain.
- The plan-verification gate and schema-enforced planning are meant to carry smaller models. Results vary by model: in our tests it did well on some local models and poorly on others, so measure it on yours.
- Parallel tool execution for independent steps.

**Tradeoff:** plans once with **no mid-course observation** — it can't react to surprises (tool failures, results that change the plan). For those, use Plan-Execute-Reflect or ReAct.

**Best for:** multi-file/artifact generation, static pipelines, independent parallel subtasks. **Avoid for:** flaky network I/O, debug-until-passing, fetch-then-decide.

**Requirements:** Tools via `.withTools()` / `tools: { builtins: true }`. Select with `reasoning: { defaultStrategy: "blueprint" }` (declarative) or `.withReasoning({ defaultStrategy: "blueprint" })` (builder) — alias: `"rewoo"`.

---

### Plan-Execute-Reflect

Generates a structured JSON plan before taking any action, then executes each step individually (via tool call or LLM analysis), and reflects after completion to refine or replan.

**Strengths:**
- Handles complex multi-step workflows with dependencies between steps
- Produces structured, auditable output
- Plans are persisted in SQLite for inspection and replay

**Loop:** **Plan** (numbered, typed steps) → **Execute** each step (direct tool call, single LLM analysis, or a scoped ReAct kernel) → **Reflect** against the plan → **Refine** with a revised plan if gaps remain.

**Options** (under `strategies.planExecute`, builder-only): `maxRefinements` (default 2), `reflectionDepth` (`"shallow"` or `"deep"`, default `"deep"`), `stepRetries` (default 1), `stepKernelMaxIterations` (derived as `max(5, ceil(runMaxIterations / planLength))` unless set) and `planMode` (`"linear"` or `"dag"`, default `"linear"`). The plan schema, cross-step references, error recovery and persistence are documented in [Reasoning: Structured Plan Engine](../reasoning/#structured-plan-engine).

Not to be confused with `agent.plan()` / `agent.execute(plan)`, an experimental way to review a plan before it runs: see [Plan then execute](../plan-then-execute/).

**Requirements:** plans are JSON, so the model must produce structured output reliably; some local models fail at it. `.withMemory()` is recommended so the plan store has a backing layer.

---

### Reflexion

Adds a self-evaluation loop based on the [Reflexion paper](https://arxiv.org/abs/2303.11366) (Shinn et al., 2023): **Generate → Self-Critique → Improve**, repeated until the critique returns `SATISFIED:` or `maxRetries` is reached. Prior critiques are stored in episodic memory and used to improve subsequent attempts.

**Strengths:**
- Self-correcting — identifies and addresses gaps in its own reasoning
- High accuracy on factual tasks
- Learns from prior run critiques across sessions when episodic memory is enabled

**Trade-off:** each retry cycle is three passes (generate, critique, improve), typically about 3× the tokens of ReAct per cycle. Worth it when output quality matters more than speed: writing, detailed analysis, summarization.

**Options** (under `strategies.reflexion`, builder-only):

| Option | Default | Description |
|--------|---------|-------------|
| `maxRetries` | 3 | Max generate-critique-improve cycles |
| `selfCritiqueDepth` | `"deep"` | `"shallow"` or `"deep"` critique |
| `kernelMaxIterations` | 3 | Max ReAct tool-call iterations per generate or improve pass |

**Cross-run learning:** with memory enabled (`.withMemory()` or `memory: {}`) the execution engine loads `priorCritiques` from episodic memory for similar tasks, so the agent avoids repeating past mistakes. No extra wiring is needed.

**Requirements:** 8B+ model. Benefits significantly from episodic memory via `.withMemory({ tier: "standard" })`.

---

### Tree-of-Thought

Generates multiple candidate thoughts at each step, scores them, and expands the most promising branches (BFS or DFS). Only the highest-scoring path is executed. It runs in two phases:

1. **Search** (breadth-first): **Expand** candidate thoughts grounded in the available tools, **Score** each (0.0–1.0), **Prune** any below `pruningThreshold`, **Deepen** the survivors up to `depth` levels.
2. **Execute**: a ReAct-style think/act/observe loop guided by the best path, calling real tools.

**Strengths:**
- Explores multiple solution paths before committing
- Best for creative, ambiguous, or open-ended problems, especially ones that also need tools (repository queries, file operations, multi-source research)
- Tolerates underspecified prompts better than linear strategies

**Options** (under `strategies.treeOfThought`, builder-only):

| Option | Default | Description |
|--------|---------|-------------|
| `breadth` | 3 | Candidate thoughts per expansion |
| `depth` | 3 | Maximum tree depth |
| `pruningThreshold` | 0.5 | Minimum score to survive pruning |

**Requirements:** a capable model. Token usage is significantly higher than other strategies — budget accordingly.

---

### Adaptive

Selects the most appropriate strategy per-iteration based on observed task characteristics. Simple analytical steps are routed to fast strategies; complex or uncertain steps are escalated.

**Strengths:**
- Handles mixed workloads where task complexity shifts mid-run
- Routes simple steps to fast strategies, reducing unnecessary overhead
- No single-strategy lock-in

**Routing by task characteristics:** trivial/short → ReAct; static local artifact generation → **Blueprint**; observation-driven or network/fetch tasks → Plan-Execute-Reflect; compare/explore → Tree-of-Thought; critique/refine → Reflexion. On the local tier it defaults to ReAct (heavy strategies show no quality lift there); Blueprint auto-routes on mid/large/frontier and is available opt-in on local.

**Requirements:** Must explicitly set `adaptive: { enabled: true }` in the reasoning options — builder-only (no declarative config key for this sub-option). An 8B+ model is recommended. You can also keep a named default and turn on routing alone with `.withReasoning({ adaptive: { enabled: true } })`: every task is then classified and routed.

**Which strategy ran:** `result.metadata.strategyUsed` reports the sub-strategy that produced the output (for example `"reactive"`), not `"adaptive"`, and `result.metadata.selectedStrategy` carries it for downstream use. The `[think]` observability log shows it inline, e.g. `(adaptive→reactive)`. The EventBus `ReasoningStepCompleted` event still carries `strategy: "adaptive"` for subscribers that need the entry point.

---

### Direct

A single LLM call with no reasoning loop — no think/act/observe cycle, no tool calls. The model answers from its own knowledge.

**Strengths:**
- Lowest latency and token cost of any strategy — one call, no iterations
- The right default for questions that don't need a tool or multi-step reasoning

**Requirements:** None beyond a base model. Not suitable for tasks that need current information, file access, or any tool.

---

### Code-Action `@experimental`

The LLM generates a TypeScript IIFE that runs inside a Worker-thread sandbox. Tools are exposed as normal async functions and called directly in generated code — no JSON tool-call schema round-trip per call.

**Strengths:**
- Multi-tool orchestration expressed as control flow (loops, conditionals) instead of N sequential tool-call turns
- Handles pure computation tasks with no tools at all

**Requirements:** A model capable of generating syntactically valid TypeScript. Experimental — API surface and sandboxing behavior may still change. See [Code-Action](/features/code-action/) for the full sandbox model.

## Automatic Strategy Switching

When you enable strategy switching, the framework monitors execution and can automatically switch to a different strategy mid-run if the current one appears to be stuck.

Strategy switching is **off by default**. You turn it on with `enableStrategySwitching: true`. It was on by default until we measured it. In the 2026-11-05 ablation on local models (qwen3:4b, cogito:8b), switching gave no measurable accuracy gain: -6.2pp, which is inside the noise. It also added 28% more billed tokens, and 41% more on one task. None of the 14 runs that switched in the follow-up went on to solve the task. Turn it on if your own measurements show it helps on your workload.

<Tabs syncKey="syntax">
  <TabItem label="Declarative">
```typescript
import { createAgent } from "reactive-agents";

const agent = await createAgent({
  name: "switching-agent",
  provider: "anthropic",
  reasoning: {
    enableStrategySwitching: true,  // default: false
    maxStrategySwitches: 2,         // default: 1
  },
});
```
  </TabItem>
  <TabItem label="Builder">
```typescript
import { ReactiveAgents } from "reactive-agents";

const agent = await ReactiveAgents.create()
  .withName("switching-agent")
  .withProvider("anthropic")
  .withReasoning({
    enableStrategySwitching: true,  // default: false
    maxStrategySwitches: 2,         // default: 1
  })
  .build();
```
  </TabItem>
</Tabs>

### What triggers a switch

The kernel runner detects a loop condition when any of the following occur repeatedly within a sliding window of recent steps:

- The same tool is called with identical arguments multiple times
- The same thought text appears in consecutive iterations
- Multiple consecutive `think` steps occur without any `act` step in between

When a loop is detected, the framework pauses execution and evaluates whether to continue with the current strategy or hand off to a different one.

### Evaluation mechanism

By default, an **LLM evaluator** is called with the current task, the last few steps, and a summary of the stuck pattern. It returns a recommended strategy and a rationale. The evaluation result is surfaced as an EventBus event (`StrategySwitchEvaluated`) before any switch occurs.

If you want deterministic switching without an extra LLM call, set `fallbackStrategy` directly:

<Tabs syncKey="syntax">
  <TabItem label="Declarative">
```typescript
const agent = await createAgent({
  name: "switching-agent",
  provider: "anthropic",
  reasoning: {
    enableStrategySwitching: true,
    fallbackStrategy: "plan-execute-reflect",  // skip LLM evaluator, always switch to this
  },
});
```
  </TabItem>
  <TabItem label="Builder">
```typescript
const agent = await ReactiveAgents.create()
  .withName("switching-agent")
  .withProvider("anthropic")
  .withReasoning({
    enableStrategySwitching: true,
    fallbackStrategy: "plan-execute-reflect",  // skip LLM evaluator, always switch to this
  })
  .build();
```
  </TabItem>
</Tabs>

When `fallbackStrategy` is set, the evaluator is bypassed and the agent switches immediately to the named strategy.

### Handoff context

When a strategy switch occurs, the new strategy receives a `StrategyHandoff` object containing:
- The task description
- All steps completed so far (thoughts, actions, observations)
- The stuck pattern that triggered the switch
- The evaluator's rationale (or `"fallback"` if `fallbackStrategy` was used)

This ensures the new strategy can pick up where the old one left off rather than restarting from scratch.

### EventBus events

Two events are emitted around strategy switches. Subscribe to them via `agent.subscribe()` for observability or custom logic:

| Event | When emitted | Key fields |
|-------|-------------|------------|
| `StrategySwitchEvaluated` | After the evaluator runs, before switching | `taskId`, `fromStrategy`, `recommendedStrategy`, `rationale`, `willSwitch` |
| `StrategySwitched` | After the switch completes | `taskId`, `fromStrategy`, `toStrategy`, `switchNumber`, `stepsCarriedOver` |

```typescript
await agent.subscribe("StrategySwitchEvaluated", (event) => {
  console.log(`[eval] ${event.fromStrategy} → ${event.recommendedStrategy}: ${event.rationale}`);
});

await agent.subscribe("StrategySwitched", (event) => {
  console.log(`[switch ${event.switchNumber}] ${event.fromStrategy} → ${event.toStrategy}`);
  console.log(`  ${event.stepsCarriedOver} steps carried over`);
});
```

### Switch cap

`maxStrategySwitches` (default: 1) limits how many times the strategy can change within a single run. Once the cap is reached, the framework continues with the last active strategy regardless of further loop detection, and logs a warning.

### When to use it

We have not measured a workload where strategy switching improves accuracy. Before you keep it on, compare runs with it on and off. Cases worth testing:
- Tasks with **unknown complexity**, where you do not want to over-provision (for example, start with ReAct and escalate to Plan-Execute-Reflect only if needed)
- Experiments with agent behavior, where you want to see how a different strategy handles a stuck run
- A **mixed workload** where the primary task is clear but subtasks vary

For tasks where you already know the complexity profile, it's more token-efficient to pick the right strategy upfront using the decision tree above.

## Local Model Recommendations

This section is the canonical strategy-by-model-size guidance. [Local Models](../local-models/) covers everything else about running locally (setup, tiers, pitfalls) and links here for strategy choice.

We have not measured every strategy at every model size, so this section makes no per-size ratings. What the tests we ran show:

- **ReAct (`"reactive"`) is the default on every tier.** It is the strategy we measured most on 4B-8B models. It completes tool tasks on some models (`qwen3:4b` fully solved 5 of 12 frozen tasks) and fails on others (`cogito:8b` solved almost none of the same suite). Test your own model.
- **Heavier strategies cost more and showed no measured quality gain on local models.** Reflexion, Plan-Execute-Reflect and Tree-of-Thought use more tokens and time on local models (Plan-Execute-Reflect ran at 2-5x the tokens and time of ReAct at matching accuracy) and failed outright on some 8B-14B models.
- **Reach for the heavy strategies on frontier models, or after you have measured them on your own tasks.** We have not measured Reflexion or Tree-of-Thought by model size.
- **Adaptive** routes to ReAct on the local tier. Blueprint is available opt-in on the local tier; its results vary by model.

Keep `maxIterations` modest on small models and use `.withContextProfile({ tier: "local" })`.

### Small models (4B-8B, e.g., phi-4-mini, gemma-3-4b, llama-3.1-8b)

Use **ReAct**. Keep `maxIterations` at 10 or below. Heavier strategies cost more and showed no measured quality gain on small local models.

<Tabs syncKey="syntax">
  <TabItem label="Declarative">
```typescript
const agent = await createAgent({
  name: "local-agent",
  provider: "ollama",
  reasoning: {},                        // ReAct (default strategy)
  execution: { maxIterations: 10 },
});
```
  </TabItem>
  <TabItem label="Builder">
```typescript

```
  </TabItem>
</Tabs>

### Larger models (14B and up)

The same rule holds: start with ReAct and move to a heavier strategy only if your own measurements show it helps. Plan-Execute-Reflect and Tree-of-Thought are better matched to frontier models and quality-critical workloads, where the extra cost is easier to justify.

```typescript
import { ReactiveAgents } from "reactive-agents";

const adaptiveAgent = await ReactiveAgents.create()
```

For a direct conversational query with no tool use, skip the ReAct loop entirely:

```typescript
const result = await agent.chat("What is the capital of France?");
console.log(result.answer);
```

`agent.chat()` routes directly to the LLM without invoking any reasoning strategy, making it significantly faster and cheaper for simple Q&A.
