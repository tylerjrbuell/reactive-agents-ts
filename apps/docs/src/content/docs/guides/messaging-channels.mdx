Reactive Agents sends and receives messages on **Signal** and **Telegram** through **native channel adapters** from `@reactive-agents/channels`. An adapter owns its platform: inbound messages, outbound sends, sender identity, delivery receipts and reconnect. `ChannelService` consumes it, applies access control, runs the agent and sends the reply itself, so every reply has a real platform message id (or a typed `ChannelError`) instead of depending on the model to call a send tool.

| Platform | Native adapter | Transport |
|----------|----------------|-----------|
| Signal | `SignalChannelAdapter` | `signal-cli` JSON-RPC (daemon socket or spawned process) |
| Telegram | `TelegramChannelAdapter` | Bot API with a BotFather token (long polling or webhook) |
| HTTP | `WebhookChannelAdapter` | HMAC-signed webhook requests |

See [Signal (native)](#signal-native) and [Telegram (bot)](#telegram-bot) for setup, then register the adapters:

```typescript
import { Redacted } from "effect";
import { ReactiveAgents } from "@reactive-agents/runtime";
import { TelegramChannelAdapter } from "@reactive-agents/channels";

const telegram = new TelegramChannelAdapter({
  token: Redacted.make(process.env.TELEGRAM_BOT_TOKEN ?? ""),
});

const builder = ReactiveAgents.create()
  .withName("telegram-agent")
  .withProvider("anthropic")
  .withChannels({ adapters: [telegram] })
  .withGateway({
    accessControl: {
      accessPolicy: "allowlist",
      allowedSenders: ["telegram:123456789"], // platform:userId
    },
  });
```

To write an adapter for another platform, see the [Channel Adapters guide](/guides/channel-adapters/). To run the agent unattended, see [Deploying Agents](/guides/deploying-agents/).

## Legacy: MCP servers

The two MCP setups below predate the adapters. They still work, but the agent reads and replies by calling MCP tools, so there are no delivery receipts, and Signal echoes are detected by message text. **Signal** ships as a Docker image in this repo (`docker/signal-mcp/`). **Telegram** uses the community **[chigwell/telegram-mcp](https://github.com/chigwell/telegram-mcp)** personal-account client, run with `uvx`, a local clone or your own container; this monorepo publishes no Telegram image. Prefer the native adapters for new work.

### How the MCP path works

```
Gateway heartbeat fires every N seconds
  → Agent calls receive_message MCP tool
  → Processes new messages (with guardrails)
  → Responds via send_message MCP tool
```

The **Signal** MCP server is a TypeScript implementation (`docker/signal-mcp/server/`) that spawns signal-cli in persistent `jsonRpc` mode (one JVM boot, no cold start per message). Signal can also push `notifications/message` for faster inbound handling.

**Telegram:** plain `pip install telegram-mcp` / `uvx telegram-mcp` **without** `--from` pointing at chigwell’s sources often resolves to a **different** PyPI project (hosted relay) that expects `TELEGRAM_CHAT_ID`, not the Telethon user MCP described here. Telegram on this path relies on polling tools.

## Security Best Practices

### Container Hardening (Signal)

The Signal Docker example uses strict isolation:

| Flag | Purpose |
|------|---------|
| `--cap-drop ALL` | Remove all Linux capabilities |
| `--no-new-privileges` | Prevent privilege escalation |
| `--memory 512m` | Hard memory limit (Signal needs 512m for JVM) |
| `--pids-limit 30` | Prevent fork bombs |
| `--user 1000:1000` | Run as non-root |
| `--read-only` | Immutable root filesystem |

Telegram via `uvx` runs as your host user; apply process isolation separately if you need a sandbox.

### Secret Management

- **Never pass secrets as MCP tool arguments** — they'd appear in agent context
- **For Telegram with `uvx`:** pass credentials via `.withMCP({ env: { ... } })` or your process manager — avoid putting secrets in MCP `args`
- **Use Docker volumes** for Signal auth keys (`./signal-data/`)
- **Add `.env.telegram` and `signal-data/` to `.gitignore`**

### Sender Access Control

Inbound messages are untrusted. With `accessControl` configured, the gateway decides who may trigger the agent, keyed by **`platform:userId`** so a Signal number and a Telegram id can never collide:

```typescript
const accessControl = {
  accessPolicy: "allowlist" as const, // default; unknown senders are skipped
  allowedSenders: ["signal:+15551234567", "telegram:123456789"],
};
// pass as the `accessControl` field of .withGateway({ ... })
```

- **Channels reject unknown senders by default.** A gateway with no `accessControl` denies every inbound sender (Telegram, Signal, webhook-channel); the deny reason names the sender (`telegram:123`) and the gateway logs a warning at start. Set `allowedSenders`, or accept anyone on purpose with `accessControl: { accessPolicy: "open" }`. A block with no `accessPolicy` still defaults to `allowlist`, so an empty `allowedSenders` also denies everyone.
- Entries **must** carry the platform prefix (`signal:+1555...`). A bare `+1555...` no longer matches a platform-tagged sender; update existing allow/block lists when you upgrade.
- A channel event with an **empty sender** is always denied (fail closed), even under `"open"`.
- `unknownSenderAction: "escalate"` surfaces the denied sender instead of silently skipping.
- `replyToUnknown` (a fixed text sent to an allowlist-denied sender) is only delivered by the `@reactive-agents/channels` `ChannelService` (`deps.replyToUnknown`), which the native adapters use. The legacy MCP-push path has no deterministic send step, so it does **not** send that reply.

### Guardrails

Always enable `.withGuardrails()` for messaging agents. Inbound messages from external users can contain prompt injection attempts. Guardrails check for injection, PII, and toxicity **before** the LLM processes the message.

### Kill Switch

Always enable `.withKillSwitch()` for autonomous messaging agents. This provides:
- `agent.stop(reason)` — graceful shutdown at next phase boundary
- `agent.terminate(reason)` — immediate halt

## The Channel Adapter Contract

The Signal and (personal-account) Telegram setups above are MCP servers: the agent reads and replies by calling tools, so delivery is whatever the model decides to do. `@reactive-agents/channels` defines the replacement: one `ChannelAdapter` contract every platform implements. The webhook adapter, the native Signal adapter and the Telegram bot adapter ship on the new contract today.

An adapter owns its platform (inbound, outbound, identity, receipts, reconnect). The gateway only sees these shapes:

| Shape | What it carries |
|-------|-----------------|
| `InboundEnvelope` | platform message `id` (idempotency key), `conversation` (`channelId`, `threadId?`, `isGroup`), `sender` (`platform`, `userId`), `text`, `attachments` (`Uint8Array` or url), `replyTo`, `mentionsSelf`, `isEcho`, `receivedAt` |
| `OutboundMessage` | `conversation`, `text`, `format?`, `attachments?`, `replyTo?` |
| `DeliveryReceipt` | the platform's real `messageId`, `status` (`sent`, `queued`, `delivered`), `sentAt` |
| `ChannelError` | `kind` (`auth`, `rate_limited`, `not_found`, `forbidden`, `too_large`, `unsupported`, `network`, `unknown`), `retryable`, `retryAfterMs?` |
| `ConnectionState` | `connecting`, `connected`, `reconnecting`, `disconnected`, `failed` |

`ChannelService` consumes the adapter's backpressured `inbound` stream, drops echoes, applies access control keyed on `platform:userId`, runs the trigger and session, and sends the reply itself through `adapter.send`. That changes three things compared with the MCP path:

- **Receipts.** `ChannelMessageSent` is published only after a successful send and carries the platform's real message id.
- **Typed failures.** A failed send is counted in `status()` (`deliveryFailures`, `lastError`) and published as a `ChannelDeliveryFailed` event (currently a `Custom` event with that `type` until a dedicated core event lands). `channelService.deliver(adapterId, message)` returns the receipt or fails with a `ChannelError`, so a workflow can branch on `rate_limited` or `auth`. The raw platform error is kept in `cause` and never published, because it can contain URLs and tokens.
- **Honest status.** `status().adapters[].connected` reflects the adapter's reported `ConnectionState`.

### WebhookChannelAdapter is fail-closed

Requests are accepted only when signed:

```text
x-channels-timestamp: <epoch seconds or milliseconds>
x-channels-signature: hex(HMAC-SHA256(secret, "<timestamp>.<body>"))
```

**Per-caller limits.** A webhook route has no default per-sender cap (messaging channels default to 6 turns per sender per hour), because most webhook callers send no sender identity and would all share one bucket. The route-level caps (`maxCostPerDayUsd`, `maxTurnsPerHour`) always apply. To limit each caller, put `senderId` (or `from_id`) in the JSON body and set `maxTurnsPerSenderPerHour` on the route; each `senderId` then gets its own hourly budget. Requests without a `senderId` share one bucket under that cap.

A timestamp outside `replayWindowMs` (default 5 minutes) is rejected, and a repeated message id is delivered once. With no `secret`, every request is rejected (`missing_secret`) unless you pass `allowUnsigned: true`, which is for local development only. `secret` accepts a plain string or an Effect `Redacted`. Before anything consumes inbound (`start()` or a legacy `onMessage` handler), a request fails with `not_started` instead of being dropped.

**Connection info and signing helper.** `webhook.connectionInfo({ baseUrl })` returns how to call the channel, generated from the same constants verification uses: `{ method: "POST", path: "/channels/<id>", url?, contentType, signature: { header, algorithm, encoding, signedPayload, timestampHeader, timestamp, replayWindowMs, replay }, examples: { curl, node, openssl } }`. The pure `webhookConnectionInfo({ baseUrl?, channelId?, replayWindowMs? })` gives the same without an adapter. `signRequest(secret, body, { nowMs? })` returns `{ headers, timestamp, signature }`: the exact headers a sender must attach (the body must be sent byte-for-byte as signed). Examples use the placeholder `$WEBHOOK_SECRET`.

### Signal (native)

`SignalChannelAdapter` talks to `signal-cli` in `jsonRpc` mode directly. There is no MCP container and no model-in-the-loop send step: `ChannelService` sends the reply itself and gets a receipt.

The Docker MCP setup above (`docker/signal-mcp`) is the **legacy** path. It keeps working, but it has no receipts, detects echoes by message text, and replies through a single "last sender", so concurrent senders can be cross-wired. New setups should use the native adapter.

**Setup**

1. Register or link the account with `signal-cli` (`signal-cli -a +15551234567 register` then `verify`, or `link` for a secondary device). The registration helper `./docker/signal-mcp/register.sh` still works for this.
2. Pick a transport:
   - **Daemon socket (recommended on shared hosts).** Run `signal-cli -a +15551234567 daemon --tcp 127.0.0.1:7583` yourself, then use `makeSignalSocketTransport({ port: 7583 })` (or `{ path }` for a unix socket).
   - **Spawned process.** `makeSignalProcessTransport({ account })` starts `signal-cli -a <account> --output=json jsonRpc`. The account number is a command-line argument, so it shows up in the host's process list.
3. Create the adapter and register it with the channel service:

```typescript
import { Redacted } from "effect";
import { SignalChannelAdapter, makeSignalSocketTransport } from "@reactive-agents/channels";

const signal = new SignalChannelAdapter({
  account: Redacted.make(process.env.SIGNAL_PHONE_NUMBER ?? ""),
  transport: makeSignalSocketTransport({ port: 7583 }),
});
```

**Behaviour**

| Concern | What the adapter does |
|---------|-----------------------|
| Identity | `signal:<number>` (or `signal:<uuid>` when the sender hides their number). Allowlist entries use that key, e.g. `signal:+15551234567`. |
| Conversations | A DM's `channelId` is the sender; a group's is the group id, and the individual sender is kept on every message. Signal has no threads (`capabilities.threads` is `false`). |
| `mentionsSelf` | `true` in a DM, in a group only when the bot is mentioned or its message is quoted. |
| Echoes | Messages sent from this account are echoes only when their timestamp is one this adapter sent. Matching is by message id, never by text. |
| Replies | `replyTo` is `<author>:<timestamp>`, the same format as an inbound envelope `id`. |
| Receipts | `send` returns the message timestamp as `messageId`. Delivery and read confirmations arrive on `adapter.deliveryUpdates`. |
| Errors | Typed `ChannelError`: `not_found` (unregistered recipient, unknown group), `auth` (account not registered or authorization failed), `rate_limited` with `retryAfterMs`, `forbidden` (untrusted identity), `too_large`, `network`. |
| Reconnect | Connection loss reconnects with exponential backoff. An `auth` failure stops retrying and sets the state to `failed`. |
| Attachments | Inbound bytes arrive as `Uint8Array` (fetched with `getAttachment`; failures are counted in `metadata.attachmentsUnavailable`). Outbound accepts bytes only, not urls. |
| Secrets | The account is `Redacted`, kept out of errors, receipts, state and logs. Spawn and socket failures keep only `{ name, code }` as the `cause` (Node's own error carries the account in `spawnargs`). The last 50 `signal-cli` stderr lines are held in a ring with the account masked and readable through `transport.diagnostics()`. A line over 1 MiB, or more than 1000 unread notifications, fails the connection with a `too_large` error instead of growing memory. |

The adapter's `deliveryUpdates` stream is not yet published as an EventBus event by `ChannelService`; read it directly if you need receipts today.

### Telegram (bot)

`TelegramChannelAdapter` uses the Telegram **Bot API** with a bot token. It is not a user session: there is no phone login and no MTProto. Inbound is pushed to the agent (long polling or webhook) and `ChannelService` sends the reply itself and gets a receipt.

**Setup**

1. In Telegram, message [@BotFather](https://t.me/BotFather), send `/newbot`, and copy the token it gives you. Keep it in an environment variable or your key store, never in source.
2. Groups: by default a bot in a group only sees commands, replies to its own messages and messages that mention it (**privacy mode**). To let it read every message, send BotFather `/setprivacy`, pick the bot and choose **Disable**, then remove the bot from the group and add it back. If you leave privacy mode on, `mentionsSelf` is the signal to act on.
3. Create the adapter:

```typescript
import { Redacted } from "effect";
import { TelegramChannelAdapter } from "@reactive-agents/channels";

const telegram = new TelegramChannelAdapter({
  token: Redacted.make(process.env.TELEGRAM_BOT_TOKEN ?? ""),
});
```

**Polling or webhook**

| Mode | Use when | How |
|------|----------|-----|
| Long polling (default) | The agent runs anywhere with outbound HTTPS: laptop, home server, container. | Nothing to configure. `start()` calls `getMe` and then `getUpdates` in a loop. |
| Webhook | The agent has a public HTTPS URL. | `webhook: { secretToken, url }`. `start()` calls `setWebhook` with that secret, and your HTTP route passes each request to `telegram.handleWebhook({ body, headers })`. |

A bot can use only one of the two. If another process polls the same bot, or a webhook is set while you poll, Telegram answers `409 Conflict`; the adapter stops with a `ChannelError` that says so instead of retrying. The adapter never deletes your webhook for you. In webhook mode `handleWebhook` checks `X-Telegram-Bot-Api-Secret-Token` in constant time and rejects every request when no secret is configured.

To serve the webhook, mount the adapter on the gateway ingress server instead of writing your own route: `startIngress({ channelRoutes: [channelWebhookRoute("/channels/telegram", telegram)], onEvent })` (`channelWebhookRoute` is exported by `@reactive-agents/channels`, `startIngress` by `@reactive-agents/gateway`). It binds `127.0.0.1` by default, rejects non-POST requests and bodies over `maxBodyBytes` (default 1 MiB) before the adapter sees them, answers 408 to a sender that stalls the body past `bodyTimeoutMs` (default 10 s) and 503 beyond `maxInFlight` (default 64) concurrent requests, and maps adapter errors to generic status codes (a wrong secret is 401). When the agent cannot keep up and the adapter's inbound buffer stays full, a request waits at most `enqueueTimeoutMs` (default 5000, on `TelegramChannelAdapter` and `WebhookChannelAdapter`) and is then answered 429. See the gateway guide for the full list.

**Schedule delivery records.** `lastRun.delivery` uses the channel vocabulary: `adapterId`, `receiptStatus` (`sent`, `queued`, `delivered`) on success, `errorKind` (the `ChannelError` kind) and `retryable` on failure. Waiting events in the in-memory inbound queue are lost on restart; cron fires replay via the schedule registry.

**Restart safety.** The polling offset advances only after an update was handed to the inbound queue, so a crash replays at most the updates not yet handed off, and repeats are deduplicated by `update_id` and message id. To also survive a process restart, persist the offset: pass `onOffset: (offset) => save(offset)` and start with `initialOffset: await load()`. Without them Telegram re-sends unconfirmed updates itself (up to 24 hours).

**Behaviour**

| Concern | What the adapter does |
|---------|-----------------------|
| Identity | `telegram:<numeric user id>` with the username (or full name) as `displayName`. Allowlist entries use that key, e.g. `telegram:123456789`. |
| Conversations | A DM's `channelId` is the chat id; a group, supergroup or channel keeps its own id and the individual sender on every message. Forum topics map to `threadId` (`message_thread_id`). |
| Ids | An envelope `id` and a receipt `messageId` are `<chatId>:<messageId>`, because Telegram message ids are only unique per chat. `replyTo` on an inbound envelope is the replied-to `message_id`; on send it accepts that or an envelope id for the same chat. |
| `mentionsSelf` | `true` in a DM; in a group when the bot is mentioned (`@bot`, `/cmd@bot`), or when the message replies to one of the bot's messages. |
| Echoes | Messages from this bot, from any other bot, or with an id this adapter sent are flagged `isEcho`, so bots do not answer each other in a loop. |
| Text | `send` splits text longer than 4096 characters at paragraph, line or word boundaries (never inside an emoji or a code fence). `format: "markdown"` converts bold, italic, strike, links, headings and code to MarkdownV2 and escapes everything else; if Telegram still rejects the entities the text is resent as plain text. Plain text is sent untouched. |
| Attachments | Inbound files are downloaded to bytes (Telegram file URLs contain the token, so they are never exposed as url attachments); failures are counted in `metadata.attachmentsUnavailable`. Outbound PNG/JPEG bytes go as photos, other bytes as documents, and url attachments are passed to Telegram by reference. |
| Errors | `auth` (401), `forbidden` (403, bot blocked or removed), `not_found` (404 or "chat not found"), `rate_limited` with `retryAfterMs` from `retry_after` (429), `too_large` (413 or "message is too long"), `network` (transport and 5xx). A 409 conflict is a non-retryable error. |
| Rate limits | Outbound sends wait (never drop) to stay within Telegram's limits: about 30 messages per second overall, 1 per second per DM and 20 per minute per group. Override with `rateLimit` and `chatRateLimit`. |
| Reconnect | Network loss and 429 on `getUpdates` back off exponentially and resume from the offset. `auth` stops retrying and sets the state to `failed`. |
| Secrets | The token is `Redacted`, appears only in the request URL, and is scrubbed from every error, receipt, state and envelope. |

**Limits.** Telegram does not report delivery or read receipts to bots, so `capabilities.receipts` is `false` and `send` returns `status: "sent"`. The adapter sends typing indicators (`sendChatAction`) only when a route with `ack` asks for one.

### Writing an adapter

Implement `ChannelAdapter`, reuse the shared combinators (`withReconnect`, `makeOutboundRateLimiter`, `makeInboundDedupe`, `makeConnectionState`, `classifyChannelFailure`), and run the conformance suite from `packages/channels/tests/conformance/`:

```text
runAdapterConformance("MyAdapter", makeMyHarness)
```

You supply a fake platform (`AdapterHarness`) with no network and no tokens. The suite checks inbound normalization, idempotency, echo handling, group and thread identity, attachments, receipts, typed errors, secret redaction, namespaced identity, honest state, backpressure, outbound rate limiting and reconnect.

## Routes: One Connection, Many Agents

`.withChannels({ adapters, routes, agents })` starts a channel router. Each adapter is opened once. A **route** matches inbound conversations, names a target agent, and says who may talk and what a stranger may do.

```typescript
import { Redacted } from "effect";
import { ReactiveAgents } from "reactive-agents";
import { TelegramChannelAdapter } from "@reactive-agents/channels";

const telegram = new TelegramChannelAdapter({
  token: Redacted.make(process.env.TELEGRAM_BOT_TOKEN ?? ""),
});

const host = await ReactiveAgents.create()
  .withName("channel-host")
  .withProvider("anthropic")
  .withGateway()
  .withChannels({
    adapters: [telegram], // canonical ChannelAdapters only
    routes: [
      {
        id: "support",
        match: { channelId: telegram.id, conversation: "dm" },
        target: { agentId: "support" },
        owners: ["telegram:1001"], // set from code only, never from a message
        allow: ["telegram:2002"],
        // senderTools defaults to { _tag: "ReadOnly" } for non-owners
      },
    ],
    agents: {
      // a fresh builder per (route, role); the router narrows its tools before build()
      support: () => ReactiveAgents.create().withProvider("anthropic").withTools({ builtins: ["web-search", "file-write"] }),
    },
    meter: { reserveUsd: 0.05, maxMessagesPerDay: 500 }, // optional per-route cost and message caps
  })
  .build();

const handle = host.start(); // the router starts and stops with the gateway handle
await host.channelRouterStatus(); // { channels, routes, unrouted, dropped, activeSessions, durableStore }
```

How access works:

- **Fail closed.** A message no route claims is dropped and counted as unrouted. A denied sender never reaches an agent.
- **Owners run the agent's own tools. Everyone else gets `senderTools`**, which defaults to `ReadOnly`: only tools that declare `mutatesExternalState: false` and need no approval. Unclassified tools (custom, MCP, sub-agent) are removed. `Allowlist` keeps only named tools the agent already had.
- **The tool surface is decided when the agent is built**, not per turn and not by prompt. The router builds one agent per (route, role), so a sender never shares history or tools with an owner. Sender text reaches the model only as the user message; persona and instructions stay in the agent's own configuration.
- **The router is the only consumer of its adapters.** The gateway's legacy chat handler skips messages from adapters a router owns, so a routed message runs once, under the route's access decision.
- **State is in memory by default.** Message dedupe and turn caps reset on restart, and the router logs a warning at startup. Pass a durable `store` to keep them (see [Surviving a restart](#surviving-a-restart-the-durable-inbox)).
- This limits what an injected message can do. It does not make a model immune to injection, and read-only tools can still leak data they can read.

### Acknowledging slow turns

A tool turn can take 15 to 40 seconds, and the chat is silent until the final answer. Set `ack` on a route and the router behaves like a chat partner: it shows a typing indicator as soon as the turn starts and, if the turn is still running after `afterMs`, sends one short message, then the final reply.

```typescript
import type { RouteSpecInput } from "@reactive-agents/channels";

const route: RouteSpecInput = {
  id: "support",
  match: { channelId: "telegram", conversation: "dm" },
  target: { agentId: "support" },
  allow: ["telegram:2002"],
  ack: { afterMs: 4000, text: ["On it...", "Working on that..."], typing: true }, // all fields optional
};
```

- **Off by default.** No `ack`, or `ack: false`, sends nothing extra. `ack: {}` means typing on, and `"On it..."` after 4000 ms.
- **Fixed text is deterministic and zero-token.** The text is config (1 to 10 entries of at most 200 characters; the same message id always picks the same entry) and is never built from sender text. With `source: "model"` (below) the message can come from the agent instead.
- **Not history.** The ack goes straight to the adapter. The agent never sees it, and it is not recorded as an assistant reply.
- **Only for turns that run.** A turn that finishes before `afterMs`, a denied or dropped message and a turn the meter refuses get no ack. A failed ack is swallowed and reported as `ErrorSwallowed`; it never fails the turn. Acks go through the adapter's normal outbound rate limits, and each one publishes `ChannelTurnAcknowledged` (no text).
- **Model-written acks (`source: "model"`).** `ack: { source: "model" }` swaps the fixed text for the agent's own words. At `afterMs` the router sends, in order: (1) the agent's latest pre-tool narration, if the turn already produced some; (2) a one-line text from the session's `acknowledge` port; (3) the canned text. The port call starts when the turn starts, not at `afterMs`, so a cold model gets `afterMs` plus `modelTimeoutMs` of wall time. At `afterMs` the router uses the result if it is ready, otherwise waits up to `modelTimeoutMs` (1 to 30 000, default 12 000; sized for a cold model queued behind the turn's own calls) measured from `afterMs`, then falls back to canned with `ackFallbackReason: "timeout"`. The call is cancelled with the turn; a turn that ends before `afterMs` sends no ack. When narration wins, the prefetched port result is discarded. Narration pushed after the ack went out is dropped, so there is still exactly one ack. Model text is sanitized before sending: markdown stripped, one line, at most 300 characters. A port that fails, times out or returns nothing falls back to canned and never fails the turn. `ChannelTurnAcknowledged` carries `source: "canned" | "narration" | "model"`. When the route asked for `model` but canned text went out, the event also carries `ackFallbackReason: "timeout" | "empty" | "thinking_only" | "error"`: the router records `timeout` and a port defect (`error`) itself; a port reports the others by returning `{ text, fallbackReason }` instead of a bare string. The `channels` package never calls a model; the resolver owns that.
- **Typing support is per adapter.** The optional `ChannelAdapter.sendTyping` is implemented by Telegram (`sendChatAction`, refreshed every 4 seconds until the reply). Adapters without it still send the ack message. Webhook routes reject `ack`.

**When a turn fails.** A turn that the route accepted but could not finish (it ran past `turnTimeoutMs`, default 120 000, or the agent errored) no longer ends in silence. The router sends the sender one fixed plain-text notice through the adapter. After a timeout it reads `That took longer than the 120-second turn limit, so I stopped. Send it again, or ask me to continue.` (the limit is the route's `turnTimeoutMs` in seconds); any other failure gets `Something went wrong and I could not finish that. Send it again, or ask me to continue.` The notice never contains the error text. `ChannelTurnCompleted` with `ok: false` is published as before. No notice goes out for simulations, unregistered adapters, or denied and dropped messages, and a failed notice send is swallowed and never throws. Set `failureNotice: false` on a route to opt out (default `true`).

**For resolver authors.** Two optional ports back `source: "model"`. A resolver that implements neither still gets the canned text.

```typescript
import { Effect } from "effect";
import type { AgentResolver } from "@reactive-agents/channels";

const resolver: AgentResolver = {
  open: () =>
    Effect.succeed({
      send: (turn) =>
        Effect.sync(() => {
          // 1. Narration: onProgress exists only on source:"model" routes. Call it with the
          //    text the agent wrote before its first tool call.
          turn.onProgress?.("Checking the repo");
          return { text: "done" };
        }),
      // 2. Ack port: text only, never fails. Run a tiny side call (no tools, short max tokens)
      //    and do not append it to the session history. Return a string, or
      //    { text: "", fallbackReason: "empty" | "thinking_only" | "error" } when the call gave
      //    nothing usable, so the router can report why the canned text was sent.
      acknowledge: (turn) => Effect.succeed(`One moment, looking at: ${turn.text.slice(0, 40)}`),
      close: Effect.void,
    }),
};
```

### Surviving a restart (the durable inbox)

By default a restart loses queued messages and forgets which messages it already answered, so a platform that redelivers an update can run a turn twice. Opt in to a SQLite store and the router keeps every accepted message:

```typescript
import { openSqliteRouterStore } from "@reactive-agents/channels";
import { Effect } from "effect";

const store = await Effect.runPromise(
  openSqliteRouterStore({ path: "./.agent/router.db" }), // Node and Bun; ":memory:" for a throwaway
);

// .withChannels({ adapters, routes, agents, store })
```

With `.withChannels` you can skip opening the store yourself: `inbox: { path: "./.agent/router.db" }` (plus the optional `retentionMaxAgeMs`, `retentionMaxRows`, `maxAttempts`, `leaseTtlMs`) opens the SQLite store when the router starts and closes it after the router stops. If you also pass `store`, the explicit store wins and the host logs a warning.

- **One row per accepted message**, with a status: `received`, `running`, `done`, `failed` or `dropped`, plus the dedupe key (adapter id and the platform's message id), attempt count and last error. A denied sender, an unrouted message or a rate drop is recorded `dropped`, a failed turn `failed`.
- **Dedupe survives restart.** A redelivered message that was already accepted is refused, answered or not.
- **Crash recovery.** At start the router returns turns a dead process left `running` to `received` and runs them again, oldest first, up to `maxAttempts` (default 3). A message that runs out of attempts becomes `failed`; the router publishes `ChannelInboxRetried` and `ChannelInboxFailed` events (payloads carry no message text). `leaseTtlMs` (default 0) is how old a `running` row must be to count as orphaned: the account lease already guarantees one router per inbox, so raise it only if several processes share one file. A replayed message runs as its own turn, without batching.
- **At least once, not exactly once.** A turn killed after the agent acted but before the reply went out runs again. Keep tools idempotent or approval-gated.
- **Retention is bounded.** Finished rows are pruned by age (`retentionMaxAgeMs`, default 7 days) and count (`retentionMaxRows`, default 50 000). A key pruned away can be accepted again. Rows still `received` or `running` are never pruned. A finished row keeps no message text, only the key and status.
- **Turn caps persist too**, so a restart does not reset a sender's hourly limit.
- **Status.** `agent.channelRouterStatus()` reports `durableStore: true` and `inbox: { received, running, done, failed, dropped }`.
- A store failure never stops the router: it is reported as `ErrorSwallowed` and the message is answered without durability.

### Bursts and follow-ups (`batchWindowMs`, `midRun`)

People send several short messages, or a correction while the agent is still working. Two route fields decide what happens. Both default to today's behavior.

```typescript
import type { RouteSpecInput } from "@reactive-agents/channels";

const route: RouteSpecInput = {
  id: "main",
  match: { channelId: "telegram" },
  target: { agentId: "assistant" },
  owners: ["telegram:123"],
  batchWindowMs: 1500, // join one sender's burst into one turn
  midRun: "interrupt", // "queue" (default) | "fold" | "interrupt"
};
```

- **`batchWindowMs`** (0 to 30 000, default 0 = off). Messages from one sender in one conversation that arrive within the window become one turn input: texts joined by a newline in arrival order, attachments together, every source id in `message.metadata.batch.sourceIds`. The window starts at the first message. The turn runs once and each inbox row settles with its outcome. A `ChannelInboxBatched` event records the size and source ids (`ChannelInboxFolded` and `ChannelInboxInterrupted` do the same for `midRun`). Batching holds one inbound slot per waiting message, so very long windows on busy channels can crowd the adapter's inbound concurrency.
- **`midRun: "queue"`** (default): a message that arrives while a turn runs waits in the bounded per-conversation queue and runs as its own turn.
- **`midRun: "fold"`**: the message joins the running turn. A resolver that supports it calls `turn.takeFolded()` at a safe boundary (between tool calls) and receives the new texts once. Texts nobody drains run as one follow-up turn right after, so a resolver that ignores `takeFolded` behaves like a combined queue.
- **`midRun: "interrupt"`**: the message cancels the running turn with a typed `turn_interrupted` error (published as `ChannelTurnCompleted` with `ok: false`; the sender gets no failure notice) and a new turn starts from the original and new text joined. Partial work stays in the session history. The turn rate cap is not charged again for the restart.
- **With `.withChannels()` routes** the built-in resolver implements both. Routes using `fold` or `interrupt` run each conversation on its own agent instance and stream the turn. `fold`: the messages that arrived mid-turn are attached to the result of the next custom tool call (`{ result, userMessages }`); a turn that only calls built-in tools drains nothing and the router runs the leftovers as one follow-up turn. `interrupt`: the running stream is aborted through its signal.
- Folded and interrupting messages are bounded by the same conversation queue size, and past it they are dropped as backpressure. Router simulations skip both fields. Webhook routes reject them, because the reply is the HTTP response.

### Reliable sends: the outbox (`outbox`, `minGapMs`)

Every message the strict router sends (replies, acks, failure notices, `router.deliver`) goes through an outbox. By default it behaves as before: one attempt, no pacing. Opt in to retries and pacing. `outbox` and `followUp` (next section) are options of `createChannelRouter` and of `.withChannels`, which passes them through.

```typescript
// .withChannels({ ..., outbox: { maxAttempts: 4, baseBackoffMs: 500, maxBackoffMs: 30_000 } })
// (or createChannelRouter({ ..., outbox }))
// or per route: { id: "main", ..., minGapMs: 1200 }
```

- **Retry.** Only errors the adapter marks retryable (`network`, `rate_limited`) are retried, with doubling backoff capped by `maxBackoffMs`. A platform `retryAfterMs` is honored up to that cap. `maxAttempts` defaults to 1 (no retry).
- **Order.** One conversation sends one message at a time, in call order, so a retrying message is never overtaken by a later one. Other conversations are not held up. A retry holds its conversation for at most `maxAttempts` times `maxBackoffMs`.
- **No silent failure.** A message that cannot be sent ends as a `failed` row and a `ChannelSendFailed` event (`adapterId`, `conversationId`, `attempts`, `kind`, `retryable`, `exhausted`; never the text). It is a typed core event. The turn outcome stays `Answered` with `deliveryError`. A failed failure-notice or ack send is recorded the same way instead of being dropped without a trace. `ChannelDeliveryFailed` still reports every individual attempt.
- **Pacing.** `minGapMs` (route, 0 to 60 000) or `outbox.minGapMs` (router default) keeps at least that gap between two sends into one conversation. Default 0 (off).
- **Durable with the SQLite store.** Rows are `pending`, `sent` or `failed` with attempts and last error; finished rows keep no text and are pruned with the inbox retention. After a crash the router sends the agent replies left `pending`, oldest first. It does not resend acks and notices (stale), nor a reply whose inbox turn is about to run again (that turn writes a fresh reply). Attachments are not stored, so an attachment message is not resumed. Delivery is at least once: a crash after the platform accepted a message but before the row was marked `sent` can send it twice.
- **Status.** With a durable store `agent.channelRouterStatus()` adds `outbox: { pending, sent, failed }`. The in-memory default reports nothing.

### Follow-up timers (`followUp`)

An agent can ask to be woken in a conversation later ("check the build in 20 minutes"). Timers live in their own store, separate from the inbox and from cron schedules, and are durable with the SQLite store.

```typescript
import { createChannelRouter, makeFollowUpTool } from "@reactive-agents/channels";

// createChannelRouter({ ..., followUp: { maxPending: 5, maxHorizonMs: 7 * 86_400_000, pollMs: 1000 } })
// or followUp: true for the defaults.

// In your AgentResolver, a session that supports follow-ups reads req.followUp:
//   open: (req) => { const tool = req.followUp ? makeFollowUpTool(req.followUp) : undefined; ... }
```

- **The tool.** `makeFollowUpTool(port)` returns a `follow-up` tool definition (`name`, `description`, `parameters`, `execute`) shaped like a tools-package definition. `{ in: "90m", note }` or `{ at: "2026-11-20T09:00:00Z", note }` sets a timer; `{ cancel: id }` cancels one; no arguments lists the pending ones. It never fails: a refused request comes back as `{ ok: false, reason, error }` so the agent can adapt. The resolver registers the tool on the agent it opens. With `.withChannels({ followUp })` the runtime resolver does this for you: each conversation runs on its own agent instance (built when the session opens, disposed when it closes) with the `follow-up` tool bound to that conversation. A `ReadOnly` sender surface never gets the tool; an `AgentDefault` surface does, and an `Allowlist` surface only when it names `follow-up`.
- **Bounds.** At most `maxPending` timers per conversation (default 5), no further out than `maxHorizonMs` (default 7 days), no nearer than `minDelayMs` (default 5 s), notes up to 500 characters. An agent can only set, list and cancel its own conversation's timers.
- **Waking.** A poller (`pollMs`, default 1000) turns each due timer into an inbound message `Follow-up you scheduled: <note>` for that conversation. It takes the normal path: dedupe on `timer-<id>`, the sender's access and role, the turn-rate caps, the conversation queue. The timer re-enters the route that created it, whatever the route's `when` filter says, and counts as the sender who was in the session when it was created; if access has changed since, it is denied. A wake-up in a group passes the mention rule (the agent addressed itself) but not `groups: "off"`.
- **Restart safe.** A timer that came due while the process was down fires on the first poll. A crash between the wake-up and the `fired` mark fires it again, and dedupe refuses the duplicate. Delivery is at least once.
- **Receipts.** `ChannelFollowUpScheduled`, `ChannelFollowUpFired` and `ChannelFollowUpCancelled` (typed core events; ids and times, never the note). Status adds `timers: { pending, fired, cancelled }`.
- **Not recurring.** Repeats stay in cron schedules (gateway). Simulations get no `followUp` port.

### Starting a new conversation (`/new`)

A per-conversation route keeps history, so a wrong early reply can keep shaping later ones. A route owner (a `platform:userId` in `owners`) can send `/new` or `/reset` as the whole message to start over:

```typescript
import type { RouteSpecInput } from "@reactive-agents/channels";

const main: RouteSpecInput = {
  id: "main",
  match: { channelId: "tg" },
  target: { agentId: "assistant" },
  owners: ["telegram:123"],
  resetCommands: ["/new", "/reset"], // the default; [] turns it off; at most 5 commands like "/name"
};
```

- **Owner only.** From anyone else the text is an ordinary message. Matching is case-insensitive, accepts Telegram's `/new@my_bot` form, and needs the command to be the whole message (`/new please` is plain text).
- **Never reaches the agent.** The router calls the session's `reset`, closes the session and drops it from the cache, replies `Started a new conversation.`, and opens a fresh session on the next message. It is not rate-capped and waits for a turn already running in that conversation. A route with `session: "stateless"` has no history; it just gets the confirmation.
- **Receipt.** Each reset publishes `ChannelConversationReset` (`routeId`, `role`, `ok`, `reason?`; no text). If the resolver's `reset` fails, the sender gets `Could not start a new conversation.`, `ok` is `false` and the session is kept.
- **Strict router only.** Applies to `createChannelRouter`; the `ChannelService` pipeline is unchanged.

**With `.withChannels()` routes.** The built-in resolver implements `reset` for per-conversation sessions: it flushes and clears the live session, then empties the stored chat history for that conversation (when the memory layer persists sessions), so a restart does not bring it back. A store failure is reported to the sender as `Could not start a new conversation.` and the session is kept.

**For resolver authors.** If your history lives outside the session object (a chat store keyed by `conversationKey`), implement the optional `reset` on the `RoutedSession` and clear that store there. Otherwise the next `open` for the same key reads the old history back, including after a restart.

```typescript
import { Effect } from "effect";
import type { AgentResolver } from "@reactive-agents/channels";

const chat = new Map<string, string[]>(); // your persisted history, keyed by conversation

const resolver: AgentResolver = {
  open: (req) =>
    Effect.succeed({
      send: (turn) =>
        Effect.sync(() => {
          const history = chat.get(req.conversationKey) ?? [];
          chat.set(req.conversationKey, [...history, turn.text]);
          return { text: `${history.length + 1} messages so far` };
        }),
      reset: Effect.sync(() => void chat.delete(req.conversationKey)), // Effect<void, RoutingError>
      close: Effect.void,
    }),
};
```

The built-in resolver behind `.withChannels({ routes, agents })` implements both ports for you. On a `source: "model"` route, a per-conversation turn streams, and the text the agent writes before its first tool call goes to `turn.onProgress` (a final answer is never sent as narration). `acknowledge` is a separate tool-less completion of at most 60 tokens (one short sentence): it bypasses the session's turn queue, is not added to chat history, and returns an empty string on any failure so the router falls back to the canned text. Stateless routes get the `acknowledge` port but no narration. Custom resolvers can reuse this by building on `makeChannelAgentResolver`.

Read state from the agent: `agent.channelStatus()` gives the adapters and session counters (`null` before the gateway starts), `agent.channelRouterStatus()` the router view above (channels, routes, drops, sessions). `agent.gatewayStatus()` carries the inbound queue (`ready`, `deferred`, `capacity`, `overflow`, `dropped`).

If the router cannot start (for example a route names a channel that is not configured), the gateway stops instead of running with no inbound channels: `handle.done` resolves with a summary whose `error` explains why.

Routes (not adapters or agent factories) serialize with the rest of the agent as `channelRoutes` in `AgentConfig`. `.withChannels({ adapters, triggers })` keeps working for the single-agent path.

## Troubleshooting

### Signal registration fails
- Ensure Docker is running
- Signal requires a CAPTCHA — see the registration script
- The Docker image requires glibc (not Alpine) for signal-cli's native library

### Telegram session expired
- Re-run `./docker/telegram-session.sh`
- Update `.env.telegram` with new session string

### `TELEGRAM_CHAT_ID environment variable required`
- You are running the **wrong** PyPI `telegram-mcp` (hosted relay), not chigwell’s Telethon server.
- Use `uvx --from git+https://github.com/chigwell/telegram-mcp.git@<tag> telegram-mcp` (or upstream’s documented install), not bare `uvx telegram-mcp` from PyPI.

### `BotMethodInvalidError` / `GetDialogsRequest` / “cannot be executed as a bot”
- chigwell/telegram-mcp is a **user-account** Telethon client (full dialogs, send as you). It does **not** work with a **@BotFather bot** session string.
- Regenerate `TELEGRAM_SESSION_STRING` using `./docker/telegram-session.sh` and sign in with your **personal Telegram account** (SMS / Telegram OTP), not a bot token.

### Agent not responding to messages
- Check heartbeat interval (default: 15s)
- Verify daily token budget isn't exhausted
- Check `ProactiveActionSuppressed` events for policy blocks
- Ensure the Signal container (if used) is running: `docker ps`
- For Telegram, confirm `uvx` resolves chigwell’s package and that `TELEGRAM_*` env vars are set for the MCP subprocess
