Decide which tools an agent may call, how they are shown to the model, what each is allowed to touch, and how many times it may run.

## Disclosure: how permitted tools are shown

`disclosure` changes how permitted tools reach the model, never which tools are permitted:

- `"all"` sends every permitted tool's schema each turn.
- `"index"` sends a compact index of permitted tools.
- `"discover"` lets the agent find permitted tools on demand with `discover-tools`.

Visibility follows the size of the configured set, never keyword overlap between the task and a tool description. With 15 or fewer domain tools (custom tools and opted-in built-ins; meta-tools are not counted) and no classifier narrowing, every one is shown from turn 1, so "what is bitcoin worth" cannot hide a `crypto-price` tool. Above 15, lazy disclosure shows the tools the task names or matches plus what the run has used, and the rest stay reachable through `discover-tools`. A call to a registered tool that was not shown still resolves and runs. `disclosure: "discover"` stays strict at any size.

Left unset, the model tier picks the mode. An explicit `.withTools({ disclosure })` wins over the deprecated `.withHarness` switches, the `RA_*` environment flags and `contextProfile.toolDisclosureMode`. Each run records the winning mode and its source in `run-started.config.disclosure`.

## Scoping the Tool Set

Two `.withTools()` options control which tools the agent can reach, with different strictness:

```typescript
// Hard restriction — the agent can ONLY see/call these tools.
agent.withTools({ allowedTools: ["github/list_commits", "file-write"] })

// Soft focus — all tools remain callable, but these are surfaced/prioritized.
agent.withTools({ focusedTools: ["crypto-price"] })
```

- **`allowedTools`** is a hard allowlist. Anything outside it is pruned before the model sees it — use it to lock an agent to a known surface (and to give local-model tool selection a safety net).
- **Attached MCP servers stay visible.** Tools of a server you attached with `.withMCP()` join the allowlist automatically, so you do not list each `server/tool` by hand. To limit a server to a subset, name its tools in `allowedTools` (`"umami/get-stats"`): once any of that server's tools is named, the list is authoritative for that server. A forbidden tool from `.withContract()` stays hidden.
- **`focusedTools`** is soft guidance. The full toolset stays available, but the focused names are highlighted so the model gravitates to them without being blocked from others. Resolution order: `focusedTools` (soft guidance) → `allowedTools` (hard restriction) → all tools.

### Policy is enforced at execution, on every strategy

Schema pruning is only the first line. As of v0.14 the tool policy — `allowedTools` plus the forbidden-tools deny-list from [`.withContract()`](/reference/builder-api/) — is also enforced at the shared tool-execution choke point that **every** strategy passes through, including planned steps (plan-execute, blueprint), hallucinated tool names the model invents, and code generated by the `code-action` sandbox. A violating call is blocked *before* dispatch and recorded as a failed observation the model can route around — it is never executed. The deny-list beats everything; a non-empty `allowedTools` is a hard whitelist; kernel meta-tools (`final-answer`, `recall`, …) always pass so the loop can still terminate.

### Overriding a tool's risk level

Every tool declares a `riskLevel` (`"low"`, `"medium"`, `"high"` or `"critical"`). Built-ins ship fixed levels: `file-read` is `"medium"`. Override any tool's level by name with `riskLevels`, built-in, custom and MCP tools alike:

```typescript
agent.withTools({
  builtins: ["file-read"],
  riskLevels: { "file-read": "low" },
})
```

The level matters when a model prints a tool call inside prose or code instead of calling it on its own, as in `const x = fileRead("/abs/data.csv")`. The text tool-call parser accepts such an embedded call only for `"low"` tools; for anything else it refuses the call and asks the model to restate it as a standalone call. The override does not change the tool's definition in the registry. It applies to the tool definitions the agent reads during a run. A custom `ToolApprovalGate` still receives the declared level. Maps from several `.withTools()` calls merge, and the later call wins for the same name. A name that matches no tool logs a build warning and is ignored.

### Capping calls per tool

Limit how many times a tool may run in one agent run with `maxCallsPerTool`:

```typescript
agent.withTools({
  builtins: ["web-search"],
  maxCallsPerTool: { "web-search": 3 },
})
```

The cap counts calls for the whole run, every turn and pass, including several calls the model makes in one turn. A call past the cap is not run. The model gets a tool result for that call that says the tool was not run and why, so it can answer with what it has or use a different tool. Tools you do not name have no cap, and a name that matches no tool has no effect. Each cap must be a positive integer; `.withTools()` throws `ToolsOptionError` otherwise. To keep a tool from running at all, leave it out of `allowedTools`. Every strategy enforces the cap.

Sub-agents run under the parent's caps. A child started with `spawn-agent` gets them as they are. The model writes the `spawn-agent` arguments, so it cannot loosen them. A `.withAgentTool()` sub-agent can set its own `maxCallsPerTool`. Its map is merged over the parent's, and its cap wins for the same tool:

```typescript
agent
  .withTools({ maxCallsPerTool: { "web-search": 3, "http-get": 5 } })
  .withAgentTool("researcher", {
    name: "researcher",
    tools: ["web-search", "http-get"],
    maxCallsPerTool: { "web-search": 6 }, // researcher: web-search 6, http-get 5
  })
```

## Working directory (workspace)

Set the agent's working directory with `workspace`, next to `terminal`:

```typescript
const agent = await ReactiveAgents.create()
  .withProvider("anthropic")
  .withTools({
    builtins: ["file-read", "file-write", "file-edit", "list-directory"],
    terminal: true,
    workspace: "/home/me/project",
  })
  .build();

await agent.run("Add a unit test for parseDate");
```

The workspace is one root for every tool that touches the file system:

- **File tools** (`file-read`, `file-write`, `file-edit`, `list-directory`, `grep`) resolve relative paths against the workspace and refuse paths outside it.
- **`shell-execute`** runs with the workspace as its working directory. A file the agent wrote with `file-write` is where the shell's `ls` or `bun test` finds it.
- **Sub-agents** inherit the workspace.

The `shell-execute` definition also carries `commandPolicy`, a typed summary of what it may run: `allowedCommands`, `notEnabledCommands`, `sandbox` and `workingDirectory`. It is read from the same allowlist the handler enforces. `shellCommandAvailability(definition.commandPolicy)` from `@reactive-agents/tools` returns which allowed commands exist on PATH, cached and without spawning a process (host shell only). A tool call with a missing required parameter now returns an error that names the parameter and shows a valid example call, for example `shell-execute({"command":"git log --oneline -5"})`.

Override it for one run with the `workspace` run option. `run()`, `runStream()` and `runEffect()` take it:

```typescript
await agent.run("Fix the failing test", { workspace: "/home/me/other-project" });
```

Chat turns take it too: `agent.chat(msg, { useTools: true, workspace })`, `session.chat(msg, { useTools: true, workspace })` and `session.runStream(msg, { workspace })` run that turn in the directory, so one session can move between projects without a rebuilt agent. The direct (no-tools) chat path runs no tools, so the option does nothing there.

A durable run (`.withDurableRuns()`) stores its run `workspace` with the run. `resumeRun()`, `approveRun()`, `denyRun()`, `respondToInteraction()` and `fork()` run in that directory again, from any process. If the directory no longer exists, the resumed run rejects with an error naming it. It does not fall back to another directory.

When more than one is set, this order decides: the run option, then `.withTools({ workspace })`, then an ambient `withFileRoot()` from `@reactive-agents/tools`, which still works as before. With none set, file tools use `process.cwd()` and `shell-execute` uses a fresh `/tmp` sandbox directory.

A relative path resolves against `process.cwd()` and is stored as an absolute path. It must name an existing directory. Otherwise `.withTools()` throws `ToolsOptionError`, `run()` rejects before anything runs, and `runStream()` ends with one `StreamError`. `toConfig()` writes it as `tools.workspace`.

**Workspace and `terminal.cwd`.** The shell config's `cwd` and `allowUnsafeCwd` keep their meaning, measured against the workspace:

| `terminal` config | With a workspace | Without a workspace |
| --- | --- | --- |
| no `cwd` | runs in the workspace | runs in a fresh `/tmp` sandbox dir |
| `cwd: "pkg"` (relative) | runs in `<workspace>/pkg` | refused (not under `/tmp`) |
| `cwd` outside the workspace | refused | allowed only under `/tmp` |
| `cwd` outside, `allowUnsafeCwd: true` | runs there | runs there |

The working directory is not a sandbox for shell commands. The command allowlist and blocklist are what limit the shell. `cwd` only decides where relative paths in a command land. The shell never sees your real home directory. With a workspace, each command gets a fresh, private `HOME` and `TMPDIR` outside the workspace, deleted when the command ends, so `~`, dotfiles and tool caches never land in your project (caches do not persist between commands). Without a workspace, the shell's own throwaway sandbox directory is `HOME`.

Every path in a command, including a redirect target, must stay inside the working directory, and writes to system paths such as `/etc/` and `/dev/` are refused. One exception: a redirect whose target is exactly `/dev/null` is allowed, so `cmd 2>/dev/null`, `cmd >/dev/null 2>&1`, `cmd &>/dev/null` and `cmd </dev/null` run. Any other `/dev/` target (`>/dev/sda`, `>/dev/null2`, `>/dev/./sda`) is still refused, and so is anything glued after the null redirect (`2>/dev/null>/etc/x`). The read-only `git` toolset shell also allows redirects to exactly `/dev/null` (`git log 2>/dev/null`) and refuses output redirects to any other file.
