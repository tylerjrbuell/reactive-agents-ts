Long-running agents crash. The machine reboots, the container is rescheduled, a
deploy rolls the process. **Durable execution** lets an agent survive that: every
iteration is checkpointed to disk, and a fresh process can reconstruct the run
from its last checkpoint and finish it — without re-doing completed tool work.

Side effects are handled exactly once where the framework can observe them:
each tool call is durably recorded (an awaited pre-dispatch write, then a
terminal outcome write), so a crash between "the tool succeeded" and "the
checkpoint committed" is resolved on resume instead of silently replayed. If
the recorded outcome proves the effect already happened, the stored result is
injected and the tool is NOT re-executed; if only the pre-effect write
committed, the call replays and the run's trust receipt names it
`ambiguous-then-replayed` in `receipt.effects[]` — the honest case where the
effect may or may not have happened (the tool itself can key idempotency on
the stable call identity to close it fully). Ordinary receipts are unchanged.

*Process A checkpoints each step, then is killed mid-run. Process B — a fresh process, same agent, same store — finds the crashed run on disk and finishes it. [Demo source](https://github.com/tylerjrbuell/reactive-agents-ts/blob/main/apps/examples/src/demos/durable-resume.ts).*

## Enabling durable runs

Opt in with `durableRuns` (declarative) or `.withDurableRuns()` (builder). Absent this call there is zero overhead: no
store, no database file, no checkpoint writes.

<Tabs syncKey="syntax">
  <TabItem label="Declarative">
```typescript
import { createAgent } from "reactive-agents";

const agent = await createAgent({
  name: "research-bot",
  provider: "anthropic",
  systemPrompt: "You are a thorough research assistant.",
  reasoning: {},
  tools: { builtins: ["web-search"] },
  durableRuns: { dir: "./.runs", checkpointEvery: 1 },
});
```
  </TabItem>
  <TabItem label="Builder">
```typescript
import { ReactiveAgents } from "reactive-agents";

const agent = await ReactiveAgents.create()
  .withName("research-bot")
  .withProvider("anthropic")
  .withSystemPrompt("You are a thorough research assistant.")
  .withReasoning()
  .withTools({ builtins: ["web-search"] })
  .withDurableRuns({ dir: "./.runs", checkpointEvery: 1 })
  .build();
```
  </TabItem>

Declarative `durableRuns` / builder `withDurableRuns` options:

| Option | Default | Meaning |
|---|---|---|
| `dir` | `~/.reactive-agents/<agentId>` | Directory for the SQLite run store (`runs.db`). |
| `checkpointEvery` | `1` | Persist a snapshot every N iterations. |
| `retention.keepCompleted` | `50` | Keep the newest N `completed` runs and delete older ones. `0` removes the count limit. |
| `retention.maxAgeDays` | `30` | Delete `completed` runs older than N days. `0` removes the age limit. |
| `retention.compactCheckpoints` | `true` | For `completed` runs, keep only the final checkpoint and drop tool-effect rows. Set `false` to keep every iteration's checkpoint, which `agent.fork()` can restart from. |

### Retention

A checkpoint is a full kernel-state snapshot, so an unbounded store grows by hundreds of KB per tool-using turn. The store prunes itself when a durable run starts on the streaming path (`runStream` and the run-control plane), using the defaults above unless you set `retention`. Only runs with status `completed` are ever deleted or compacted. A run you can still resume (`stopped`, `paused`, `failed`, `awaiting-approval`, `awaiting-interaction`, or `running` with a checkpoint) is never touched, whatever its age or the count. A prune failure is swallowed and never fails the run.

```typescript
import { ReactiveAgents } from "reactive-agents";

const agent = await ReactiveAgents.create()
  .withProvider("anthropic")
  .withDurableRuns({ retention: { keepCompleted: 200, maxAgeDays: 90, compactCheckpoints: false } })
  .build();
```

To read an agent's store from another process (a dashboard, a supervisor),
resolve the default directory with `defaultDurableRunsDir(agentId)` instead of
rebuilding the path; the framework uses the same function. Each store operation
(`listDurableRuns`, or an `Effect.provide(RunStoreLive(dbPath))` of your own)
opens the SQLite file and closes it when the operation ends, so a host that
polls the store keeps no files open.

```typescript
import { join } from "node:path";
import { Effect } from "effect";
import { defaultDurableRunsDir, listDurableRuns } from "@reactive-agents/runtime";

const dbPath = join(defaultDurableRunsDir("research-agent"), "runs.db");
const runs = await Effect.runPromise(listDurableRuns({ dbPath, status: "running" }));
```

Each checkpoint is a **lossless serialized `KernelState`** — iteration counter,
reasoning steps, scratchpad, tools used, token accounting, and the provider
message thread. Checkpoints fire at every iteration boundary on the streaming
run path (`runStream` / the run-control plane).

## Resuming a run

After a crash, build the **same agent** in a new process and call `resumeRun`:

```typescript
// List runs to find what's resumable.
const runs = await agent.listRuns();
// → [{ runId, agentId, task, status, configHash, updatedAt }, ...]

const crashed = (await agent.listRuns({ status: "running" }))[0];
if (crashed) {
  const result = await agent.resumeRun(crashed.runId);
  console.log(result.output);
}
```

`resumeRun(runId)`:

1. Loads the highest-iteration checkpoint for the run.
2. Verifies the agent config still matches (see the guard below).
3. Seeds the restored `KernelState` and continues the reasoning loop to
   completion.
4. Flips the run status to `completed` (or `failed`).

`listRuns(filter?)` enumerates persisted runs, newest-updated first, optionally
filtered by `status` (`running` | `paused` | `awaiting-approval` | `completed`
| `failed`).

Both methods require `.withDurableRuns()`; calling them on a non-durable agent
throws.

### Completed tools are not replayed

Resume does **not** re-execute tools that already ran — their results live in the
restored steps and message thread. The agent picks up where it left off. (Side
effects from completed tools are therefore not repeated; in-flight work at the
moment of the crash is re-attempted from the last checkpoint boundary.)

### Continue a loop-stopped run

A loop guard can end a run that was making no progress (the same call repeated, thoughts going in circles). On a durable agent that stop is not a dead end. The run leaves its final state as a checkpoint, and the result and the run row say so:

```typescript
const result = await agent.run("Find the release date and write it up");
if (result.resumable) {
  console.log(result.loopStop);
  // → { reason: "loop_graceful", repeatedTool: "web-search",
  //     toolsDone: [{ tool: "read-file", calls: 1 }], unfinished: ["write notes.md"], iteration: 4 }

  const continued = await agent.resumeRun(result.runId!, {
    note: "The notes file is in ./docs.", // optional: appended to the corrective guidance
    extraIterations: 8,                   // optional: default 10
  });
}
```

`result.runId`, `result.loopStop` and `result.resumable` are set for durable runs. `listRuns()` rows carry the same `loopStop` and `resumable`, so a UI can offer Continue later. Resuming:

- continues from the final checkpoint with guidance that names what was done, what is unfinished, and what not to repeat, with the original task as the goal;
- does not re-run completed tool steps (their results are in the restored state) and does not re-trip on the old repeats;
- gives the run a fresh iteration budget (`extraIterations`, default 10) because the stopped run's own cap is already spent;
- checkpoints again, so a run that loops a second time can be continued again.

Any resume of a run whose iteration cap is spent (a `max_iterations` stop, including a cap a plan raised at run start) gets that many more iterations past where it stopped: `extraIterations` if given, else 10. A resume does not re-stop at the cap it already spent. A run that stopped with iterations left (a pause, an error) keeps its own cap unless you pass `extraIterations`.

`resumeRun(runId, { note?, extraIterations? })` fails `RunNotResumableError` when the run already completed. Plain `resumeRun(runId)` still resumes a crashed run.

### Stop, pause and continue any run

A loop stop is one kind of stop. Every durable run that does not complete is continuable from where it was, whatever ended it. The run row carries a typed `stop` record and a status:

| How it ended | `row.status` | `row.stop.kind` |
| --- | --- | --- |
| `agent.pauseRun(runId)` | `paused` | `user-paused` |
| `agent.stopRun(runId)`, `handle.stop()`, `handle.terminate()` | `stopped` | `user-stopped` |
| a loop guard | `stopped` | `loop` |
| the iteration budget ran out | `failed` | `budget` (`stop.reason` is `max_iterations` for the iteration cap, so a UI can word it apart from a token or cost budget) |
| a timeout | `failed` | `timeout` |
| an error | `failed` | `error` |
| the process died | `running` (stale) | none |

`row.resumable` is true for every row that did not complete and has a checkpoint (a `running` row with a checkpoint is a crashed run unless `agent.activeRunIds()` lists it as live). `result.stop` and `result.resumable` say the same on a run's own result. A user stop returns the answer so far as an honest partial: `result.success` is `false`, `result.outcome` is `"partial"`, `result.metadata.outstandingCriteria` contains `stopped_by_request`, and `result.output` holds the work done so far. `result.stop` names the stop and `resumable` says it can continue. The kernel checkpoints the stopped state itself, so `resumeRun` continues from that checkpoint and repeats no completed tool call.

```typescript
const running = agent.run("Research and write up the release");
// later, from anywhere in the same process:
await agent.pauseRun(runId);        // takes effect at the next iteration boundary; resolves once persisted
const row = (await agent.listRuns()).find((r) => r.runId === runId);
// row.status === "paused", row.stop.kind === "user-paused", row.resumable === true
const resumed = await agent.resumeRun(runId, { note: "Skip the benchmarks." });
```

- A pause or stop lands at the next iteration boundary. A tool that is already running finishes first and its result is journaled, so it never runs again on resume.
- The final checkpoint is the state after the last finished iteration, so resume repeats no completed step or tool call. A failed tool call is not recorded as done and runs again.
- A resumed run is a durable run again: it checkpoints, shows in `agent.activeRunIds()` and can be paused or stopped again.
- Resuming a user stop or pause adds a plain "continue where you left off"; a loop stop adds corrective guidance; an error, spent budget or timeout resumes the state as it is. `note` and `extraIterations` work for all of them.
- The cost on the hot path is one remembered reference per iteration. The final snapshot is serialized once, when the run is interrupted.

A durable chat turn that runs tools carries the same fields on its `ChatReply` (`runId`, `loopStop`, `resumable`). If the run failed, the history note for that turn says what was done and that Continue is available.

### Tool effects are recorded

Checkpoints alone leave a gap: a side-effecting tool can succeed after the last checkpoint and before the next one commits. On a crash in that window the tool would run again on resume. With `.withDurableRuns()`, each tool call is recorded in a `run_effects` row:

1. Before the tool runs, an `executing` row is written.
2. When it finishes, the terminal outcome (succeeded or failed) is written over that row.

On `resumeRun()`, the run reads those rows:

- **Succeeded:** the stored result is injected into the thread. The tool is not run again.
- **No terminal row (crashed mid-call):** the call is replayed, and the run's trust receipt names it `ambiguous-then-replayed`, so you can see which effects may have run twice.

```typescript
async function recoverAfterCrash(crashedRunId: string) {
  const agent = await ReactiveAgents.create()
    .withTools({ builtins: ["file-write"], workspace: "./out" })
    .withDurableRuns({ dir: "./.runs", checkpointEvery: 1 })
    .build();

  const resumed = await agent.resumeRun(crashedRunId);
  // receipt.effects[] names any call replayed as `ambiguous-then-replayed`
  return resumed;
}
```

Tools that call external systems (payments, email, webhooks) should still use an idempotency key, because a crash can leave the outcome unknown.

## The config-hash guard

A run is captured under a specific agent identity. Resuming it under a materially
different agent — a changed system prompt, a different provider — would be
incoherent. `resumeRun` guards against this: the run stores an identity hash
(system prompt + provider) at capture time, and resume recomputes it. On a
mismatch it fails with `DurableConfigMismatchError` rather than silently
continuing under the wrong configuration.

```typescript
import { DurableConfigMismatchError } from "reactive-agents";

try {
  await agent.resumeRun(runId);
} catch (e) {
  if (e instanceof DurableConfigMismatchError) {
    // Agent config drifted since the run was captured.
  }
}
```

An unknown run id (or a run with no checkpoint) fails with
`DurableRunNotFoundError`.

## Kill it, resume it

The guarantee end to end: a run captured in one OS process is reconstructed and
finished in a **different** process, purely from the on-disk checkpoint.

{/* docs-skip-typecheck */}
```typescript
// Process A — does work, then is hard-killed (SIGKILL, crash, reboot).
const a = await buildAgent();          // .withDurableRuns({ dir })
for await (const _ of a.runStream(task)) { /* ... process dies mid-run ... */ }

// Process B — a fresh start, same agent config, same dir.
const b = await buildAgent();          // .withDurableRuns({ dir })
const runId = (await b.listRuns())[0].runId;
const result = await b.resumeRun(runId);   // reconstructs + completes
```

## Human-in-the-loop builds on this

tool call pauses the run (`status: "awaiting-approval"`), persists it, and a human
approves or denies — from any process — to resume from the exact checkpoint. See
