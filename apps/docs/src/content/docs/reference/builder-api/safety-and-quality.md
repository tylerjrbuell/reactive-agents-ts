Methods that constrain and check what the agent does: guardrails and kill switch, contracts, output verification and judgment, grounding, typed output, and the approval and durable-run controls. Part of the [builder reference](/reference/builder-api/).

## Safety and quality methods

| Method                               | Description                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `withGuardrails(options?)`           | Toggle detectors: `{ injection?, pii?, toxicity?, customBlocklist? }` (all default **on** when guardrails are enabled), plus opt-in judgment battery fields: `enableJudgmentBattery?`, `judgmentStrictness?: "additive" \| "jev-primary"`, `judgmentActionThreshold?`, `judgmentReviewThreshold?`, `screenOutputs?` — see [Judgment Layer](/features/judgment-layer/). |
| `withKillSwitch()`                   | Pause / resume / stop / terminate via `KillSwitchService`                                                                                                                                                                                                                                                                                                                                                    |
| `withBehavioralContracts(contract)`  | Rules such as `deniedTools`, `allowedTools`, `maxIterations`, etc.                                                                                                                                                                                                                                                                                                                                           |
| `withContract(contract)`             | Declare a `TaskContract`: `{ prompt, tools: ToolRequirement[], fixtures?, modelFloor?, success }`. Required tools become an execute-time gate; forbidden tools are excluded from the tool schema **and enforced at the shared tool-execution gate on every strategy** (plan-execute/blueprint planned steps and the `code-action` sandbox included) — a violating call is blocked and recorded, never executed. Validated at `build()`. The declared contract is now **load-bearing**: it is compiled into the run's typed goal, the terminal gate checks requirement satisfaction against the evidence ledger, and `result.receipt.deliverables[]` reports each declared output as produced or missing.                                                                            |
| `withVerification(options?)`         | Post-output checks — toggles and thresholds: `semanticEntropy`, `factDecomposition`, `multiSource`, `hallucinationDetection`, `passThreshold`, …. `onReject` sets what happens when the answer still fails after retries: `"proceed"` (default) ships it, `"block"` withholds it and fails the run, `"annotate"` ships it unchanged with the reason on `metadata.verificationNote`. |
| `withVerificationStep(config?)`      | Post-answer LLM self-review. `{ mode: "reflect" \| "loop", prompt? }`. Reflect mode runs one LLM review; on a **REVISE** verdict it re-runs the answer once with the verification feedback so the verdict shapes the final answer. Loop mode (V1.1) re-enters the ReAct loop.                                                                                                                                |
| `withOutputValidator(fn, opts?)`     | Validate output before accepting. `fn(output) => { valid, feedback? }`. Failed validation injects feedback and retries (`opts.maxRetries`, default 2)                                                                                                                                                                                                                                                        |
| `withCustomTermination(fn)`          | Re-run until `fn({ output }) === true`, up to 3 additional times. For domain-specific completion criteria                                                                                                                                                                                                                                                                                                    |
| `withJudgment(options?)`             | Opt-in calibrated typed judgment (Choice/Score/Noul) via `@reactive-agents/judgment`: `{ backend?: "jev" \| "llm" \| "ollama", apiKey?, baseUrl?, model?, timeoutMs?, ollama?: { keepAlive? }, sites? }`. Backend auto-selects `"jev"` when a TypeSafe key resolves (`apiKey` or `TYPESAFE_API_KEY`), else `"llm"` (emulation over the agent's own `LLMService`, no key required). `"ollama"` runs the System One decision API on a local Ollama server (`ollama pull nimble`; no API key, calibrated distributions); `ollama.keepAlive` (for example `"10m"`, or `0` to unload after each request) keeps the model warm between calls. Exposes `agent.judge({ state, questions, images? })` directly (`images` is base64-only and requires a vision model such as `clef`); several internal sites (strategy selection, complexity routing, guardrails battery, …) can also opt in per-site. Throws if a judgment call is made without this method having been called. `withJudgment({ shadow: true, model?, baseUrl? })` is the separate observation-only form: auto-shadow is off by default, and this (or `REACTIVE_AGENTS_AUTO_SHADOW=1`) makes `build()` probe a local Ollama and, if the model (default `nimble`) is installed, sample shadow judgments; `agent.judge()` stays unavailable and `backend` or `apiKey` cannot be combined with `shadow`. `withJudgment(false)` turns judgment off and refuses auto-shadow even when the env var is set (`REACTIVE_AGENTS_NO_AUTO_SHADOW=1` blocks it everywhere). See [Judgment Layer](/features/judgment-layer/). |
| `withGrounding(options)`             | Opt-in numeric evidence-grounding (off by default): `{ mode: "block" \| "warn", tolerance?, maxRetries? }`. Checks figures in the final answer against the full tool data with rounding tolerance. `warn` = advisory; `block` = one corrective retry then degrade to warn (never hard-fails). Scaffold-leak detection (`[STORED:]`/`_tool_result_N` echoed as the answer) is always-on, independent of this. |
| `withFabricationGuard(mode?)`        | Configure the always-on verifier check that rejects invented empirical performance measurements (benchmark timings, % speed-ups) absent from the tool-observation corpus. **On by default (`"block"`)** — no call needed for protection. Use this only to soften (`"warn"`, advisory) or disable (`"off"`). High-precision: only perf measurements are policed; counts, prices, and Big-O are ignored, and a claim grounded by a real benchmark/execution tool always passes. Also settable via `RA_FABRICATION_GUARD` env var (this method wins). `mode: "block" \| "warn" \| "off"`. |
| `withReceiptSigning(options)`        | Opt in to an **Ed25519 provenance signature** on every trust receipt (off by default — receipts are unsigned). `{ privateKeyJwk }`; also settable via the `RA_RECEIPT_KEY` env var (this option wins when both are present). The signature certifies *this receipt, this run, untampered* — it **never** certifies the answer's correctness. Generate a keypair with `generateReceiptKeyPair()` and verify with `verifyReceipt(result.receipt!)`. See [The Process Model](/features/process-model/). |
| `withOutputSchema(schema, options?)` | **Typed structured output.** Attach any Standard Schema (Zod / Valibot / ArkType) or Effect Schema; the result carries a typed `result.object` (or `result.objectError` on parse failure). Options: `{ mode?: "auto" \| "grounded", onParseFail?: "lenient" \| "throw" }`. Builder-only — set before `.build()`. See [Typed Structured Output](/guides/structured-output/).                                       |
| `withApprovalPolicy(policy)`         | Human-in-the-loop approval gate for `requiresApproval` tools. `{ tools?, commands?, requireFor?, mode?, onApprove? }`. `commands` gates shell calls by command: `["git push"]` asks before any `shell-execute` call whose command has a segment starting with those words (see [Shell command rules](/guides/durable-hitl/#shell-command-rules)); in the read-only `git` preset a matched write then runs instead of being refused. `mode`, `tools` and `commands` round-trip in `toConfig()` as `approvalPolicy`; `requireFor` and `onApprove` are code-only. `mode: "detach"` hands each gated call to a person: `agent.approveRun`/`denyRun`/`listPendingApprovals`. Without `.withDurableRuns()` the run **waits live, in process**, and continues in the same run once answered (`runStream()` emits `ApprovalRequested`); with `.withDurableRuns()` it pauses, persists `awaiting-approval`, and can be answered from any process, even after a restart — see [Human-in-the-loop](/guides/durable-hitl/). `mode: "block"` (the default when no `mode` is given and `.withDurableRuns()` is not set) decides each gated call **in process** via `onApprove: ({ toolName, args, iteration }) => boolean \| { approve, reason }` (sync or async) — **deny-by-default**: a gated call with no `onApprove` is refused, not executed. A sub-agent (`.withAgentTool()` / `.withDynamicSubAgents()`) always runs in block mode, inheriting the parent's policy. |
| `withDurableRuns(options?)`          | Persist run state so a crashed or paused run can resume from its last checkpoint. Exposes `agent.resumeRun(runId)` and `agent.listRuns({ status? })`. Config hash = system prompt + provider. `options`: `{ dir?, checkpointEvery?, retention? }`. `retention: { keepCompleted?, maxAgeDays?, compactCheckpoints? }` bounds store growth at the start of each run: completed runs keep only their final checkpoint, and completed runs beyond the newest `keepCompleted` (default 50) or older than `maxAgeDays` (default 30) are deleted (`0` = no limit; `compactCheckpoints: false` keeps every iteration for `agent.fork()`). Resumable runs are never pruned. See [Durable Execution](/guides/durable-execution/).                                                                                                                                                            |
| `withUserInteraction(opts?)`         | Enable **agent-initiated** user interaction (Agentic UI). The model may call `request_user_input` to ask the human for a form / choice / confirmation; `agent.respondToInteraction(...)` answers it. Without `.withDurableRuns()` the question waits live in process (the stream shows `InteractionRequested`) and the same run continues with the answer; `opts.timeoutMs` bounds that wait (unanswered: the model reads "The user did not answer"). With `.withDurableRuns()` the run pauses durably and the answer resumes it. Round-trips in `toConfig()` as `userInteraction: true` (or `{ timeoutMs }`). **Distinct from `withApprovalPolicy()`,** which gates *tool calls* the model already chose (human approves/denies) — `withUserInteraction()` lets the *agent* proactively request input. Zero cost when not called. |
