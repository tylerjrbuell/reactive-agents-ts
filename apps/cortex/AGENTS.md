# Cortex — Agent Guide

Instructions for AI agents and contributors working on **`@reactive-agents/cortex`** (Bun server + SvelteKit UI). For monorepo-wide Effect-TS rules, builder patterns, and release workflow, read the repo root **`AGENTS.md`**.

---

## What Cortex Is

A **local desk** for Reactive Agents: ingest agent events over WebSocket, persist to SQLite, fan out **live** messages to subscribers, and expose a **SvelteKit** UI that dogfoods **`@reactive-agents/svelte`**.

| Layer | Location | Stack |
|-------|-----------|--------|
| Server | `apps/cortex/server/` | Bun, Elysia, Effect-TS, `bun:sqlite` |
| UI | `apps/cortex/ui/` | SvelteKit 2, Svelte 5 (runes), Tailwind, Vite, D3 (run view) |

---

## Quick Start (Human or Agent)

From repo root: `bun install`.

From **`apps/cortex`**:

```bash
bun start
```

- **UI:** http://localhost:5173 — use this in dev (Vite proxies `/api` and `/ws` to the server).
- **API/WS (direct):** http://localhost:4321

| Script | Purpose |
|--------|---------|
| `bun start` | `scripts/dev-stack.ts` — server + UI together; sets `CORTEX_NO_OPEN=1` on the server child. |
| `bun run dev` / `dev:server` | Elysia + SQLite + routes + WS only. |
| `bun run dev:ui` | SvelteKit dev only (expects server on 4321). |
| `bun run build:ui` | Production UI build → `ui/build`. |
| `bun test` | Server tests under `server/tests/`. |

**Two ways to run cortex:**
- **From any project (npm):** `bun add @reactive-agents/cortex` then `rax cortex` — the CLI lazy-loads the package and starts the bundled server + UI.
- **From source repo (contributors):** `bun cortex` runs `scripts/dev-stack.ts` — server + Vite UI dev mode in parallel. Same as `bun start` from this folder.

Pair with `rax run "<prompt>" --cortex --provider …` so the agent uses `.withCortex()` against `CORTEX_URL` (default `http://127.0.0.1:4321`).

UI tests: `cd ui && bun test src/lib`. UI build: `cd ui && bun run build`.

User-facing overview: **`README.md`** in this folder.

## Environment

| Variable | Default | Notes |
|----------|---------|--------|
| `CORTEX_PORT` | `4321` | HTTP + WebSocket listen port. |
| `CORTEX_HOST` | `127.0.0.1` | Interface the server binds. Default is loopback only: Cortex has no authentication and its API lists directories and starts runs. Set `0.0.0.0` (or a LAN address) to expose it on purpose; the server logs a warning. `startCortexServer({ hostname })` overrides it. Resolver: `server/listen-host.ts`. |
| `CORTEX_URL` | — | Public base URL (HTTP) for display / agent `.withCortex()` alignment. |
| `CORTEX_NO_OPEN` | unset | `1` disables opening a browser when starting the server alone. |
| `CORTEX_LOG` | `info` | Server log verbosity: `error` \| `warn` \| `info` \| `debug` \| `off`. **`debug`** logs every persisted ingest event, empty bridge broadcasts, replay counts. The framework **`CortexReporter`** reads the same variable for connection / dropped-event warnings. |
| `CORTEX_SKILL_SCAN_ROOT` | — | Optional extra absolute path: a workspace-picker suggestion, and merged with `process.cwd()` and the Cortex app root by the older `GET /api/skills/files` scan (no UI reads it now; chat and Lab use framework discovery, section 9 below). |

DB file defaults to **`.cortex/cortex.db`** relative to the server process cwd (usually `apps/cortex`). See `server/types.ts` → `defaultCortexConfig`.

## Server Architecture (High Level)

1. **`server/index.ts`** — Wires routers, `/ws/ingest`, `/ws/live/:agentId`, optional static UI from `ui/build`.
2. **Ingest** — Agents POST events to **`/ws/ingest`**. `CortexIngestService` persists rows and **`CortexEventBridge.broadcast(agentId, liveMsg)`** — subscribers are keyed by **real `agentId`**, not run id.
3. **Live** — Clients connect to **`/ws/live/:agentId?runId=`**. `runId` triggers **replay** of stored events for that run on open (`ws/live.ts` + `replayRunEvents`).
4. **REST** — `GET /api/runs`, `GET /api/runs/:runId`, `GET /api/runs/:runId/events`, **`POST /api/runs`** (desk runner). Skills: `GET /api/skills/session/:sessionId` (what a chat's agent can load), `GET /api/skills/workspace?root=&paths=&global=1` and `GET /api/skills/workspace/file?…&path=` (Lab; framework discovery, section 9), `GET /api/skills/sqlite/:id` (Cortex library row), and the older Cortex-scan routes `GET /api/skills/files`, `GET /api/skills/file?path=` (no UI reads them). Workspace picker: `GET /api/workspace/check?path=` (absolute existing dir → normalised path, else 400), `GET /api/workspace/recent`, `GET /api/workspace/candidates` (ranked suggestions: launch dir's git root, launch dir = server cwd, `CORTEX_SKILL_SCAN_ROOT`, recent; plus `home`), `GET /api/workspace/browse?path=&hidden=1` (subdirectory names + `isGitRepo` only, home by default, 400 on relative/missing paths, capped at 500 entries). Built-in toolset shortcuts: `GET /api/tools/toolsets`; shell toolsets → the programs they run: `GET /api/tools/shell-presets`; shell allowlist sources (defaults, opt-in, groups): `GET /api/tools/shell-commands`. Routers under `server/api/`.
5. **Workspace** — `workspace` (absolute existing dir) on a chat session / run / saved agent maps to `.withTools({ workspace })`: file tools confine to it and `shell-execute` runs in it. Chat create/PATCH and `POST /api/runs` refuse a bad path with 400 (`services/workspace-dir.ts`); chat sessions forward it, the shell options and `terminalTools` only when tools are on (a tools-off chat never gets `shell-execute`). Shell options ride in `terminalShellOptions` (`cwd`, `allowUnsafeCwd`, `timeoutMs`, `maxOutputChars`, `commandAccess`, `sandbox`). The builder edits the shell allowlist as **one list** (`ShellCommandsField.svelte`): the exact commands the agent gets as removable chips, framework defaults pre-filled from `GET /api/tools/shell-commands` (framework `DEFAULT_ALLOWED_COMMANDS`, `OPT_IN_COMMANDS`, and the commands behind each `commandAccess` group; never copied into the UI), an add input, and quick-add buttons for the opt-in groups (no `github`: the `git` toolset brings `gh`). `ui/src/lib/shell-allowlist.ts` folds stored `terminalShellAllowedCommands` + `terminalShellAdditionalCommands` + legacy `commandAccess` into that list and writes edits back as extras beyond the defaults → `terminalShellAdditionalCommands`, or, once a default is removed, the full list → `terminalShellAllowedCommands`; it never sets `commandAccess` (cleared on the first edit; an unedited legacy config still sends it, so no command is lost). The group → commands map is the framework's `COMMAND_CAPABILITY_MAP` (`@reactive-agents/tools`), served as is; Cortex keeps no copy (`server/tests/shell-commands-catalog.test.ts`).
6. **Tool disclosure + toolsets** — `.withTools({ disclosure, builtins })` are AgentConfig paths, so they ride `rawConfig.tools` (builder Tools section `ToolDisclosureField.svelte` and chat `/tools` "Show tools" rows, both via `disclosurePatch` in `ui/src/lib/chat-quickbar.ts`; `builtins` via the Lab generic renderer). The Tools quick picks list `kind: "built-in"` catalog rows plus the shell toolsets (`shellPresetPicks`); meta-tools are configured in Meta tools. A shell toolset (`git` = `git`/`gh`; framework `BUILTIN_SHELL_PRESETS`, served by `GET /api/tools/shell-presets`, never hard-coded in the UI) is selected by its own name in `tools`, never as `shell-execute`: the framework resolves the name to a `shell-execute` limited to those programs, while `shell-execute` in `tools` means the full host shell (`shellExecuteRequested`). Chat `/tools` rows follow the same rule (`toolsetChoice` in `ui/src/lib/chat-quickbar.ts`). The shell has three states (`ui/src/lib/shell-from-picks.ts`): off, toolset-only (a toolset picked, `terminalTools` off: `shell-execute` limited to its programs) and full (`terminalTools` on). While a toolset is picked the builder's host-shell checkbox never shows unchecked but stays clickable: a click flips the user's own `terminalTools` (git · gh only, full shell), and a hint says which. The chat shell chip and the `/terminal` off row read `Shell: git · gh only` in that state. Unpicking the toolset shows the user's own value again. Stored configs naming the removed `gh-cli` / `git-cli` tools are rewritten to `git` on read and at build; `gws-cli` and a stored `workspace` pick (the gws toolset the framework removed) are dropped with a server warning and never turn on the shell (`server/services/legacy-cli-tools.ts`, pinned by `server/tests/legacy-cli-tools.test.ts`). `tools.builtins` suggestions come from `GET /api/tools/toolsets`. The run view pill reads `AgentStarted.config.disclosure` (`{ mode, source }`). Pinned by `server/tests/tool-disclosure-parity.test.ts`.

7. **Provider API keys** — `/api/settings/keys` (`api/provider-keys.ts`): `GET /` (masked status per provider, never a key), `PUT /:provider` `{ apiKey }`, `PATCH /:provider` `{ preferStored }`, `DELETE /:provider`, `POST /:provider/test` `{ apiKey? }` (framework `listProviderModels` with that key; failures go through `redactKey`). Store: `services/provider-key-store.ts`, AES-256-GCM (`node:crypto`, provider id as AAD) with a random 32-byte `secret.key` and `provider-keys.json` beside the DB (`.cortex/`), both mode 0600, atomic writes. An env key wins unless the user turns on "use the saved key" (`preferStored`). `buildCortexAgent` is the one funnel: `providerKeyForAgent` → `.withProvider(provider, { apiKey })`; `process.env` is never written. The model list and `keyConfigured` / `/api/health/providers` count a saved key. Every keyed provider's framework adapter honours the passed key (llm-provider `d1955526c`, anthropic and gemini included), so `storedKeyAppliesToAgents` is true for all of them; a new keyed provider whose adapter ignores a passed key must stay out of its set. No-key help (Model page, model picker note) points to Settings · Providers as well as the env variable. Pinned by `server/tests/provider-keys.test.ts`, UI `provider-keys.test.ts`.

8. **Output speed (tok/s, TTFT)** — one formula: core `outputTokensPerSecond` = `tokensOut / ((durationMs - firstTokenMs) / 1000)`; ui-core `throughputOf` / `throughputOfCalls` carry the same math for the browser (pinned equal in `server/tests/model-throughput.test.ts`). A call without `firstTokenMs` gives a lower bound, shown `~`. Chat (`ChatTokenUsage.svelte`, `turnSpeedOf` in `lib/chat-token-usage.ts`): a live `~tok/s` estimate while text streams (`liveRate`, ui-core `liveTokensPerSecond` over `estimateTokens` since the call's first delta), then the measured speed + TTFT over `usage.calls` (persisted with the turn trace). Run view: per-loop speed on trace rows (`CortexTraceFrame.throughput`), run average in `RunVitals` (`RunVitals.llmCalls`); both read stored `LLMRequestCompleted`. Model page: `GET /api/model-throughput?provider=&model=&runs=` (`api/model-throughput.ts`, `services/model-throughput.ts`) gives medians; exact and lower-bound rates are never mixed (a lower-bound median only when no call measured TTFT, marked). Wording: `lib/llm-throughput.ts`. The runtime `TokenUsage` stream event does not forward `firstTokenMs` yet, so a chat turn's settled speed reads `~` (lower bound) until it does; the run view and Model page already read the exact value.

9. **Workspace skills** — Cortex lists skills with the framework's own discovery (`discoverSkills` / `skillScanPaths`, `server/services/workspace-skills.ts`) at the root a run uses: the session or Builder `workspace`, else the server cwd; scan order `<root>/.<agentId>/skills`, `<root>/.agents/skills`, configured `paths`, `<root>/.claude/skills`, then `~/.agents/skills` and `~/.reactive-agents/skills` only with `global`. Cortex keeps no copy of that order. Every chat agent gets `.withSkills()` (`migrateChatSkillsConfig` always returns a config; desk runs and saved agents only when they set paths, pins or `global`: `parseCortexSkillsConfig`). Pins are skill **names** (`skills.activate`); `toggleSkillPatch` and the agent's `pin-skill` proposal never write a scan root. Older chat pins stored a cwd-relative root in `paths`: `migrateChatSkillsConfig` rewrites it to an absolute dir (workspace first, then server cwd) and drops roots discovery already scans. A skill for one message is its `/name` token in the composer text: recognized skill tokens anywhere in a message (bare `/<skill>`, `/skill <skill>`, or `/skills <skill>` to pin) are highlighted (mirror layer behind the textarea in `ChatComposer.svelte`), activated on send and stripped from the prompt; turn skills are sent as `skills` on `POST /chat/sessions/:id/chat/stream`. Token grammar (boundary after start/whitespace/`(`, name `[A-Za-z0-9][A-Za-z0-9_-]*`, only closing punctuation after it, never in code spans, `\/name` escapes) and the inline `/` menu at the caret: `ui/src/lib/chat-inline-commands.ts`; send routing (a leading real command still owns the whole message) and skill picks: `ui/src/lib/chat-composer-input.ts` (`routeComposerInput`, `pickSkill`). Picks from the `/` menu, `/skill` picker or skills chip insert the token at the caret (the chip's stashed draft and caret are kept); `/skills <name>` from the picker still toggles a session pin. Pinned by `chat-inline-commands.test.ts`, `chat-composer-input.test.ts`, `chat-menu-items.test.ts` (`inlineMenuItems`). The pins ride the turn as `session.runStream(msg, { skills: { activate } })` / `session.chat(msg, { skills })` (`turnSkillsOption`); the cached session agent is kept and the session config is never written. What a run had active: `server/services/chat-turn-skills.ts` `recordSkillActivity` keeps each run's `AgentStarted.config.skills` and `SkillActivated` events (an event without `taskId`, as the kernel's `activate-skill` publishes today, counts for the session's current run) and stores ui-core `foldRunSkills` on the turn as `trace.skills`; the chat turn and the run view render it with `SkillActivationRow.svelte` (`lib/skill-row.ts`: `pinned`, `matched the task`, `loaded by the agent`). Lab Skills has two views (`LabSkillsUi.view`): **Agent skills** (section 11) and **Skill files**, the workspace skills for the Builder's scope (`lib/stores/lab-skills-store.ts` `skillScopeOf`) plus the Cortex library rows (cortex.db, **deprecated**, not sent to agents; each row has "Move into agent skills"). Pinned by `server/tests/workspace-skills.test.ts`, `chat-turn-skills.test.ts`, UI `skill-row.test.ts`, `chat-menu-items.test.ts`, `lab-skills-store.test.ts`, ui-core `skill-activations.test.ts`.

10. **Memory studio** — every memory read and write goes through the framework's `agent.memory()` facade; Cortex never opens a `memory.db`. `server/services/memory-inspector.ts` (`MemoryInspector`, one per server, `disposeAll` on stop) builds one small `test`-provider agent per inspected agent id with `.withAgentId(id).withMemory({ dbPath })`, where `dbPath` is the framework's own `defaultUserMemoryPath(id)` (`$HOME/.reactive-agents/memory/<id>/memory.db`, the path a bare `.withMemory()` uses; passed explicitly because a `test` build would otherwise use `:memory:`). An id whose database does not exist is reported `available: false` and never built, so looking never creates a database; ids with a path separator or `..` are refused. Routes (`server/api/memory.ts`): `GET /api/memory/agents` (ids with a database under the memory root, labelled by saved agent, chat session or latest run name: `db/memory-agent-queries.ts`), `GET /api/memory/:agentId?runId=` (semantic, procedural, episodic; `runId` narrows to what that run wrote: semantic and procedural through the facade's `list({ runId })` (filtered in the store query, before the limit), episodic rows by `taskId` = the run id or a task id the run's entries carry (`listingForRun`; the episodic list has no run filter, so that part still applies after its 200-row limit)), `GET /api/memory/:agentId/search?q=&runId=` (framework FTS5; words of 2+ characters, common stop words dropped), `PATCH|DELETE /api/memory/:agentId/semantic/:id`, `PATCH|DELETE /api/memory/:agentId/procedural/:id` (404 for an unknown agent or id). UI: Lab tab `components/memory/MemoryStudio.svelte` (agent picker, search, layer tabs Facts / Workflows / Log, entry, provenance link to `/run/<runId>`, edit form, delete through kit `Overlay`); rules and client in `lib/memory-studio.ts` (`semanticPatchOf` / `proceduralPatchOf` send changed fields only, `provenanceOf`, `memoryStudioHref`). The run view's Memory tab (`MemoryPanel.svelte`) lists what the run wrote from the same route. Agents with a custom `memory.dbPath` are not found (the inspector only knows the default path). Pinned by `server/tests/memory-studio.test.ts`, UI `memory-studio.test.ts`, `lab-tabs.test.ts`.

11. **Living skills** — an agent's stored skills (the framework SkillStore in its memory database) in Lab Skills · Agent skills (`components/skills/AgentSkillsPanel.svelte`, rules and client in `lib/agent-skills.ts`; version diff, confidence words and lifecycle entries from ui-core `skillLineDiff` / `skillConfidenceLabel` / `skillLifecycleEntryOf`). Server `services/agent-skills.ts` (`AgentSkillsService`) goes through the framework only: list = `agent.skills()` on the Memory studio's inspector agent (`MemoryInspector.withAgent`, so the same agent ids and "no database = unavailable" rule); Refine now = `agent.refineSkills()` on an agent built with the agent's last recorded provider/model (`lastRunModelOf`, cortex_runs) over the same database; Export = `agent.exportSkill(name, <Builder workspace>/.agents/skills/<name>)`; Move from the library = `agent.loadSkill(dir, { evolutionMode })` of a temp SKILL.md (front matter single-quoted; the dialog `components/skills/MoveLibrarySkillDialog.svelte` picks the mode, `auto` first; no mode = the framework default, `locked` for a new skill). A name the agent already has is 409 unless the body has `update: true`: then the row reloads over that skill, and the framework keeps its id, stats and history and adds a version when the text changed (the dialog offers **Update existing** on the 409). The library row is deleted after a move. Roll back = `agent.rollbackSkill(name)`; Lock / Unlock = `agent.setSkillMode(name, "locked" | "auto")` (history untouched; `lockActionOf` in `lib/agent-skills.ts`). Manual Refine now and Roll back publish `SkillRefined` / `SkillRolledBack` (`reason: "manual"`) on the acting agent's bus with no run; `AgentSkillsService` subscribes for the call and hands them to its `SkillEventSink`, which `server/index.ts` wires to `recordSkillControlEvents` (cortex.db, `run_id` `""`, source `cortex-skill-control`, so run retention never drops them); the timeline shows them "in Cortex" (`timelineOriginOf`). Routes (`server/api/agent-skills.ts`): `GET /api/agent-skills/:agentId` (skills + `refineWith`), `GET /api/agent-skills/:agentId/events?skill=` (stored `SkillActivated` / `SkillRefined` / `SkillRolledBack` / `SkillPromoted`, newest first, `runId` = the event's `taskId` when Cortex has that run, `""` for a Cortex action: `db/skill-lifecycle-queries.ts`), `POST …/refine` `{ provider?, model? }`, `POST …/skills/:name/rollback`, `POST …/skills/:name/mode` `{ mode }`, `POST …/skills/:name/export` `{ root }`, `POST …/library/:libraryId` `{ evolutionMode?, update? }`. Pinned by `server/tests/agent-skills.test.ts`, UI `agent-skills.test.ts`, ui-core `skill-evolution.test.ts`.

12. **Live questions, structured results, field editor, searchable pickers** — (a) **Live ask**: `request_user_input` without durable runs waits in process (runtime `e4877472f`). The AgentConfig path `userInteraction` rides `rawConfig` (Lab Execution · "Ask me questions": default / yes / no, `lib/user-interaction.ts`); a durable build sets it itself unless `rawConfig` does. A chat defaults it ON (`chat-session-service.ts`, comment there; a chat with tools off has no tool layer and cannot ask). `durable-approvals.ts` `askWaitsLive` / `waitsLive` decide when a running agent registers as a live source (`watchLive`); `listLiveInteractions` / `answerLiveInteraction` list and answer its questions, and the runner's `listPendingInteractions` / `respondToInteraction` (so `GET /api/runs/pending-interactions` and `POST /api/runs/:runId/interaction`) fall back to them with `chatSessionId`/`agentId` on live rows. The chat turn shows the question inline from the stream's `InteractionRequested` (`ChatLiveInteraction.svelte`, rules `lib/chat-live-interaction.ts`; replies are `InteractionReply.svelte`, shared with the held-turn card); after a reload `orphanChatInteractions` shows it from the polled list. Framework gap: the event carries no `timeoutMs`, so the wait is not shown. Pinned by `server/tests/live-ask.test.ts`, UI `chat-live-interaction.test.ts`, `user-interaction.test.ts`. (b) **Structured output**: the output schema maps in `cortexParamsToAgentConfig` (`outputSchema`, `outputSchemaOptions.onParseFail` when `throw`); the old Cortex `withOutputSchema` overlay and `json-schema-output.ts` are gone, and the framework's validator refuses an unsupported schema keyword at build. Result view: `StructuredResult.svelte` (field table, Raw JSON, "How output was obtained") over ui-core `fieldRowsOf` / `obtainedOf`; fed by `StreamCompleted.object/objectError/objectReport` and `StructuredOutputReported` through ui-core `foldTurnTrace` (`TurnTrace.structured`, persisted with the chat turn) and the run store (`structuredReport`, from the framework event or the runner's `StructuredOutputExtracted.objectReport`). Pinned by ui-core `structured-output.test.ts`, `server/tests/structured-output-config.test.ts`. (c) **Field editor**: `agent-config/FieldEditor.svelte` (name, type, description, required) edits Variables (names locked, detected) and the Output schema section (`OutputSchemaSection.svelte`, `lib/field-editor.ts`, ui-core `fieldsToJsonSchema` / `jsonSchemaToFields`; a schema the editor cannot express opens as JSON only). Sub-agent inputs (`agent.parameters`, runtime) will reuse it: hook documented in `field-editor.ts`, no UI yet. (d) **Searchable pickers**: the kit `Combobox.svelte` (rules `lib/combobox.ts`: ranked match, groups, cap of 40 rows with a "N more" line, keyboard wrap) replaces the native agent select on Lab Memory and Skills; agents list recent first, Named before Unnamed, never a raw id as the label. Loads are cancelled when a newer one starts (`AbortSignal` on the fetchers) and Skills loads an agent only once picked. The prompt-library popover lists every saved prompt (`lib/prompt-picker.ts`): a field's `types` only put its own kinds first.

13. **Composer bar, `/mcp`, `/btw`, Context sources** — (a) **Bar**: `ChatQuickBar.svelte` shows the model chip plus only settings that differ from the defaults (`composerBar` / `chipOnBar` in `ui/src/lib/chat-composer-bar.ts`: strategy ≠ `reactive`, steps ≠ 16, a thinking choice, and every chip with `on`), capped at `MAX_BAR_CHIPS` (4), and a **Config** popover (`configGroups`: Model, Reasoning, Tools, Workspace, Limits). A row hands its slash command to the composer exactly as a chip does (`pickChip`), so no picker was duplicated. Chip text still comes from `quickBarChips` (unchanged). `disclosureSummary` words the tool disclosure in force (`rawConfig.tools.disclosure`, else "tier default"), shared by the popover and `ToolDisclosureField` (Tools section; a closed section shows a Disclosure badge when set). The number of tools the framework actually shows is not known to Cortex, so the line counts picked tools only. (b) **`/mcp`**: picker `mcp` in `chat-menu-items.ts` (`mcpRows`: the `/tools` server toggle, `toggleMcpServerPatch`, plus `add <command|URL>`); `lib/mcp-quick-add.ts` `parseMcpQuickAdd` → body for `POST /api/mcp-servers` (the server infers the transport) → `addMcpServer` (save + `refresh-tools`) → `quickAddMcpToChat` (turns it on only when discovery listed tools). Lab Tools has the same one line (`tools/McpQuickAdd.svelte`, in `ToolWorkshop` head); the palette's "Add an MCP server" opens Lab Tools. (c) **`/btw <question>`**: `POST /api/chat/sessions/:id/btw` (`api/chat.ts`, `services/chat-btw.ts` `ChatBtwService`, wired in `server/index.ts`). The browser snapshots the latest exchange (`lib/chat-btw.ts` `btwContextOf`: task, tool calls with args/results, draft; `redactSecrets` applied); the server answers with a tool-less one-shot agent (`UTILITY_AGENT_PARAMS`, **memory explicitly off**: Cortex's default memory would otherwise recall into and write from the observer) on the session's provider/model. It never touches the session, its cached agent, history or totals, so it works mid-run (`btw` and `mcp` are in `LIVE_CONFIG_COMMANDS`, never queued). With no client context it uses the last stored exchange. Asides live in `stores/chat-btw.ts` (per chat, in memory only) and render via `chat/ChatBtwAsides.svelte` at the end of the thread. Pinned by `server/tests/chat-btw.test.ts`, `utility-agent-lightweight.test.ts`, UI `chat-composer-bar.test.ts`, `mcp-quick-add.test.ts`, `chat-btw.test.ts`, `stores/chat-btw.test.ts`, `chat-menu-items.test.ts`. (d) **Context sources**: the run inspector's Context tab (above the gauge) and the chat inspector's Context tab render `ContextSources.svelte` (rules `lib/context-sources.ts`): skills active (`foldRunSkills`, why/version, link to Lab Skills) and memories the run wrote (`GET /api/memory/:agentId?runId=`; a chat uses `ChatSession.stableAgentId` and the turn's `runId`). **Framework gap:** no memory-recalled event exists (`MemoryBootstrapped` / `MemoryFlushed` carry a tier and an agent id only), so the tab states that recalled memory is not reported (`RECALL_NOT_REPORTED`) rather than faking a list. Pinned by `context-sources.test.ts`.

14. **Judgment (Lab · Judgment, Run view · Judgments)** — (a) **Config**: `judgment` (`{ enabled: true, backend?: jev|ollama|llm, model?, timeoutMs?, baseUrl?, keepAlive? }`, stored only while on) is **not** an AgentConfig field (runtime `AgentConfigSchema` has no `judgment`: framework gap), so `.withJudgment()` is an overlay in `cortexAgentBuilder` (`CORTEX_OVERLAY_CALLS` has `withJudgment`; the exported-code note lists it). Hops: Lab section `JudgmentSection.svelte` (`lib/judgment-config.ts`) → `cortex-runs-post-body.ts` → `agent-config-body.ts` → `runs.ts` / `chat.ts` / `gateway-process-manager.ts` / `chat-session-service.ts` → `BuildCortexAgentParams.judgment` → `server/services/cortex-judgment.ts` (`parseCortexJudgmentConfig`, `judgmentBuilderOptionsOf`). Backend with no choice follows the framework's presence rule (jev with a TypeSafe key, else `llm`, uncalibrated); the section says which is active. Pinned by `server/tests/ollama-cloud.test.ts`, UI `ollama-endpoint.test.ts`, `run-error.test.ts`, `provider-keys.test.ts`.

Canonical live payload shape: **`CortexLiveMessage`** in `server/types.ts` (`v`, `ts`, `agentId`, `runId`, `source`, `type`, `payload`). Event `type` is the AgentEvent `_tag` string; `payload` is the event object as JSON.

## WebSocket Paths (Critical)

| Path | Role |
|------|------|
| `/ws/ingest` | Agent → server; JSON `CortexIngestMessage`. |
| `/ws/live/:agentId?runId=` | UI (or tools) → server; **`agentId` must match the agent that receives broadcasts** (same string used in `broadcast(agentId, …)`). |

**Gotcha — Stage grid:** `+layout.svelte` historically used a path like **`/ws/live/cortex-broadcast`**. The bridge **only** fans out to subscribers registered under each message’s **`agentId`**. Until Stage subscribes using the **same `agentId`** as ingest (or the server adds a separate fan-out channel), the desk grid may not show live events. **Run detail** is correct: `run-store.ts` loads `GET /api/runs/:runId`, then connects to **`/ws/live/${encodeURIComponent(agentId)}?runId=…`**.

## Pitfalls (Cortex-Specific)

0. **Rebuild packages before testing Cortex.** Cortex imports `@reactive-agents/*` from `dist/` (compiled output), not `src/`. If you modify framework packages without running `bun run build:packages` (or `bun run build`) from the repo root, Cortex will execute stale code. Always rebuild after package changes: `bun run build:packages && cd apps/cortex && bun start`.
1. **Live WS `agentId` in the URL must match broadcast keys** — derived from ingest `agentId`, not arbitrary labels.
2. **Do not double-load run history** — Run view relies on **WS replay** after connect; avoid also replaying the full event list from REST in the same client unless you dedupe.
3. **`POST /api/runs`** is still **501** by design — UI must handle gracefully (`stage-store` already does).
4. **Pause/stop** routes may be missing — `run-store` `pause`/`stop` fail quietly.
5. **Debrief in REST** — Run summary exposes `hasDebrief`; full debrief object typically arrives via **`DebriefCompleted`** on the live stream.
6. **Approval policy** — the gate is the framework's top-level `approvalPolicy` (`mode`, `tools`, `commands`: shell command rules such as `git push`), carried as is through the run body, chat config and saved agents, and sent to the framework through the AgentConfig (`cortexParamsToAgentConfig`). `server/services/approval-policy.ts` `approvalPolicyOf` is the one reader on all three build paths; it also reads the legacy `durableRuns.approvalTools` / `approvalMode` / `durableRuns.approvalPolicy` shapes (only while durable runs are on) and drops a policy that gates nothing (any policy makes the framework also gate its `requiresApproval` tools, served by `GET /api/tools/approval-required`). A `detach` policy does NOT turn durable runs on (`isDurableBuild` = durable runs on, nothing else; runtime `078365780`): without them the run waits LIVE in process (runtime HumanGate). A tools-off chat gets no policy.
   **Live approvals (no durable runs)** — `approvalsWaitLive(params)` in `services/durable-approvals.ts`. Every path that runs such an agent registers it with `durableApprovals.watchLive({ agentId, agent, chatSessionId? })` while it runs (runner `start`, gateway run, chat session agent at build; unregistered when the run ends / the session agent is disposed). `listPending()` adds each source's `agent.listPendingApprovals()` rows (live waits only: no store) to `GET /api/runs/pending-approvals`; `decide()` of a runId not registered as durable goes to `decideLive`, which calls `approveRun` / `denyRun` on the source holding the wait without awaiting the run's end (its own caller reports it). So the toast, Runs strip, Beacon and the run view header work unchanged. Chat: the stream's `ApprovalRequested` sets `ChatTurn.liveApproval` (`ui/src/lib/chat-live-approval.ts`, cleared when the run moves on) and `ChatLiveApproval.svelte` renders Approve / Deny in the streaming turn (posting to `/api/runs/:runId/approve|deny`); nothing is held in `chat_pending_approvals`. The Lab no longer switches durable runs on when a gate is set (`ApprovalPolicyFields.svelte`). A live wait in chat ends when the chat's SSE stream drops (page closed or reloaded: the turn is interrupted as a disconnect). Pinned by `server/tests/live-approvals.test.ts` (registry, chat approve / deny, desk runner approve), UI `chat-live-approval.test.ts`.
   **One approval surface at a time** — `ui/src/lib/approval-surface.ts` `showToast(approval, view)`: the app-wide toast (`stores/approval-watcher.ts`) shows only when the approval is not on screen. `view` is set by the chat page (`{ kind: "chat", sessionId }`) and `RunDetail` (`{ kind: "run", runId, agentId, chatSessionId }`) through `setApprovalView` (release-guarded, so an unmount after the next page mounted does not reset it); the run-view match is `waitingRunsOf`, the header's own rule. The watcher reconciles toasts on every poll and view change, so opening the chat or run removes its toast. Answering from any surface calls `clearApproval(runId)` (store + toast at once). **Dismiss** on a chat card (durable `ChatApprovalCards`, live `ChatLiveApproval`) only hides the card for this browser session (`hiddenApprovalCards` in `chat-live-approval.ts`); the UI no longer calls the server `…/approvals/:runId/dismiss` route. Pinned by UI `approval-surface.test.ts`, `chat-live-approval.test.ts`. Cortex supplies no `onApprove`, so `block` refuses every gated call; the UI says so. UI: `lib/approval-policy.ts` (rules, `autoGatedTools`, `approvalPatch`), `agent-config/ApprovalPolicyFields.svelte` (Tools section), chat `/approvals` rows in `chat-menu-items.ts`. The run view header shows Approve / Deny while the run waits (`runApprovalOf` in `waiting-on-you.ts`; the endpoints take the approval's durable run id). Pinned by `server/tests/approval-policy.test.ts`, `config-parity`, `build-path-parity`, `chat-builder-controls`, UI `approval-policy.test.ts`, `chat-menu-items.test.ts`.
   **Tool call arguments while running** — core puts post-heal `args` on the bus `ToolCallStarted`; ui-core `ToolCallStarted.args` and the `foldTurnTrace` running call carry them.    **Durable approvals in chat** — a streamed chat turn with `durableRuns` + an approval-gated tool pauses (`StreamCompleted.pendingApproval`). `services/chat-approvals.ts` holds it as a `chat_pending_approvals` row (the user message waits there, not in `cortex_chat_turns`) and registers it in `durable-approvals` as an owner-managed entry: listed by `GET /api/runs/pending-approvals` (with `chatSessionId`) and `GET /api/chat/sessions/:id/approvals`, resolved by `POST /api/chat/sessions/:id/approvals/:runId/approve|deny|dismiss` or the desk `/api/runs/:runId/approve|deny`. The UI keeps the message too when nothing streamed (`failTurn` in `chat-stream.ts`). Stop calls `POST /api/chat/sessions/:id/chat/stop` (`stopTurn`, `services/chat-turn-stop.ts`), which aborts the run server-side, then drops the stream; a stream that only drops (page closed, navigated off) reads as a disconnect. Both store `trace.outcome { ending: "interrupted", interruptedBy: "user" | "disconnect", error }` with the partial text (`interruptedOutcome`; cause lines are ui-core `interruptionCause`), `StreamCancelled.reason` carries who, and history tells the model the reply was cut off. The runtime publishes no terminal bus event for an aborted stream, so `chat-ingest.ts` tracks the runs a turn started and `closeOpenRuns` ends them through ingest: `ExecutionCancelled` → run status `stopped`, `TaskFailed` → `failed`; a stopped run that then reports a failure stays `stopped`. The desk Stop and Terminate publish `AgentStopped` / `AgentTerminated` (then a failed `AgentCompleted`): ingest, `recomputeRunStats`, `run-live-status.ts` and the run view's `deriveStatus` all read them as `stopped` (pinned by `server/tests/ingest-service.test.ts`, UI `run-live-status.test.ts`, `stores/run-store-status.test.ts`). In `runner-service.ts`, Terminate lets `agent.run()` settle before disposing the agent (disposing first failed the run with "ManagedRuntime disposed" and lost its `AgentTerminated`), and Stop ends the run like Terminate when it has not stopped within `stopGraceMs` (5s): `agent.stop()` is honoured only at an execution-engine phase boundary, and the reasoning loop is one phase. A run that ends without its own stop event gets one ingested by Cortex (`endAsStopped`). Pinned by `server/tests/runner-service.test.ts`. Runs store how a finished run ended on `cortex_runs.ending` (ui-core `turnOutcomeOf` over `AgentCompleted`, `server/services/run-ending.ts`; written by ingest and `recomputeRunStats`, backfilled once by `backfillRunEndings` when the column is added); Runs and Beacon read it through `runRowStatus` (`lib/runs-table.ts`, the run header's `runHeaderStatus` rule), so an abstained or partial run reads Abstained / Partial (attention), not Failed; live rows classify `AgentCompleted` the same way. Pinned by `server/tests/run-ending.test.ts`, UI `runs-table.test.ts`, `beacon-board.test.ts`. A durable run paused at an approval gate or a question publishes no terminal event (its stored status stays `live`); Runs, the run view and Beacon show it as **Waiting on you** through one resolver, `waitingRunsOf` / `waitingStatusOf` in `ui/src/lib/waiting-on-you.ts`, fed by the app-wide `pendingApprovals` / `pendingInteractions` stores. At boot `closeOrphanedChatRuns` (`db/queries.ts`) closes chat runs a restart left `live`, except sessions holding a paused turn. The live Trace list follows the same rules (`ui/src/lib/run-live-status.ts`). While a turn waits on the model (request out, no token back; ui-core `foldModelWait`, from the send and after the last running tool finishes) the turn has `awaitingModelSince` and `ChatModelWait.svelte` shows `modelWaitLabel` (`Waiting for Ollama (loading the model or queued)` for Ollama) with the elapsed time. Status ticks and run rows paint ui-core `statusOfTurn` / `statusOfRun` tones. Pinned by `server/tests/chat-turn-endings.test.ts`, UI `stores/chat-stream.endings.test.ts`, `stores/chat-store.test.ts`, `run-live-status.test.ts`, ui-core `chat-states.test.ts`.
