# Cortex — Agent Guide

Instructions for AI agents and contributors working on **`@reactive-agents/cortex`** (Bun server + SvelteKit UI). For monorepo-wide Effect-TS rules, builder patterns, and release workflow, read the repo root **`AGENTS.md`**.

---

## What Cortex Is

A **local desk** for Reactive Agents: ingest agent events over WebSocket, persist to SQLite, fan out **live** messages to subscribers, and expose a **SvelteKit** UI that dogfoods **`@reactive-agents/svelte`**.

| Layer | Location | Stack |
|-------|-----------|--------|
| Server | `apps/cortex/server/` | Bun, Elysia, Effect-TS, `bun:sqlite` |
| UI | `apps/cortex/ui/` | SvelteKit 2, Svelte 5 (runes), Tailwind, Vite, D3 (run view) |

---

## Quick Start (Human or Agent)

From repo root: `bun install`.

From **`apps/cortex`**:

```bash
bun start
```

- **UI:** http://localhost:5173 — use this in dev (Vite proxies `/api` and `/ws` to the server).
- **API/WS (direct):** http://localhost:4321

| Script | Purpose |
|--------|---------|
| `bun start` | `scripts/dev-stack.ts` — server + UI together; sets `CORTEX_NO_OPEN=1` on the server child. |
| `bun run dev` / `dev:server` | Elysia + SQLite + routes + WS only. |
| `bun run dev:ui` | SvelteKit dev only (expects server on 4321). |
| `bun run build:ui` | Production UI build → `ui/build`. |
| `bun test` | Server tests under `server/tests/`. |

**Two ways to run cortex:**
- **From any project (npm):** `bun add @reactive-agents/cortex` then `rax cortex` — the CLI lazy-loads the package and starts the bundled server + UI.
- **From source repo (contributors):** `bun cortex` runs `scripts/dev-stack.ts` — server + Vite UI dev mode in parallel. Same as `bun start` from this folder.

Pair with `rax run "<prompt>" --cortex --provider …` so the agent uses `.withCortex()` against `CORTEX_URL` (default `http://127.0.0.1:4321`).

UI tests: `cd ui && bun test src/lib`. UI build: `cd ui && bun run build`.

User-facing overview: **`README.md`** in this folder.

## Environment

| Variable | Default | Notes |
|----------|---------|--------|
| `CORTEX_PORT` | `4321` | HTTP + WebSocket listen port. |
| `CORTEX_HOST` | `127.0.0.1` | Interface the server binds. Default is loopback only: Cortex has no authentication and its API lists directories and starts runs. Set `0.0.0.0` (or a LAN address) to expose it on purpose; the server logs a warning. `startCortexServer({ hostname })` overrides it. Resolver: `server/listen-host.ts`. |
| `CORTEX_URL` | — | Public base URL (HTTP) for display / agent `.withCortex()` alignment. |
| `CORTEX_NO_OPEN` | unset | `1` disables opening a browser when starting the server alone. |
| `CORTEX_LOG` | `info` | Server log verbosity: `error` \| `warn` \| `info` \| `debug` \| `off`. **`debug`** logs every persisted ingest event, empty bridge broadcasts, replay counts. The framework **`CortexReporter`** reads the same variable for connection / dropped-event warnings. |
| `CORTEX_SKILL_SCAN_ROOT` | — | Optional extra absolute path: a workspace-picker suggestion, and merged with `process.cwd()` and the Cortex app root by the older `GET /api/skills/files` scan (no UI reads it now; chat and Lab use framework discovery, section 9 below). |

DB file defaults to **`.cortex/cortex.db`** relative to the server process cwd (usually `apps/cortex`). See `server/types.ts` → `defaultCortexConfig`.

## Server Architecture (High Level)

1. **`server/index.ts`** — Wires routers, `/ws/ingest`, `/ws/live/:agentId`, optional static UI from `ui/build`.
2. **Ingest** — Agents POST events to **`/ws/ingest`**. `CortexIngestService` persists rows and **`CortexEventBridge.broadcast(agentId, liveMsg)`** — subscribers are keyed by **real `agentId`**, not run id.
3. **Live** — Clients connect to **`/ws/live/:agentId?runId=`**. `runId` triggers **replay** of stored events for that run on open (`ws/live.ts` + `replayRunEvents`).
4. **REST** — `GET /api/runs`, `GET /api/runs/:runId`, `GET /api/runs/:runId/events`, **`POST /api/runs`** (desk runner). Skills: `GET /api/skills/session/:sessionId` (what a chat's agent can load), `GET /api/skills/workspace?root=&paths=&global=1` and `GET /api/skills/workspace/file?…&path=` (Lab; framework discovery, section 9), `GET /api/skills/sqlite/:id` (Cortex library row), and the older Cortex-scan routes `GET /api/skills/files`, `GET /api/skills/file?path=` (no UI reads them). Workspace picker: `GET /api/workspace/check?path=` (absolute existing dir → normalised path, else 400), `GET /api/workspace/recent`, `GET /api/workspace/candidates` (ranked suggestions: launch dir's git root, launch dir = server cwd, `CORTEX_SKILL_SCAN_ROOT`, recent; plus `home`), `GET /api/workspace/browse?path=&hidden=1` (subdirectory names + `isGitRepo` only, home by default, 400 on relative/missing paths, capped at 500 entries). Built-in toolset shortcuts: `GET /api/tools/toolsets`; shell toolsets → the programs they run: `GET /api/tools/shell-presets`; shell allowlist sources (defaults, opt-in, groups): `GET /api/tools/shell-commands`. Routers under `server/api/`.
5. **Workspace** — `workspace` (absolute existing dir) on a chat session / run / saved agent maps to `.withTools({ workspace })`: file tools confine to it and `shell-execute` runs in it. Chat create/PATCH and `POST /api/runs` refuse a bad path with 400 (`services/workspace-dir.ts`); chat sessions forward it, the shell options and `terminalTools` only when tools are on (a tools-off chat never gets `shell-execute`). Shell options ride in `terminalShellOptions` (`cwd`, `allowUnsafeCwd`, `timeoutMs`, `maxOutputChars`, `commandAccess`, `sandbox`). The builder edits the shell allowlist as **one list** (`ShellCommandsField.svelte`): the exact commands the agent gets as removable chips, framework defaults pre-filled from `GET /api/tools/shell-commands` (framework `DEFAULT_ALLOWED_COMMANDS`, `OPT_IN_COMMANDS`, and the commands behind each `commandAccess` group; never copied into the UI), an add input, and quick-add buttons for the opt-in groups (no `github`: the `git` toolset brings `gh`). `ui/src/lib/shell-allowlist.ts` folds stored `terminalShellAllowedCommands` + `terminalShellAdditionalCommands` + legacy `commandAccess` into that list and writes edits back as extras beyond the defaults → `terminalShellAdditionalCommands`, or, once a default is removed, the full list → `terminalShellAllowedCommands`; it never sets `commandAccess` (cleared on the first edit; an unedited legacy config still sends it, so no command is lost). The group → commands map is the framework's `COMMAND_CAPABILITY_MAP` (`@reactive-agents/tools`), served as is; Cortex keeps no copy (`server/tests/shell-commands-catalog.test.ts`).
6. **Tool disclosure + toolsets** — `.withTools({ disclosure, builtins })` are AgentConfig paths, so they ride `rawConfig.tools` (builder Tools section `ToolDisclosureField.svelte` and chat `/tools` "Show tools" rows, both via `disclosurePatch` in `ui/src/lib/chat-quickbar.ts`; `builtins` via the Lab generic renderer). The Tools quick picks list `kind: "built-in"` catalog rows plus the shell toolsets (`shellPresetPicks`); meta-tools are configured in Meta tools. A shell toolset (`git` = `git`/`gh`; framework `BUILTIN_SHELL_PRESETS`, served by `GET /api/tools/shell-presets`, never hard-coded in the UI) is selected by its own name in `tools`, never as `shell-execute`: the framework resolves the name to a `shell-execute` limited to those programs, while `shell-execute` in `tools` means the full host shell (`shellExecuteRequested`). Chat `/tools` rows follow the same rule (`toolsetChoice` in `ui/src/lib/chat-quickbar.ts`). The shell has three states (`ui/src/lib/shell-from-picks.ts`): off, toolset-only (a toolset picked, `terminalTools` off: `shell-execute` limited to its programs) and full (`terminalTools` on). While a toolset is picked the builder's host-shell checkbox never shows unchecked but stays clickable: a click flips the user's own `terminalTools` (git · gh only, full shell), and a hint says which. The chat shell chip and the `/terminal` off row read `Shell: git · gh only` in that state. Unpicking the toolset shows the user's own value again. Stored configs naming the removed `gh-cli` / `git-cli` tools are rewritten to `git` on read and at build; `gws-cli` and a stored `workspace` pick (the gws toolset the framework removed) are dropped with a server warning and never turn on the shell (`server/services/legacy-cli-tools.ts`, pinned by `server/tests/legacy-cli-tools.test.ts`). `tools.builtins` suggestions come from `GET /api/tools/toolsets`. The run view pill reads `AgentStarted.config.disclosure` (`{ mode, source }`). Pinned by `server/tests/tool-disclosure-parity.test.ts`.

7. **Provider API keys** — `/api/settings/keys` (`api/provider-keys.ts`): `GET /` (masked status per provider, never a key), `PUT /:provider` `{ apiKey }`, `PATCH /:provider` `{ preferStored }`, `DELETE /:provider`, `POST /:provider/test` `{ apiKey? }` (framework `listProviderModels` with that key; failures go through `redactKey`). Store: `services/provider-key-store.ts`, AES-256-GCM (`node:crypto`, provider id as AAD) with a random 32-byte `secret.key` and `provider-keys.json` beside the DB (`.cortex/`), both mode 0600, atomic writes. An env key wins unless the user turns on "use the saved key" (`preferStored`). `buildCortexAgent` is the one funnel: `providerKeyForAgent` → `.withProvider(provider, { apiKey })`; `process.env` is never written. The model list and `keyConfigured` / `/api/health/providers` count a saved key. Every keyed provider's framework adapter honours the passed key (llm-provider `d1955526c`, anthropic and gemini included), so `storedKeyAppliesToAgents` is true for all of them; a new keyed provider whose adapter ignores a passed key must stay out of its set. No-key help (Model page, model picker note) points to Settings · Providers as well as the env variable. Pinned by `server/tests/provider-keys.test.ts`, UI `provider-keys.test.ts`.

8. **Output speed (tok/s, TTFT)** — one formula: core `outputTokensPerSecond` = `tokensOut / ((durationMs - firstTokenMs) / 1000)`; ui-core `throughputOf` / `throughputOfCalls` carry the same math for the browser (pinned equal in `server/tests/model-throughput.test.ts`). A call without `firstTokenMs` gives a lower bound, shown `~`. Chat (`ChatTokenUsage.svelte`, `turnSpeedOf` in `lib/chat-token-usage.ts`): a live `~tok/s` estimate while text streams (`liveRate`, ui-core `liveTokensPerSecond` over `estimateTokens` since the call's first delta), then the measured speed + TTFT over `usage.calls` (persisted with the turn trace). Run view: per-loop speed on trace rows (`CortexTraceFrame.throughput`), run average in `RunVitals` (`RunVitals.llmCalls`); both read stored `LLMRequestCompleted`. Model page: `GET /api/model-throughput?provider=&model=&runs=` (`api/model-throughput.ts`, `services/model-throughput.ts`) gives medians; exact and lower-bound rates are never mixed (a lower-bound median only when no call measured TTFT, marked). Wording: `lib/llm-throughput.ts`. The runtime `TokenUsage` stream event does not forward `firstTokenMs` yet, so a chat turn's settled speed reads `~` (lower bound) until it does; the run view and Model page already read the exact value.

9. **Workspace skills** — Cortex lists skills with the framework's own discovery (`discoverSkills` / `skillScanPaths`, `server/services/workspace-skills.ts`) at the root a run uses: the session or Builder `workspace`, else the server cwd; scan order `<root>/.<agentId>/skills`, `<root>/.agents/skills`, configured `paths`, `<root>/.claude/skills`, then `~/.agents/skills` and `~/.reactive-agents/skills` only with `global`. Cortex keeps no copy of that order. Every chat agent gets `.withSkills()` (`migrateChatSkillsConfig` always returns a config; desk runs and saved agents only when they set paths, pins or `global`: `parseCortexSkillsConfig`). Pins are skill **names** (`skills.activate`); `toggleSkillPatch` and the agent's `pin-skill` proposal never write a scan root. Older chat pins stored a cwd-relative root in `paths`: `migrateChatSkillsConfig` rewrites it to an absolute dir (workspace first, then server cwd) and drops roots discovery already scans. `/skill <name>` (picker `skill-once`) queues a skill for the next message, sent as `skills` on `POST /chat/sessions/:id/chat/stream`; `/skills <name>` toggles a session pin. The pins ride the turn as `session.runStream(msg, { skills: { activate } })` / `session.chat(msg, { skills })` (`turnSkillsOption`); the cached session agent is kept and the session config is never written. What a run had active: `server/services/chat-turn-skills.ts` `recordSkillActivity` keeps each run's `AgentStarted.config.skills` and `SkillActivated` events (an event without `taskId`, as the kernel's `activate-skill` publishes today, counts for the session's current run) and stores ui-core `foldRunSkills` on the turn as `trace.skills`; the chat turn and the run view render it with `SkillActivationRow.svelte` (`lib/skill-row.ts`: `pinned`, `matched the task`, `loaded by the agent`). Lab Skills has two views (`LabSkillsUi.view`): **Agent skills** (section 11) and **Skill files**, the workspace skills for the Builder's scope (`lib/stores/lab-skills-store.ts` `skillScopeOf`) plus the Cortex library rows (cortex.db, **deprecated**, not sent to agents; each row has "Move into agent skills"). Pinned by `server/tests/workspace-skills.test.ts`, `chat-turn-skills.test.ts`, UI `skill-row.test.ts`, `chat-menu-items.test.ts`, `lab-skills-store.test.ts`, ui-core `skill-activations.test.ts`.

10. **Memory studio** — every memory read and write goes through the framework's `agent.memory()` facade; Cortex never opens a `memory.db`. `server/services/memory-inspector.ts` (`MemoryInspector`, one per server, `disposeAll` on stop) builds one small `test`-provider agent per inspected agent id with `.withAgentId(id).withMemory({ dbPath })`, where `dbPath` is the framework's own `defaultUserMemoryPath(id)` (`$HOME/.reactive-agents/memory/<id>/memory.db`, the path a bare `.withMemory()` uses; passed explicitly because a `test` build would otherwise use `:memory:`). An id whose database does not exist is reported `available: false` and never built, so looking never creates a database; ids with a path separator or `..` are refused. Routes (`server/api/memory.ts`): `GET /api/memory/agents` (ids with a database under the memory root, labelled by saved agent, chat session or latest run name: `db/memory-agent-queries.ts`), `GET /api/memory/:agentId?runId=` (semantic, procedural, episodic; `runId` narrows to what that run wrote: semantic and procedural through the facade's `list({ runId })` (filtered in the store query, before the limit), episodic rows by `taskId` = the run id or a task id the run's entries carry (`listingForRun`; the episodic list has no run filter, so that part still applies after its 200-row limit)), `GET /api/memory/:agentId/search?q=&runId=` (framework FTS5; words of 2+ characters, common stop words dropped), `PATCH|DELETE /api/memory/:agentId/semantic/:id`, `PATCH|DELETE /api/memory/:agentId/procedural/:id` (404 for an unknown agent or id). UI: Lab tab `components/memory/MemoryStudio.svelte` (agent picker, search, layer tabs Facts / Workflows / Log, entry, provenance link to `/run/<runId>`, edit form, delete through kit `Overlay`); rules and client in `lib/memory-studio.ts` (`semanticPatchOf` / `proceduralPatchOf` send changed fields only, `provenanceOf`, `memoryStudioHref`). The run view's Memory tab (`MemoryPanel.svelte`) lists what the run wrote from the same route. Agents with a custom `memory.dbPath` are not found (the inspector only knows the default path). Pinned by `server/tests/memory-studio.test.ts`, UI `memory-studio.test.ts`, `lab-tabs.test.ts`.

11. **Living skills** — an agent's stored skills (the framework SkillStore in its memory database) in Lab Skills · Agent skills (`components/skills/AgentSkillsPanel.svelte`, rules and client in `lib/agent-skills.ts`; version diff, confidence words and lifecycle entries from ui-core `skillLineDiff` / `skillConfidenceLabel` / `skillLifecycleEntryOf`). Server `services/agent-skills.ts` (`AgentSkillsService`) goes through the framework only: list = `agent.skills()` on the Memory studio's inspector agent (`MemoryInspector.withAgent`, so the same agent ids and "no database = unavailable" rule); Refine now = `agent.refineSkills()` on an agent built with the agent's last recorded provider/model (`lastRunModelOf`, cortex_runs) over the same database; Export = `agent.exportSkill(name, <Builder workspace>/.agents/skills/<name>)`; Move from the library = `agent.loadSkill(dir, { evolutionMode })` of a temp SKILL.md (front matter single-quoted; the dialog `components/skills/MoveLibrarySkillDialog.svelte` picks the mode, `auto` first; no mode = the framework default, `locked` for a new skill). A name the agent already has is 409 unless the body has `update: true`: then the row reloads over that skill, and the framework keeps its id, stats and history and adds a version when the text changed (the dialog offers **Update existing** on the 409). The library row is deleted after a move. Roll back = `agent.rollbackSkill(name)`; Lock / Unlock = `agent.setSkillMode(name, "locked" | "auto")` (history untouched; `lockActionOf` in `lib/agent-skills.ts`). Manual Refine now and Roll back publish `SkillRefined` / `SkillRolledBack` (`reason: "manual"`) on the acting agent's bus with no run; `AgentSkillsService` subscribes for the call and hands them to its `SkillEventSink`, which `server/index.ts` wires to `recordSkillControlEvents` (cortex.db, `run_id` `""`, source `cortex-skill-control`, so run retention never drops them); the timeline shows them "in Cortex" (`timelineOriginOf`). Routes (`server/api/agent-skills.ts`): `GET /api/agent-skills/:agentId` (skills + `refineWith`), `GET /api/agent-skills/:agentId/events?skill=` (stored `SkillActivated` / `SkillRefined` / `SkillRolledBack` / `SkillPromoted`, newest first, `runId` = the event's `taskId` when Cortex has that run, `""` for a Cortex action: `db/skill-lifecycle-queries.ts`), `POST …/refine` `{ provider?, model? }`, `POST …/skills/:name/rollback`, `POST …/skills/:name/mode` `{ mode }`, `POST …/skills/:name/export` `{ root }`, `POST …/library/:libraryId` `{ evolutionMode?, update? }`. Pinned by `server/tests/agent-skills.test.ts`, UI `agent-skills.test.ts`, ui-core `skill-evolution.test.ts`.

Canonical live payload shape: **`CortexLiveMessage`** in `server/types.ts` (`v`, `ts`, `agentId`, `runId`, `source`, `type`, `payload`). Event `type` is the AgentEvent `_tag` string; `payload` is the event object as JSON.

## WebSocket Paths (Critical)

| Path | Role |
|------|------|
| `/ws/ingest` | Agent → server; JSON `CortexIngestMessage`. |
| `/ws/live/:agentId?runId=` | UI (or tools) → server; **`agentId` must match the agent that receives broadcasts** (same string used in `broadcast(agentId, …)`). |

**Gotcha — Stage grid:** `+layout.svelte` historically used a path like **`/ws/live/cortex-broadcast`**. The bridge **only** fans out to subscribers registered under each message’s **`agentId`**. Until Stage subscribes using the **same `agentId`** as ingest (or the server adds a separate fan-out channel), the desk grid may not show live events. **Run detail** is correct: `run-store.ts` loads `GET /api/runs/:runId`, then connects to **`/ws/live/${encodeURIComponent(agentId)}?runId=…`**.

## UI Architecture

### Constants and proxy

- **`ui/src/lib/constants.ts`** — `CORTEX_SERVER_URL` and `WS_BASE` use **`window.location`** in the browser so fetches and WS go through the Vite dev origin; SSR fallback uses `localhost:4321`.
- **`ui/vite.config.ts`** — Proxies **`/api`** and **`/ws`** to `http://127.0.0.1:$CORTEX_PORT` (default 4321, and WS). A second stack for live checks, beside a running one: start the server from its own cwd (its DB is `.cortex/cortex.db` under the cwd) with `CORTEX_PORT=4417 CORTEX_NO_OPEN=1 bun run <repo>/apps/cortex/server/index.ts`, then `CORTEX_PORT=4417 bun run --cwd apps/cortex/ui dev -- --port 5217 --strictPort`.

|-------|---------|
| `/` | Beacon — Board (default) or Field (`?view=field`, stored as `cortex.beacon.view`; the URL wins), first-run hero, prompt bar; `stage-store` + layout `agentStore`. |

### UI theme (stay consistent)

Cortex is a **local desk**: readable, keyboard-friendly, and visually aligned with **Reactive Agents docs** (`docs.reactiveagents.dev`), not a generic marketing site.

The design language is **Bench** (`wiki/Architecture/Design-Specs/2026-11-10-cortex-ui-modernization.md`; mockups and the token source `tokens.css` beside it). Violet is the agent, cyan is tools and data, green/amber/red are outcomes; the signal gradient's motion, the live glow and the sonar mean "running now" and nothing else.

| What | Where |
|------|--------|
| Semantic tokens, both themes (`--cortex-canvas`, `--cortex-surface-1..3`, `--cortex-line(-strong)`, `--cortex-text/-2/-3`, `--cortex-accent(-fill)`, `--cortex-io`, `--cortex-ok/warn/bad` + `*-tint`, `--cortex-focus`; type, radius, `--cortex-z-*` layers, motion) | `ui/src/app.css`. Light is `:root`, dark is `html.dark`; each colour also has a `*-rgb` channel token. There is **no** light-mode override block: a new colour is a token, never an `html:not(.dark)` patch. The legacy names (`--cortex-bg`, `--cortex-surface`, `--cortex-border`, `--cortex-text-muted`, …) were removed in step 8. |
| Tailwind colours | `ui/tailwind.config.ts` — the semantic tokens by their own names, each `rgb(var(--cortex-*-rgb) / <alpha-value>)`: `canvas`, `surface-1..3`, `line`, `line-strong`, `text`, `text-2`, `text-3`, `accent`, `accent-fill`, `io`, `ok`, `warn`, `bad` (`bg-surface-1`, `border-line`, `text-text-2`, `text-accent`, `bg-accent-fill`). The neutral text colours have an opacity floor (`text-text-3/40` renders as text-3) so muted text keeps AA. The MD3 aliases (`surface-container-low`, `on-surface`, `primary`, …) were removed in step 8. Layers: `z-sticky` `z-nav` `z-drawer` `z-modal` `z-toast` `z-tooltip`. |
| Fonts and icons | Self-hosted via fontsource (`app.css`): Geist for words, JetBrains Mono for machine values; nothing loads from a font CDN. Wordmark is Geist 600, sentence case. Every icon is inline SVG from `kit/Icon.svelte` (typed `IconName`); the Material Symbols ligature font is gone. Tool quick picks carry a kit `IconName` (`TOOL_ICONS` in `lib/builder-tool-picks.ts`); `Command.icon` in the palette store is a typed `IconName`. `MarkdownRich`'s `--cortex-md-*` tokens alias the semantic tokens. `lib/no-legacy-visuals.test.ts` fails on any Material Symbols use or CDN link, MD3 alias, retired identity class (`gradient-border`, `cortex-progress-*`, `hover-lift`, `sonar-ring`, `cortex-shell-bg`, `cortex-kbd`, `ra-gradient-text`) or legacy `--cortex-*` alias under `ui/src`. |
| Identity layer | `NeuralMark` (`kit/NeuralMark.svelte`, geometry in `lib/neural-mark.ts`; `static/favicon.svg` matches it) is the only logo and illustration. Utilities in `app.css`: `.band` (grid behind page headers), `.dotgrid` (Beacon Field), `.glow-live` (live cards only), `.sonar` (running Field nodes only), `.rail` + `.rail-live/-failed/-attention`, `.brand-grad` (22px and up only). |
| Theme and Motion (Settings · Appearance) | Both apply at once and Save never writes them (`savePatchOf` in `lib/settings-page.ts`), so a Settings form opened earlier cannot undo the top-bar theme switch. Theme (`lib/theme.ts`, stored as `theme`): `system` follows `prefers-color-scheme` (the layout listens for changes), `dark` / `light` pin one; the top-bar switch pins the opposite of what is showing; `app.html` applies it before first paint. Motion (`lib/motion.ts`, stored as `motion`) sets `html[data-motion="reduce"]`; `app.css` applies the same rules as `prefers-reduced-motion`. Every animation needs a reduced-motion fallback. |

## Pitfalls (Cortex-Specific)

0. **Rebuild packages before testing Cortex.** Cortex imports `@reactive-agents/*` from `dist/` (compiled output), not `src/`. If you modify framework packages without running `bun run build:packages` (or `bun run build`) from the repo root, Cortex will execute stale code. Always rebuild after package changes: `bun run build:packages && cd apps/cortex && bun start`.
1. **Live WS `agentId` in the URL must match broadcast keys** — derived from ingest `agentId`, not arbitrary labels.
2. **Do not double-load run history** — Run view relies on **WS replay** after connect; avoid also replaying the full event list from REST in the same client unless you dedupe.
3. **`POST /api/runs`** is still **501** by design — UI must handle gracefully (`stage-store` already does).
4. **Pause/stop** routes may be missing — `run-store` `pause`/`stop` fail quietly.
5. **Debrief in REST** — Run summary exposes `hasDebrief`; full debrief object typically arrives via **`DebriefCompleted`** on the live stream.
6. **Approval policy** — the gate is the framework's top-level `approvalPolicy` (`mode`, `tools`, `commands`: shell command rules such as `git push`), carried as is through the run body, chat config and saved agents, and sent to the framework through the AgentConfig (`cortexParamsToAgentConfig`). `server/services/approval-policy.ts` `approvalPolicyOf` is the one reader on all three build paths; it also reads the legacy `durableRuns.approvalTools` / `approvalMode` / `durableRuns.approvalPolicy` shapes (only while durable runs are on) and drops a policy that gates nothing (any policy makes the framework also gate its `requiresApproval` tools, served by `GET /api/tools/approval-required`). A `detach` policy turns durable runs on in `buildCortexAgent` (build refuses detach without a store). A tools-off chat gets no policy. Cortex supplies no `onApprove`, so `block` refuses every gated call; the UI says so. UI: `lib/approval-policy.ts` (rules, `autoGatedTools`, `approvalPatch`), `agent-config/ApprovalPolicyFields.svelte` (Reasoning section), chat `/approvals` rows in `chat-menu-items.ts`. The run view header shows Approve / Deny while the run waits (`runApprovalOf` in `waiting-on-you.ts`; the endpoints take the approval's durable run id). Pinned by `server/tests/approval-policy.test.ts`, `config-parity`, `build-path-parity`, `chat-builder-controls`, UI `approval-policy.test.ts`, `chat-menu-items.test.ts`.
   **Durable approvals in chat** — a streamed chat turn with `durableRuns` + an approval-gated tool pauses (`StreamCompleted.pendingApproval`). `services/chat-approvals.ts` holds it as a `chat_pending_approvals` row (the user message waits there, not in `cortex_chat_turns`) and registers it in `durable-approvals` as an owner-managed entry: listed by `GET /api/runs/pending-approvals` (with `chatSessionId`) and `GET /api/chat/sessions/:id/approvals`, resolved by `POST /api/chat/sessions/:id/approvals/:runId/approve|deny|dismiss` or the desk `/api/runs/:runId/approve|deny`. Either way the resumed reply lands in the thread and the cached agent is evicted so history rebuilds from the DB. New turns get 409 while a turn is pending. Rows survive restart (`restore()` at boot); resuming then needs the same session config (durable config hash). A turn that pauses on `request_user_input` (`pendingInteraction`, first turn or after an approval) is held the same way in `chat_pending_interactions` (not in the desk approval list), returned as `pendingInteractions` on `GET /api/chat/sessions/:id`, and rendered by `ChatInteractionCards.svelte` as a reply box (Yes/No, choice buttons, form fields, or free text; helpers in `ui/src/lib/chat-interactions.ts`). `POST /api/chat/sessions/:id/interactions/:runId/respond` (`{ value }`) resumes it through `respondToInteraction`; the question and the answer land in the thread as their own exchange, then the reply (or the next pause). `.../interactions/:runId/dismiss` drops it. Both the stream and non-stream chat paths hold pauses (`ChatApprovals.holdIfPaused`). Pinned by `server/tests/chat-durable-approval.test.ts`.
7. **Chat slash menu state** — the menu anchors above the quick bar (so chips stay clickable) and closes on a pointer press outside it; elements marked `data-slash-menu-keep` (composer, quick bar) do not count as outside. Chip/draft/multi-select rules are pure in `ui/src/lib/chat-menu.ts` (`chipClicked`, `menuClosed`, `pickChip`/`closeMenu` for the composer + menu state together, `keepsMenuOpen`, pinned by `chat-menu.test.ts`); multi rows (`MenuItem.multi`) toggle through `createToggleQueue`, which queues PATCHes and computes each patch when it runs. ChatPanel effects that reset per session read the `$derived` `activeSession`, never the `sessionId` prop directly: the prop getter tracks the parent's whole chat store, so a direct read re-ran on every store update and wiped the composer.
8. **Chat transcript contract** — an assistant turn in `/chat` reads as the agent talking (`ChatTranscript.svelte`, ChatPanel only wires it): ui-core's `buildTurnTranscript` via `turnTranscript` in `ui/src/lib/stores/chat-timeline.ts` gives the order. The model's narration renders as normal markdown prose; the tool work between two pieces of prose is one collapsed row (`Ran 7` plus one badge per tool from ui-core `toolBadgesOf`: `web-search ×3`, an unfixed failure as a red badge that never hides behind the `+N` overflow, a fixed one with a check, then `N failed` and the duration; `Running` while a call runs) that expands into the step rows below (`ChatTurnTimeline` with `only={group.steps}`: no summary, no narration, since the prose already shows it); the answer closes the turn with its copy button. Provider thinking never enters the reading path (it stays in the expanded steps). While streaming, the in-flight text is a non-final answer, muted and unrendered. Sub-agents render as compact cards (`ChatSubAgentCards.svelte`, ui-core `subAgentCardOf` / `subAgentRollup` via `subAgentCard` in `ui/src/lib/sub-agent-view.ts`): a `4 agents · 1 running` header, then per agent its name, a status dot (running / done / failed / abstained), its goal icon, `2 tools · 20s · $0.003`, and one muted activity line (the running call with a short argument hint, the result's first line, or why it failed; never raw tool JSON). A click opens `ChatSubAgentDrawer.svelte`, a side panel that renders the child's own `ChatTranscript` (nested sub-agents are cards again); a failed child's synthetic turn carries `runFailed` so the panel closes with its ending note. Goal checks (`ChatPlanCard`, `planCardModel` in `ui/src/lib/checklist-view.ts`) are a compact `Goals 3/4` pill in the footer: the floor requirement every run has (`produce a substantive answer…`, id `answer`, ui-core `isImplicitRequirement` / `goalSummaryOf`) is hidden unless blocked, a card with only implicit checks is not shown, it opens while a plan runs or a goal is unmet, and sub-agent goals fold into each card's icon (ui-core `findSubAgentGroup`). The summary line sits in the footer; model and token usage stay in the header. Under each message an action row (`ChatTurnActions.svelte`, helpers in `ui/src/lib/chat-turn-meta.ts`) holds a status tick, the time (user: `3 minutes ago`; assistant: `Ran 2m 05s · finished 3 minutes ago`, a live `Running 12s` while it streams; the absolute time on hover), the strategy chip (`ReAct`, `ReAct + Reflexion` when sub-agents ran others; read from `StreamCompleted.metadata.strategyUsed` on the turn and each child, never from config) and copy / retry / trace / fork. Duration is the run's reported `metadata.duration`; ui-core's fold records `strategy` and `durationMs` on the trace and the server keeps them through the turns table (`db/chat-queries.ts`). A live turn's `ts` is its send time; a stored assistant row's `ts` is its finish time (`hydrateTurn` sets `finishedAt`). The assistant turn pins the provider/model it started with (`turnModelOf`). Reloaded turns build the same transcript from the stored trace (`hydrateTurn`); a trace with no narration reads as one tool group plus the answer, a turn with only `toolsUsed` shows tool-name chips. Do not re-derive the order in Cortex. Pinned by `chat-timeline.test.ts` (`turnTranscript`) and ui-core `turn-transcript.test.ts`. **Chat turn steps** — the step list (`ChatTurnTimeline.svelte`, in the turn inspector and inside an expanded tool group) is ui-core's action-first step view (`buildTurnSteps` via `turnSteps` / `turnSummary` in `ui/src/lib/stores/chat-timeline.ts`): rows are titled by the tools called (retries grouped, `· 2 failed → ok`), narration shows under the row, thinking is collapsed, a repeat says "same as step N", failures show the reason and the fixing call, and a summary line above gives steps, calls, failures, outcome and the context window in use. Cortex renders it; it does not re-derive steps. Persisted traces carry `narration` / `thinking` per iteration (older ones only `thought`, read as narration). **Chat trace timeline** — the turn inspector's Run trace tab gets frames and timeline groups from `buildRunTrees` (`ui/src/lib/chat-export.ts`), built from the tracer JSONL (each line is already a `TraceEvent`). The run view builds its timeline from live AgentEvents (`timeline-store.ts`) instead; both categorise with `timeline-filter.ts`.
9. **Panel field styles** — `.acp-field` / `.acp-stack` / `.acp-hint` / `.acp-check` / `.config-input` etc. are global under `.agent-config-panel` (`components/agent-config/agent-config.css`, imported by AgentConfigPanel), so section components (`ShellWorkspaceFields`, `GuardrailsFields`) inherit them; the section shell and its head are `ConfigSection` (`icon`, `title`, optional summary snippet). New panel sections go in their own component; `AgentConfigPanel.svelte` and `ChatPanel.svelte` only wire them. 10. **Chat queue, draft swap and compaction contract** — Config changes during a run never queue (`ui/src/lib/chat-live-config.ts`): quick-bar chips and the config commands (`/model`, `/provider`, `/thinking`, `/strategy`, `/tools`, `/terminal`, `/workspace`, `/iterations`, `/skill`, `/skills`, `/docs`, `/agent`) open their picker (`/skill` only marks a skill for the next message, no PATCH) and PATCH the session config at once, the toast says it applies to the next turn, and the send button reads Send, not Queue. The server keeps the running turn's agent: `updateSessionConfig` during an in-flight turn marks the session and evicts the cached agent when the turn releases (pinned by `server/tests/chat-session-service.test.ts`). Enter during a run parks other text in one slot (`ui/src/lib/chat-queue.ts`); it auto-sends only when the run ends normally, and an error, a user stop, or a run that reported `success: false` (`lastRunFailed`; such a run still ends with a normal `StreamCompleted`) keeps it with "Send now". Text put into the composer goes through `replaceDraft` (`ui/src/lib/chat-draft.ts`), never a raw assignment; `restoreDraft` is a swap, so the text Restore displaces gets its own Restore. Compaction summaries follow `COMPACTION_SECTIONS` (`server/services/compaction-summary.ts`); headings match after `normalizeSectionHeading` (case, spacing, trailing colon or parenthetical) and are rewritten to the exact name, the UI parser mirrors the list and the rule (pinned against each other in `compaction-summary.test.ts`), and section guidance stays out of the prompt's heading lines; unstructured output is wrapped, not rejected. The estimate the compact call computes is persisted on the summary row, kept rows lose their readings, and `carryContext` must not resurrect a pre-compaction reading. Pinned by `chat-queue.test.ts`, `chat-draft.test.ts`, `chat-context.test.ts`, `compaction-summary.test.ts`, `chat-compaction-context.test.ts`.
11. **Run endings (failed, partial, abstained, files only)** — the harness never writes text into `output`. A failed or abstained run's `StreamCompleted` has `output: ""`, the cause on `error` (`… What was attempted: …`) and `terminatedBy`; an abstention also has `terminatedBy: "abstained"` and `abstention { reason, missing }`; a partial run ships the model's draft plus an `Unfinished:` list; a successful run whose answer is a file can have `output: ""` with `receipt.deliverables`. Never read harness sentences (`Could not complete the task`, `Strategy execution failed`, `[verification blocked]`, `Completed: …`) from `output`. ui-core `turnOutcomeOf` is the one classifier: server `chat-turn-trace.ts` (`turnOutcomeOf`, `readStoredOutcome`) and UI `ui/src/lib/turn-ending.ts` (`completionEnding`, `chatTurnOutcome`, `endingNote`, `endingBadge`, `runEnding`) wrap it. The cause comes from `StreamCompleted.error`; `server/services/chat-run-errors.ts` (bus `ReasoningFailed` / `AgentCompleted` / `TaskFailed`) only fills in when a completion reports none. The stream path persists a turn that did not succeed with its `output` as content (often `""`, never the streamed narration) and `trace.outcome = { success: false, ending, terminatedBy?, error?, abstention?, unfinished? }` (rows without `ending` read as failed), and a file-only answer with `trace.deliverables`. `turnsToChatMessages` sends `[The previous run failed (…): cause. No answer was given.]`, `[The previous run abstained: reason. …]` or `[The previous run produced: files.]` in place of the content (`historyContentOf`), and the auto-titler gets no reply text for a failed turn. The live cached session's own history still records the framework's own failed-turn note (`ChatEngine.streamTurn`) until the agent is rebuilt from the DB. The chat transcript closes with ui-core's `ending` segment, rendered by `ChatRunEndingNote.svelte`: failed in red (`ChatRunFailedNote`), abstained as a quiet decline with its reason and missing inputs (when the model wrote its decline as the answer, `abstentionInAnswer` in `ui/src/lib/turn-ending.ts` is true and the note only marks the decline, never repeating the reason), partial as the draft plus the unfinished list, files as a "Produced" list; the header badge (`endingBadge`) reads `did not finish` / `partial` / `abstained`. The run view's `RunEndingBanner.svelte` does the same from `AgentCompleted` (`outcome.status`). The run toast (`ui/src/lib/run-toast.ts`, one keyed toast per run) and `ui/src/lib/run-error.ts` (first line, credentials redacted, capped) are unchanged. Pinned by `server/tests/chat-failed-turn.test.ts`, `chat-run-errors.test.ts`, `chat-turn-trace.test.ts`, `chat-strategy-matrix.test.ts`, UI `turn-ending.test.ts`, ui-core `turn-outcome.test.ts`. Local providers get no Cortex `numCtx` default: unset, the framework sizes the window per model. The shared live socket is ref-counted (`ws-client.ts`): a page closing its handle must not close the layout's.
12. **Turns that never complete, and the wait on the model** — a turn that fails before its run reports (the agent cannot be built, `session.chat` throws on the tools-off path, e.g. a model that is not pulled) is persisted with the user message and `trace.outcome { ending: "failed", error }` and ends with a failed `StreamCompleted` (`failedOutcome` / `failedCompletion` in `chat-turn-trace.ts`); the cause goes through ui-core `causeLineOf`, which drops error class tags (`LLMError: `). The UI keeps the message too when nothing streamed (`failTurn` in `chat-stream.ts`). Stop calls `POST /api/chat/sessions/:id/chat/stop` (`stopTurn`, `services/chat-turn-stop.ts`), which aborts the run server-side, then drops the stream; a stream that only drops (page closed, navigated off) reads as a disconnect. Both store `trace.outcome { ending: "interrupted", interruptedBy: "user" | "disconnect", error }` with the partial text (`interruptedOutcome`; cause lines are ui-core `interruptionCause`), `StreamCancelled.reason` carries who, and history tells the model the reply was cut off. The runtime publishes no terminal bus event for an aborted stream, so `chat-ingest.ts` tracks the runs a turn started and `closeOpenRuns` ends them through ingest: `ExecutionCancelled` → run status `stopped`, `TaskFailed` → `failed`; a stopped run that then reports a failure stays `stopped`. The desk Stop and Terminate publish `AgentStopped` / `AgentTerminated` (then a failed `AgentCompleted`): ingest, `recomputeRunStats`, `run-live-status.ts` and the run view's `deriveStatus` all read them as `stopped` (pinned by `server/tests/ingest-service.test.ts`, UI `run-live-status.test.ts`, `stores/run-store-status.test.ts`). In `runner-service.ts`, Terminate lets `agent.run()` settle before disposing the agent (disposing first failed the run with "ManagedRuntime disposed" and lost its `AgentTerminated`), and Stop ends the run like Terminate when it has not stopped within `stopGraceMs` (5s): `agent.stop()` is honoured only at an execution-engine phase boundary, and the reasoning loop is one phase. A run that ends without its own stop event gets one ingested by Cortex (`endAsStopped`). Pinned by `server/tests/runner-service.test.ts`. Runs store how a finished run ended on `cortex_runs.ending` (ui-core `turnOutcomeOf` over `AgentCompleted`, `server/services/run-ending.ts`; written by ingest and `recomputeRunStats`, backfilled once by `backfillRunEndings` when the column is added); Runs and Beacon read it through `runRowStatus` (`lib/runs-table.ts`, the run header's `runHeaderStatus` rule), so an abstained or partial run reads Abstained / Partial (attention), not Failed; live rows classify `AgentCompleted` the same way. Pinned by `server/tests/run-ending.test.ts`, UI `runs-table.test.ts`, `beacon-board.test.ts`. A durable run paused at an approval gate or a question publishes no terminal event (its stored status stays `live`); Runs, the run view and Beacon show it as **Waiting on you** through one resolver, `waitingRunsOf` / `waitingStatusOf` in `ui/src/lib/waiting-on-you.ts`, fed by the app-wide `pendingApprovals` / `pendingInteractions` stores. At boot `closeOrphanedChatRuns` (`db/queries.ts`) closes chat runs a restart left `live`, except sessions holding a paused turn. The live Trace list follows the same rules (`ui/src/lib/run-live-status.ts`). While a turn waits on the model (request out, no token back; ui-core `foldModelWait`, from the send and after the last running tool finishes) the turn has `awaitingModelSince` and `ChatModelWait.svelte` shows `modelWaitLabel` (`Waiting for Ollama (loading the model or queued)` for Ollama) with the elapsed time. Status ticks and run rows paint ui-core `statusOfTurn` / `statusOfRun` tones. Pinned by `server/tests/chat-turn-endings.test.ts`, UI `stores/chat-stream.endings.test.ts`, `stores/chat-store.test.ts`, `run-live-status.test.ts`, ui-core `chat-states.test.ts`.
