# Subsystem Audit — Error Handling & Recovery

**Date:** 2026-07-29. **Part of:** [[00-overview|Systems Audit — Root Cause Analysis]].

**Scope (as given to the auditing agent):**
> Error Handling & Recovery (tool-error retry, M4 healing pipeline, verify/fix loops, LLM-call error handling)

## System health summary

The system is internally split in a telling way: tool-execution-layer error handling is genuinely mature (context-aware recovery hints gated on the actually-exposed schema, a 4-stage fuzzy healing pipeline, a bounded verification-retry gate with an explicit onReject policy, and a correctly-computed RI consecutive-tool-failure detector) — but LLM/stream-layer error handling is essentially absent on the path that matters: retryPolicy exists and is well-designed but is wired only into every provider's complete(), never into stream(), so the kernel's actual think-call path gets zero retry for any error class, transient or not. That single boundary gap (confirmed live against a real Ollama model) mechanically explains the rung-3 llm_error cluster, independent of tool-surface pruning. A second, narrower gap sits at the observability layer: the one public, documented field for building external tool-failure-streak alerting is either a hardcoded constant or silently means something else at a different emission site, while the framework's own correct streak count is computed but funneled into an unrelated, undocumented string tag instead — so the system does the right internal thing but can't be observed doing it. Neither gap is contradicted by, or duplicates, the already-filed and correctly-retracted F8/F9 history, which held up against current source.</systemHealthSummary>


## Findings

### 1. Streaming LLM calls — the path every kernel `think` call uses — get zero retry, on all 5 providers; retryPolicy is wired only into complete()

🔴 **Severity:** critical · **Confidence:** confirmed · **New this audit:** True

**Evidence:** grep across all 5 provider files shows exactly one `Effect.retry(retryPolicy)` per file, always attached to `complete:` (anthropic.ts:308, openai.ts:373, gemini.ts:424, litellm.ts:301, local.ts:612), and never again before or inside the following `stream:` method (anthropic.ts:325, openai.ts:390, gemini.ts:442, litellm.ts:317, local.ts:634 — zero occurrences of `retryPolicy`/`Effect.retry` in any of the five `stream()` bodies). The runtime-level wrapper (`packages/llm-provider/src/runtime.ts:42`, `stream: (req) => breaker.protect(llm.stream(req))`) only applies `CircuitBreaker.protect`, which counts failures for open/half-open/closed state and re-throws the single failure verbatim (`circuit-breaker.ts:74-81`) — it never retries the effect itself. `packages/reasoning/src/kernel/llm-gateway.ts:274` (`gatewayStream`, the sole mediator for every kernel LLM call per the 2026-07-26 fix) adds no retry either. `think.ts:700-757` calls `gatewayStream` directly and on any stream-init or stream-consume error sets `terminatedBy: "llm_error"` and fails the whole kernel state in one shot — no retry attempt anywhere in the chain from think.ts down to the wire.

**Mechanism:** retry.ts's `retryPolicy` (exponential backoff, 3 retries) is explicitly designed to retry `LLMRateLimitError`/`LLMTimeoutError` and skip permanent classes. Someone wired that policy into every provider's `complete()` method, but the parallel `stream()` method — added for the streaming/tool-calling path that the kernel actually uses (`gatewayStream` in every reasoning strategy's think phase) — never got the same wrapping. The gap is structural: two sibling functions in the same file/class, one inherits the retry contract, the other doesn't, and nothing upstream (gateway, runtime circuit breaker) fills it in. The result is that even the two error classes the codebase explicitly intends to retry (429 rate-limit, timeout) get zero retry benefit on the path 100% of reasoning-strategy LLM calls take.

**Downstream impact:** Any transient rate-limit or timeout hit during a kernel think call ends the entire agent run immediately (terminatedBy=llm_error, 0 tokens billed, task failed) with no backoff attempt, on every provider. This directly undercuts the documented backoff contract in retry.ts's own comment ("exponential backoff, up to 3 retries") for the codepath that matters, and is the mechanical explanation for the rung-3 qwen3.5 `llm_error` cells reproduced below — a single malformed-generation stream error kills the run at iteration 0/1 with no second attempt.

**Cross-tier behavior:** Verified live only on the local/ollama provider (see next finding's reproduction); the same structural gap (retryPolicy absent from stream()) is present verbatim in anthropic.ts/openai.ts/gemini.ts/litellm.ts, so a frontier-tier rate-limit or 5xx hit during a streaming think call should fail the same way, though this was not separately reproduced live against a frontier provider in this session — flagged as untested cross-tier for the anthropic/openai/gemini arms specifically, confirmed by source inspection only there.

### 2. qwen3.5-on-ollama `llm_error` cells (rung-3 bench) are a real, reproduced local-model tool-call-decode fragility, NOT tool-surface-pruning-specific — and the harness gives it zero retry

🟠 **Severity:** high · **Confidence:** confirmed · **New this audit:** True

**Evidence:** Live reproduction (packages/benchmarks/tmp-probe/probe-llm-error.ts, deleted after use, ollama qwen3.5:latest via real `ollama` daemon on this machine): `prune-only` arm failed at iteration 0 with `[debug] Fiber terminated with an unhandled error — LLMError: ollama request failed: XML syntax error on line 4: element <function> closed by </parameter>`, run-completed error `"LLM stream failed at iteration 0: ollama call failed (ollama:qwen3.5:latest): ollama request failed: XML syntax error on line 4..."`, terminatedBy=llm_error, 0 tokens. Re-ran the identical task on the `no-prune` arm (full, unpruned 4-tool surface) 3 times: run 1 succeeded (harness_deliverable), run 2 hit the SAME error verbatim (`XML syntax error on line 3: element <function> closed by </parameter>`, terminatedBy=llm_error, only 1 llm call / 3079 tokens), run 3 succeeded via a different path (max_iterations). This falsifies the hypothesis that pruning causes the error: the identical Ollama-side XML-decode failure fires under a full tool surface too. The rung-3 JSON (`2026-07-28-rung3-qwen35.json`) shows the same signature across arms — every llm_error cell has iterations=1, 2-3 total llm-exchange calls, and 14.5-17s duration (long for so little work, consistent with the model actually generating before the malformed-tool-call decode failure fires) — and it also hits `no-prune` once (cell 15, 1/3), just at lower frequency than the small n=3 sample suggested.

**Mechanism:** qwen3.5 (via Ollama's tool-calling template) occasionally emits malformed function-call markup (mismatched `<function>`/`</parameter>` closing tags) — a stochastic decode/generation fault, not a schema-exposure problem (the model never even reaches ToolNotFoundError; Ollama's own server-side template parser rejects the whole response before it becomes a tool_use event). `provider-error.ts:190` has no branch that recognizes this failure shape, so it falls through to the generic `new LLMError(...)` — NOT `LLMRateLimitError`/`LLMTimeoutError` — which `retry.ts`'s policy explicitly excludes from retry (comment: "Permanent failures (4xx bad-request/auth, model-not-found, parse, context-overflow) are NOT retried — retrying can't change them"). But this data shows retrying CAN change it: the same prompt against the same model succeeds in the majority of runs, so a single resample would very likely have recovered the task at near-zero additional cost. Compounded by the prior finding (stream() has no retryPolicy wiring at all), so this class of error was never going to be retried by either mechanism.

**Downstream impact:** A one-off, plausibly-transient local-model decode glitch currently causes a full task failure with 0 tokens delivered, indistinguishable in the harness from a genuinely permanent error (bad auth, missing model). This is the practical inverse of the historically-catalogued FM-B1 ("infinite retry on persistent tool failure") — here the failure mode is zero retry on a likely-transient generation fault, and it sits squarely in the audit's error-handling/recovery scope. Directly relevant to interpreting the rung-3 bench: the arm-correlated pattern in the JSON (2/3 vs 2/3 vs 1/3 vs 0/3) is consistent with small-n Bernoulli noise around a single systemic zero-retry defect rather than being caused by tool-surface pruning itself.

**Cross-tier behavior:** Local-tier only, live-reproduced 4 times in this session (1 in prune-only, 3 in no-prune re-runs) against a real running Ollama instance with the actual qwen3.5:latest model — not a synthetic/deterministic-provider artifact. Not tested against granite4 or frontier tiers in this session; the granite4 JSON (2026-07-28-rung4-granite4.json) was read but not separately probed for the same signature — flagged as untested for that tier.

### 3. The one documented, illustrated public API field for tool-failure-streak alerting (`lifecycle.failure.failureStreak`) is either hardcoded to 1 or silently repurposed as an unrelated counter — it never reflects an actual consecutive-failure count

🟡 **Severity:** medium · **Confidence:** confirmed · **New this audit:** True

**Evidence:** `packages/reasoning/src/kernel/capabilities/act/tool-observe.ts:576` and `packages/reasoning/src/kernel/capabilities/act/act.ts:856` both emit `emitToCompose(pipeline, "lifecycle.failure", { ...., failureStreak: 1, ... })` — a literal constant, on every single tool failure regardless of how many times the same tool has already failed in a row. `packages/reactive-intelligence/src/controller/dispatcher.ts:60/112` emits the SAME field name on the `switch-strategy`/`harness-harm`/`stall-detect` RI decisions as `ctx.budget.interventionsFiredThisRun (+1)` — the count of RI interventions fired this run, an entirely different metric under the identical field name. The one path that computes a REAL consecutive-tool-failure count (`evaluateToolFailureStreak`, `reactive-intelligence/src/controller/evaluators/tool-failure-streak.ts`, fed by `consecutiveToolFailures` correctly computed in `reactive-observer.ts:209-219`) does NOT feed the structured `lifecycle.failure` tag at all — it emits an unstructured string via `nudge.healing-failure` (`dispatcher.ts:152-157`, `streak=${decision.streakCount}` buried inside free text). `apps/docs/src/content/docs/reference/harness-tags.mdx:107-126` documents `LifecycleFailurePayload.failureStreak: number` with a worked example: `harness.tap('lifecycle.failure', (failure) => { alerting.trigger({ reason: failure.reason, streak: failure.failureStreak }); })`. Confirmed no test anywhere asserts an incrementing value: `packages/reasoning/tests/kernel/act/tool-observe.test.ts:91-106` only checks `failures[0]?.reason`; `packages/core/tests/compose-bridge.test.ts` only feeds synthetic literals (0, 1, 2) into `emitToCompose` directly, never through the real emission sites.

**Mechanism:** The `LifecycleFailurePayload.failureStreak: number` field was declared once in `harness-types.ts` and documented with a streak-alerting example, but never given a real per-tool consecutive-failure counter at either of the two sites that actually emit `lifecycle.failure` for tool errors — both hardcode `1`. Meanwhile the correctly-computed streak (used internally by RI's own tool-failure-redirect) rides a different, unstructured tag instead of populating this field. Three independent code paths all touch a field with the same name and type but three different (and two of them wrong) semantics, and nothing in the test suite pins the field to a real value, so the drift is invisible.

**Downstream impact:** Any user following the documented pattern to build an external circuit-breaker or alerting rule on `failure.failureStreak` (exactly the retry/escalation instrumentation this audit is about) gets a signal that is always 1 for ordinary tool errors — indistinguishable from a first-time hiccup no matter how many consecutive times the SAME tool has failed — while the framework's own internal escalation (RI's tool-failure-redirect) silently uses the correct number through a different, string-embedded channel the docs never mention. A user cannot build the exact retry/backoff distinction (persistent vs transient tool failure) this audit asked about using the documented public mechanism for it.

**Cross-tier behavior:** Not tier-dependent — this is a pure code-path defect independent of model behavior; not separately probed live since the emission is deterministic from the source code (hardcoded literal), confirmed by static reading rather than a live run.
