# Subsystem Audit — Observability & Trace Fidelity

**Date:** 2026-07-29. **Part of:** [[00-overview|Systems Audit — Root Cause Analysis]].

**Scope (as given to the auditing agent):**
> Observability & trace fidelity — RunLedger (packages/reasoning/src/kernel/ledger/), sub-agent ledger merge (Wave C.2 slice 2), and cross-provider token/cost accounting (packages/llm-provider/src/providers/)

## System health summary

The ledger substrate itself (run-scope.ts, step-projection.ts, ledger-sink.ts) is well-designed and its two tested delegation paths (inline default-path, kernel ReAct path) genuinely merge sub-agent ledgers correctly — I live-verified both, including 2-level nested delegation on the kernel path that has zero test coverage but works. The gap is a coverage/scope one: Wave C.2 slice 2 was wired at three sites (inline-act.ts, tool-observe.ts, act.ts) but code-action.ts runs tool calls through a fourth, bespoke sandbox-bridge path that nobody re-visited, so it silently reproduces the exact pre-Wave-C.2 disease (sub-agent work vanishes past a summary string) on that one strategy. Token/cost accounting is the same story: the Anthropic fix was real and is pinned, OpenAI and Gemini are independently correct by their own API semantics but have zero regression coverage, and LiteLLM — a 4th provider nobody re-checked after the Anthropic fix — has literally no cache-token handling, so its cost figures are silently wrong in the opposite direction (overstated, not understated) whenever the proxied backend caches. Both findings are the same underlying failure mode: a fix scoped to the two or three paths that were being actively measured, not audited against the full set of paths that structurally do the same thing.

## Findings

### 1. code-action strategy's sandboxed tool-execution bridge never merges a delegated sub-agent's ledger — Wave C.2 slice 2 has a fourth, unfixed delegation path

🟠 **Severity:** high · **Confidence:** confirmed · **New this audit:** True

**Evidence:** packages/reasoning/src/strategies/code-action.ts:161-187 (toolHandlers closure calls `toolSvc.execute()` directly and returns `output.result` — the raw SubAgentResult, containing `childRunLedger` — with no extraction) and :316-336 (the action/observation steps built for each sandbox tool call attach only `toolCall`/`observationResult`, never `subAgentLedger`, unlike the sibling sites at packages/reasoning/src/kernel/capabilities/act/tool-observe.ts:539 and act.ts:817-818 and packages/runtime/src/engine/phases/agent-loop/inline-act.ts:318,330 which all explicitly attach it). Live-reproduced with a probe calling the real `executeCodeAction` (packages/reasoning/src/strategies/code-action.ts) with a fake ToolService whose `spawn-agent` handler returns a SubAgentResult carrying a 2-entry `childRunLedger` (matching the exact shape at packages/tools/src/adapters/agent-tool-adapter.ts:143-165): the resulting `runLedger` correctly records `tool-invocation`/`tool-result` for the `spawn-agent` call itself (with the full childRunLedger JSON visible verbatim, un-merged, inside the tool-result preview text) but contains zero entries with `pass: "sub-agent:child-one"` — `new Set(ledger.map(e => e.pass))` = `{ undefined }` only. By contrast, an equivalent probe against the two paths Wave C.2 slice 2 actually touched — the default inline path (existing test packages/runtime/tests/subagent/ledger-merge.test.ts) and a `.withReasoning()` kernel-path probe I ran with the identical 2-level nested-delegation scenario — both correctly produce `sub-agent:child-one` and `sub-agent:child-two` passes with dense monotonic seq.

**Mechanism:** `stepToEntries` (packages/reasoning/src/kernel/ledger/step-projection.ts:168-172) is the ONE place that merges a child's ledger into the parent's, and it only fires when an observation step's `metadata.subAgentLedger` is populated. Three call sites populate it (tool-observe.ts single-call, act.ts parallel-batch, inline-act.ts default path) — all three were touched by Wave C.2 slice 2. code-action.ts runs tool calls through its own sandboxed-Worker bridge (a documented, deliberate bypass of the shared executeToolAndObserve/kernel act primitive, originally built to let LLM-generated code call bound JS functions) and was never revisited when the sub-agent merge feature was added, even though the DEBT-REGISTER's own Wave C.2 slice 3 entry (wiki/Architecture/DEBT-REGISTER.md:166) explicitly lists code-action as one of the three ledger-writer paths that needed separate migration for a related concern (ledger→stream announcement) — proving the team already knew code-action was a structurally separate writer, just not for this concern.

**Downstream impact:** A run using (or auto-switched into, since strategy-switching is default-on for multi-step tasks per this project's own memory) the code-action strategy that delegates to a sub-agent gets a receipt/runLedger that reports the delegation call succeeded but contains none of the child's actual tool calls, artifacts, or verdicts as queryable facts — the exact 'a sub-agent's work leaves no trace in its parent' disease Wave C.2 was built to cure, reopened on one strategy. Any downstream consumer that trusts runLedger as ledger-preferred evidence (the DEBT-REGISTER's own Wave C.2 slice 3c note says analyze.ts now prefers the ledger for tool facts) will undercount or misjudge deliverables produced by a sub-agent spawned from code-action-generated code.

**Cross-tier behavior:** untested cross-tier — reproduced purely at the strategy-function level with the deterministic test provider/ToolService; no model-tier dependence in the mechanism itself (it's a pure wiring gap, not a model-behavior issue), so it should reproduce identically on any tier that ever selects code-action with delegation available.

### 2. LiteLLM provider path has zero cache-token accounting — the exact bug class the Anthropic fix (2f97ca1e) closed was never checked on this 4th provider

🟡 **Severity:** medium · **Confidence:** confirmed · **New this audit:** True

**Evidence:** packages/llm-provider/src/providers/litellm.ts: the LiteLLMRawResponse.usage type (lines 104-113) declares only prompt_tokens/completion_tokens/total_tokens/input_cost/output_cost — no prompt_tokens_details.cached_tokens field, unlike openai.ts:449/852 which does declare and read it. Both response-mapping sites (mapLiteLLMResponse lines 165-186, and the streaming path lines 487-503 and 524-527) call calculateCost(inputTokens, outputTokens, model, undefined, ...) — passing undefined as the CacheUsage argument every time. Contrast with anthropic.ts:482-493 and openai.ts:936-944 and gemini.ts:224-232, which all extract and forward a provider-specific cache breakdown into calculateCost. Confirmed no test exists either: packages/llm-provider/tests/litellm-*.test.ts (litellm-stream-tool-calls.test.ts, litellm-thinking-parity.test.ts) contain zero references to caching, versus Anthropic's dedicated red-on-cut gate packages/llm-provider/tests/cached-input-tokens-are-counted.test.ts.

**Mechanism:** packages/llm-provider/src/token-counter.ts's calculateCost (lines 204-254) subtracts each provider's cache-token count from inputTokens to get baseInputTokens, then re-adds the cached portion back at its provider-specific discounted rate (Anthropic 0.1x/1.25x, OpenAI 0.5x, Gemini 0.25x). When usage is undefined (LiteLLM's only code path), baseInputTokens = inputTokens (the FULL prompt, cached tokens included) and NO discount line fires — every token in the prompt is billed at full base-input price. Since LiteLLM is commonly used specifically to proxy Anthropic/OpenAI-family models (which DO earn cache discounts upstream), any such discount silently vanishes at this layer.

**Downstream impact:** Every cost figure reported for a run routed through .withProvider("litellm") is systematically OVERSTATED whenever the proxied backend applies a cache discount — the same class of confound as the fixed Anthropic bug ('a cache dimension silently excluded from a reported total'), but inverted in direction and unexamined until now. Any harness cost-ablation or cost-based routing decision that includes a LiteLLM arm inherits this skew silently; the DEBT-REGISTER note that 'every token-overhead number in this repository predating 2f97ca1e is unverified' (D-2026-07-28-A) did not extend the audit to LiteLLM's cost path, so this defect predates and postdates that fix without ever being checked.

**Cross-tier behavior:** untested cross-tier — this is a provider-mapping defect independent of model tier; it would fire identically regardless of which model is proxied through LiteLLM, as long as the backend applies any cache discount.

### 3. Sub-agent ledger merge on the kernel (.withReasoning()) parent path is completely untested in the actual suite — only the inline default path has a pinning test, despite the RED-ON-CUT claim implying full coverage

⚪ **Severity:** low · **Confidence:** confirmed · **New this audit:** True

**Evidence:** grep across packages/runtime/tests/subagent/*.ts and packages/reasoning/tests shows every sub-agent test (cancellation, depth-correlation, nesting-depth, inheritance-dispatch, ledger-merge, child-observability, dispatch-logging, nested-dashboard-rollup) builds its agent with no .withReasoning() call — all exercise the inline default path only. grep -rln "runLedger" ... | xargs grep -l "spawn-agent" returns exactly one file, ledger-merge.test.ts, which is inline-only. I ran a live probe (packages/runtime, using the exact scenario from ledger-merge.test.ts plus .withReasoning()) and it PASSED — both sub-agent:child-one and sub-agent:child-two passes were present with dense monotonic seq — so the kernel path mechanism is not broken, it is simply unverified by the committed suite.

**Mechanism:** The ledger-merge.test.ts docstring frames itself as 'the end-to-end pin over the whole chain' but its own agent-builder call never enables the reasoning kernel, so the RED-ON-CUT claim only covers the inline writer (inline-act.ts) and never exercises the kernel writers (tool-observe.ts / act.ts) that carry the same mechanism. This is exactly the audit-instruction risk called out for this task ('verify against the actual sub-agent execution paths, not just the test file') — here the mechanism happens to be sound, but the test suite could not have caught it if it were not, since no assertion ever ran the kernel arm.

**Downstream impact:** None currently (mechanism verified working), but a future refactor of act.ts/tool-observe.ts that silently drops the subAgentLedger attach would pass the entire committed suite green — the regression would be invisible until a live kernel-path delegation run was inspected by hand, mirroring exactly how F9/O1/F8/F2 in the RUNNING-CATALOGUE were probe artifacts caught only by manual inspection, not by CI.

**Cross-tier behavior:** not applicable — this is a test-coverage gap in a deterministic-provider harness, no model tier involved.
