# Subsystem Audit — Cross-Tier Model Behavior

**Date:** 2026-07-29. **Part of:** [[00-overview|Systems Audit — Root Cause Analysis]].

**Scope (as given to the auditing agent):**
> Cross-tier model behavior — packages/llm-provider capability/calibration system (STATIC_CAPABILITIES, capability probing, classifierReliability) vs. measured harness behavior across haiku/qwen3.5/granite4 in this session's rung2/rung3 data

## System health summary

The tier/capability machinery is real (a genuine 3-tier resolver: probed cache > static table > conservative fallback, plus a separate hand-authored calibration-file corpus), but it fights itself in two ways: (1) the one decision where model-specific tool-calling reliability actually matters — native-FC vs text-parse driver selection — reads a hardcoded provider-level flag and explicitly ignores both the static table's and the calibration files' per-model dialect signal, so months of hand-measured calibration data have zero effect on runtime behavior; (2) a terminal-gate defect that was investigated, retracted as a probe artifact, and closed out (F2) reproduces at 88 percent (22 of 25 cells) on the exact fixed instrument that retracted it, across all three tiers, meaning this project's own accuracy numbers for the kernel path were being read off a status field that lies most of the time. Every rung2/rung3 table in this session graded off disk contents instead of status for exactly this reason, which is the right workaround but leaves the underlying defect un-catalogued as live.

## Findings

### 1. Kernel terminal/synthesis gate reports FAILURE on a correct, on-disk deliverable in 22 of 25 cells across all three tiers — F2 reproduces post-fix, at much higher confidence, and was never re-filed

🔴 **Severity:** critical · **Confidence:** confirmed · **New this audit:** True

**Evidence:** wiki/Research/Harness-Reports/2026-07-28-rung2-haiku-composite.json: all 12 non-inline (kernel) cells have correct:true, wroteFile:true, and status:'failure' (terminatedBy either 'harness_synthesis' or 'controller_early_stop:dispatcher_early_stop') — 12/12. wiki/.../2026-07-28-rung3-granite4.json: 5 of 5 kernel-arm correct:true cells (no-prune r1/r3, stable-surface r1/r2/r3) show status:'failure', terminatedBy:'harness_deliverable'. wiki/.../2026-07-28-rung3-qwen35.json: 5 of 8 kernel-arm correct:true cells show status:'failure' (prune-only r1, no-prune r2/r3, stable-surface r3, prune+discover r3). Combined: 22/25 = 88%. Only the inline arm (12/12 across tiers) reliably reports status matching on-disk truth. The probe script documents this in-line: packages/benchmarks/src/disclosure-ablation.ts:183-185 ('this ablation turned up kernel arms that wrote the CORRECT file and still reported failure'). This is the identical shape as RUNNING-CATALOGUE.md's F2, marked RETRACTED on 2026-07-28 because its original n=3 probe had an unpinned, confounded tool surface. This rung2/rung3 data uses the SAME instrument built to fix that confound (identical tool surface every arm, disclosure-ablation.ts:115-128) and reproduces the defect at far higher n and consistency than the original claim ever had, on all three tested tiers. Neither RUNNING-CATALOGUE.md nor DEBT-REGISTER.md has been updated with this post-retraction data — F2 still reads RETRACTED.

**Mechanism:** The kernel's terminal/synthesis layer (guard-fired events carrying terminatedBy, and run-completed's own status field) makes its success/failure judgment from something other than the actual filesystem state of the declared deliverable — it fires on iteration-budget/dispatcher/synthesis conditions decorrelated from whether the file was actually written correctly. Every downstream consumer that reads status (gates, benches, receipts) inherits a false-negative rate around 88% on kernel-path runs that actually succeeded, which is why this project's own benchmarking scripts had to bypass the harness's own status field ('Grade on DISK, not on the model's claim about the disk', disclosure-ablation.ts:208) to get a trustworthy number.

**Cross-tier behavior:** This is the opposite of tier-adaptive: it fires almost identically hard on frontier (haiku, 12/12 = 100%) and on the weakest local model tested (granite4, 5/5 = 100%), with qwen3.5 only slightly better (5/8 = 62.5%). A defect this uniform across a 4.5B-to-frontier span means the terminal-gate logic is not reading anything that varies with model quality — it is a structural bug in how the gate is wired, not a model-capability gap, and it is exactly why 'kernel arms fail more on weak models' claims elsewhere in this project's history must be re-audited against correct/wroteFile, not status, before being trusted.

### 2. qwen3.5's pruned-arm llm_error crashes are diagnosed: Ollama's own chat-template tool-call parser throws on malformed intermediate XML tags — not a harness tool-list bug, and not exclusive to pruning

🟠 **Severity:** high · **Confidence:** confirmed · **New this audit:** True

**Evidence:** Live reproduction this session (ollama qwen3.5:latest, 2/2 runs against prune-only and prune+discover): stack trace 'LLMError: ollama request failed: XML syntax error on line 4: element <function> closed by </parameter>' at packages/llm-provider/src/providers/local.ts:872 -> provider-error.ts:190 -> think.ts:754/830 sets terminatedBy:'llm_error'. Both runs died at iteration 0, 0 tokens billed, before any tool executed. This is the exact mechanism wiki/Research/Harness-Reports/2026-07-28-corrected-composite-rebaseline.md section 3 flagged and explicitly declined to attribute ('A pruned tool array may be producing a request Ollama rejects. That is an instrument hypothesis and it has not been tested'). The recorded rung3 data (2026-07-28-rung3-qwen35.json) shows 4 of 6 pruned-arm cells dying this way (tools=[] or [file-read] only, 1-3 LLM calls, 1 iteration) plus 1 of 9 non-pruned cells (no-prune r3) hitting the identical terminatedBy — the failure is not exclusive to pruned arms, only much more frequent there in the recorded sample.

**Mechanism:** qwen3.5:latest under Ollama does not have first-class structured tool-calling — Ollama's server translates the model's own chat-template output (Hermes-style <function>...</parameter> tag markup for this GGUF build) into the API's structured tool_calls, and that translation has zero tolerance: any malformed closing tag from the model's own probabilistic generation aborts the whole HTTP request with a hard error, at 0 tokens billed and with no retry or partial-recovery path anywhere in the kernel (think.ts:747-757 and :818-833 both go straight to status:'failed', terminatedBy:'llm_error' on any stream-init or stream-consume error). This is model-generation noise amplified into a total-run failure by a parser with no slack, not a tool-surface-churn bug as originally hypothesized.

**Cross-tier behavior:** Reproduces only on the local tier's Ollama-served models with fragile chat-template tool-call grammars — haiku (Anthropic native FC, no chat-template translation layer) shows zero llm_error cells anywhere in rung2 (0/15), and granite4 shows zero llm_error cells in rung3 (0/15) despite failing just as often on the same task via a completely different mechanism (see next finding) — so 'the local tier is fragile under tool-list churn' as a single story is wrong; it is two unrelated local-tier failure modes that happen to co-occur in the same bench, one a provider/template-parsing crash (qwen3.5) and one a silent tool-starvation (granite4).

### 3. Granite4's pruning-arm deliverable failures have a confirmed tool-level signature: file-write is never called in any of the 6 pruned-arm cells, only in non-pruned arms — extends the filed lead with the missing mechanism

🟠 **Severity:** high · **Confidence:** likely · **New this audit:** True

**Evidence:** wiki/Research/Harness-Reports/2026-07-28-rung3-granite4.json: all 6 pruned-arm cells (prune+discover x3, prune-only x3) show tools lists of exactly [file-read, code-execute, (list-directory|final-answer)] — file-write never appears, and wroteFile:false in all 6. All non-pruned cells that reach completion call file-write (no-prune r1/r3, stable-surface all 3, inline r1) and wroteFile:true matches tools containing file-write in every case — internally consistent, so the trace tooling is not silently dropping tool-call records. The existing filed lead (2026-07-28-corrected-composite-rebaseline.md section 3, and 09-UNIFIED-PROGRAM.md's 'pruning correlates with deliverable failure, p approx 3.2e-4') recorded only wroteFile/correct, not which tool the model actually attempted — this is the missing mechanistic layer.

**Mechanism:** Under lazy disclosure, granite4 apparently never regains visibility of file-write for this task once it is pruned out of the per-turn allow-set — it substitutes list-directory or terminates via final-answer instead, and never calls the recorded-as-available discover-tools escape hatch either (discoverCalls:0 on every cell in all three raw JSON files, all tiers). The per-turn trace files that would show the exact tool schema offered at the failing turn were deleted by the probe's own cleanup (disclosure-ablation.ts:220-221) before this audit ran, so I cannot directly confirm file-write was absent from the wire payload rather than present-but-ignored by the model — flagged 'likely' rather than 'confirmed' for that reason — but the 0/6 vs 9/9 tool-call pattern is a much stronger signal than the wroteFile-only correlation already on file.

**Downstream impact:** If the mechanism is allow-set starvation (the more likely reading given granite4 never recovers the tool across 5-14 iterations of budget), the disclosure heuristic's tool-relevance decision is being made in a way this model can never escape from — the mirror-image of F9 (kernel silently widening the surface): here the surface may be silently narrowing past the point of task-completability for weaker local instruction-followers, with no symmetric safety net.

**Cross-tier behavior:** Zero reproduction on haiku (all 12 pruned-arm haiku cells call file-write and reach correct:true) and a different, non-overlapping mechanism on qwen3.5 (provider-level crash, not tool starvation) — the two local models fail the same bench for two structurally different reasons, both invisible on frontier, which argues against a single 'small models can't handle churning tool arrays' story and for treating disclosure pruning as tier-conditional at minimum.

### 4. The tool-calling driver decision (native-FC vs text-parse) discards the model-specific calibration/capability dialect signal entirely — decided by a parameter that is never read, plus a provider-level flag hardcoded true for every Ollama model

🟠 **Severity:** high · **Confidence:** confirmed · **New this audit:** True

**Evidence:** packages/tools/src/drivers/select-driver.ts:36-42 — selectToolCallingDriver(_dialect, supportsToolCalling = true) names its first parameter with the underscore convention for 'intentionally unused', and its body is exactly: if supportsToolCalling===false return TextParseDriver, else return NativeFCDriver. The dialect argument, which is effectiveInput.calibration?.toolCallDialect (packages/reasoning/src/kernel/loop/runner.ts:258-261), never participates in the branch. supportsToolCalling for Ollama is hardcoded true at every call site: packages/llm-provider/src/providers/local.ts:529, :681, :1074 — no per-model branching exists. runner.ts:195-200's own comment documents this as a deliberate post-482c11e4 redesign ('Capability is the single master signal'), not an oversight.

**Mechanism:** Because supportsToolCalling can never be false for an Ollama-routed model, every Ollama model — regardless of what its STATIC_CAPABILITIES entry or its calibration file says about toolCallDialect — gets NativeFCDriver unconditionally, and the kernel always attaches the raw tools: schema on the wire (think.ts:719, gated only on toolCallingDriver.mode !== 'text-parse', a mode this path can never reach for Ollama). This is the exact channel through which qwen3.5:latest's fragile server-side tool-call-template translation (previous finding) gets exercised every kernel turn with no calibration-driven off-ramp, even though sibling models in this same family (qwen3:14b, qwen3:4b) have hand-measured calibration data explicitly recording toolCallDialect:'none' for themselves.

**Downstream impact:** Renders the entire STATIC_CAPABILITIES.toolCallDialect field and the calibration-file toolCallDialect field inert for the one decision (wire-level native-FC vs text-parse) they were designed to drive; the only two remaining live consumers are cosmetic (tool-schemas.ts:159, final-answer description text) and strategy-scoped (blueprint.ts:129, worker-concurrency cap in the blueprint strategy only, not the reactive strategy used in every rung2/rung3 cell this session). Any future recalibration effort aimed at fixing qwen3.5's dialect entry would have zero runtime effect until this dead branch is reconnected.

**Cross-tier behavior:** A real tier/provider split the codebase does NOT adapt on when it structurally could: Anthropic/OpenAI go through a genuinely native, schema-validated tool-call channel with no server-side template translation, so driver choice is moot for them; Ollama-served models funnel through a translation layer of unknown, unmeasured per-model reliability, and the harness treats all of them identically (always native-FC) rather than using the calibration data it already collected — and disagrees with itself about — to route the unreliable ones through TextParseDriver as a safety valve.

### 5. The calibration-file corpus and STATIC_CAPABILITIES directly contradict each other on toolCallDialect for the same models, is 2-3 months stale, and has zero coverage for either model this session's cross-tier benches actually used

🟡 **Severity:** medium · **Confidence:** confirmed · **New this audit:** True

**Evidence:** packages/llm-provider/src/calibrations/qwen3-14b.json:11, qwen3-4b.json:11, cogito-14b.json:11 all record toolCallDialect:'none' (calibratedAt 2026-05-07 / 2026-05-24 / 2026-05-07). packages/llm-provider/src/capability.ts's STATIC_CAPABILITIES entries for the identical three models ('ollama/qwen3:14b' ~L482-494, 'ollama/qwen3:4b' ~L502-514, 'ollama/cogito:14b' ~L467-479) all record toolCallDialect:'native-fc' — a direct, unreconciled contradiction on the same field for the same model between two sources the codebase actually loads (calibration.ts:112-131 precedence chain; capability-resolver.ts:163). Across the entire STATIC_CAPABILITIES table, every entry uses 'native-fc' and the literal string 'text-parse' is used zero times, for any provider — a schema value that exists (capability.ts:48) but is apparently never assigned. Separately, packages/llm-provider/src/calibrations/llama3.2-3b.json and llama3.2-latest.json carry byte-identical calibratedAt timestamps (2026-04-14T20:48:22.490Z) and identical field values for two different model tags — evidence of copy-paste rather than independent per-model measurement. Neither qwen3.5:latest nor granite4:tiny-h/latest (the models used in wiki/Research/Harness-Reports/2026-07-28-rung3-{qwen35,granite4}.json, this session's own cross-tier data) has a STATIC_CAPABILITIES entry or a calibrations/*.json file at all — confirmed by direct grep, zero hits for either model in capability.ts or the calibrations/ directory.

**Mechanism:** The live /api/show probe (packages/llm-provider/src/providers/local-probe.ts:106: toolCallDialect: caps.has('tools') ? 'native-fc' : 'none') derives dialect from a structural boolean (does Ollama's metadata declare a tools capability flag for this model) rather than from any behavioral measurement of tool-call reliability, so even the live-calibrated path for qwen3.5/granite4 could only ever produce 'native-fc' (Ollama declares tools support for both) and would never surface the fragility this audit reproduced live. Combined with the previous finding: no calibration exists for the models actually in current use, the calibration that does exist for close relatives contradicts the static table with no reconciliation logic visible anywhere in the resolution chain, and neither would matter anyway because the dialect signal is discarded at the point of driver selection.

**Cross-tier behavior:** This answers the audit's central question directly: STATIC_CAPABILITIES/dialect data is NOT calibrated against real measured behavior for the models this project is currently benchmarking — it is either absent (qwen3.5, granite4), stale and internally contradictory (qwen3-family, 2-3 months old, disagreeing with itself), or structurally incapable of detecting the failure mode that matters (the live probe reads a capability flag, not a reliability rate). The framework has real per-tier infrastructure (a genuine 3-source resolver, a calibration-runner, a probe) but none of it currently reflects, or could currently detect, the concrete cross-tier divergence this session's own rung2/rung3 data records.
