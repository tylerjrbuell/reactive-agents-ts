# Subsystem Audit — Tool Exposure & Surface Control

**Date:** 2026-07-29. **Part of:** [[00-overview|Systems Audit — Root Cause Analysis]].

**Scope (as given to the auditing agent):**
> Tool Exposure & Surface Control (lazy disclosure, tool-relevance classifier, discover-tools, builtins floor, forbidden/allowed lists, tool-surface.ts resolver)

## System health summary

The tool-surface RESOLVER itself (tool-surface.ts) is coherent: floors, deny-lists, and the never-prune-to-meta-only guard compose in a well-documented, deliberately-ordered pipeline, and `hasClassification` is correctly keyed off non-empty classifier OUTPUT (think.ts:316) rather than 'was it attempted', which closes off a plausible worse-than-unclassified trap I checked for and did not find. The system is fighting itself one layer up, though: the builder's config-assembly layer (contract-tool-set.ts) reintroduces the exact default-on classifier behavior that commit 228bf10e/60730287 and RUNNING-CATALOGUE F6 declare fixed, for the overwhelmingly common `.withReasoning()+.withTools()` builder pattern with no explicit `.withRequiredTools()` call — and a same-named-but-unrelated `adaptive` field on `ToolsOptions` gives callers false confidence they opted out when they did not. This is the fifth instance this session of an arm-comparison silently varying more than its stated axis, this time sitting underneath figures (F7's '+168%', F9's regression test, F10's cache-churn harness) the catalogue currently treats as settled rather than retracted.

## Findings

### 1. The F6 classifier opt-in fix is silently defeated for the common builder pattern — `mergeContractRequiredTools` re-defaults `requiredTools` to `{adaptive:true}`

🔴 **Severity:** critical · **Confidence:** confirmed · **New this audit:** True

**Evidence:** packages/runtime/src/builder/contract-tool-set.ts:127-132 — `mergeContractRequiredTools`: `if (contractRequired.length === 0) return priorConfig ?? (reasoningEnabled && toolsEnabled ? { adaptive: true } : undefined);`. Called at packages/runtime/src/builder/build-effect/runtime-construction.ts:471-476 with `state._requiredToolsConfig` as `priorConfig` — which is `undefined` unless the caller explicitly calls `.withRequiredTools()` or `.withTools({required:...})` (confirmed: `_requiredToolsConfig` is written ONLY in packages/runtime/src/builder/withers/tools.ts's `mergeRequiredToolsConfig`, never as a side effect of `.withReasoning()` or plain `.withTools({builtins, ...})`). Downstream, packages/runtime/src/engine/phases/agent-loop/setup/classifier.ts:117-127 computes `wantsClassification = (config.requiredTools?.adaptive === true && !hasStaticRequiredList) || config.adaptiveToolFiltering === true` and gates the LLM classifier call on it. An EXISTING repo test pins this exact default as intentional: packages/runtime/src/__tests__/contract-required-tools-execute.test.ts:105-108 — `mergeContractRequiredTools(undefined, undefined, true, true)` asserts `toEqual({ adaptive: true })`. I additionally reproduced this live (probe, deleted after use, not committed): built two agents through the real `.build()`/`.run()` path (not the cosmetic `toConfig()` export, which does NOT reflect this default and which I initially mis-probed with — an instrument trap I caught before reporting) with `.withProvider('test').withTools({builtins:true, adaptive:false}).withReasoning({defaultStrategy:'reactive'})` (disclosure-ablation.ts's exact pattern, no `.withRequiredTools()` call): trace showed 2 extra `purpose:'extract'` LLM exchanges (the classifier call, retried once after the test provider's canned reply failed to parse as the classifier's structured JSON) before the `think` exchange. The same builder chain with an added `.withRequiredTools({adaptive:false})` produced 0 extra exchanges — only `think`.

**Mechanism:** `.withReasoning()` sets `_enableReasoning=true`; any `.withTools(...)` call (even just to opt into builtins) sets `_enableTools=true`. Neither touches `_requiredToolsConfig`. At build time `mergeContractRequiredTools(undefined /*priorConfig*/, undefined /*contract*/, true, true)` hits the `contractRequired.length === 0` branch and returns `{ adaptive: true }` — the 'prior inline default semantics' the code comment says it deliberately preserves. This flows straight into `config.requiredTools.adaptive`, which is exactly the flag `wantsClassification` checks. So the classifier is default-ON again for any `.withReasoning()+.withTools()` agent that does not ALSO make an explicit `.withRequiredTools()` call — which none of the four disclosure-ablation.ts reasoning arms, none of abstention-cost.ts's `kernel`/`kernel+tools` arms, and the pinned `discover-tools-respects-surface.test.ts` regression test do. classifier.ts's own header comment claims 'OPT-IN as of 2026-07-28 (228bf10e, 60730287)' and RUNNING-CATALOGUE F6 records it as 'flipped to opt-in' — both are true only for callers who never touch `.withReasoning()+.withTools()` without an explicit `.withRequiredTools()`, which is not how any of this session's own benchmark scripts are written.

**Downstream impact:** Every cross-arm cost/token comparison in this session that builds a reasoning-enabled agent via `.withTools({...})` without an explicit `.withRequiredTools()` call is silently paying 1-2 uncontrolled classify() round trips on the kernel side only (classifyTools is wired into pre-loop-dispatch.ts, part of the reasoning agent-loop setup the inline path never traverses) — inflating every 'kernel tax' / 'residual overhead' number by an amount the catalogue believes was eliminated. Concretely: abstention-cost.ts's `kernel+tools` arm (line ~151-158, no `.withRequiredTools()` call) produced F7's currently-standing 'matched surface, +168% residual overhead' figure; disclosure-ablation.ts's 4 reasoning arms (kernel/prune-only/no-prune/stable-surface, none call `.withRequiredTools()`) are the harness underneath F9's fix-verification and F10's 'highest open item' cache-churn analysis. F10 in particular is at risk twice over: the classify() call is an extra, unaccounted harness LLM exchange stacked onto every reasoning arm's token/cost total, AND classifier output (when non-empty) is documented (F6) to feed the lazy-disclosure allow-set that determines the very tools-array prefix F10's cache-churn story is about — so whether classify silently fires or not can change which code path populates that allow-set from run to run without any arm boundary in the ablation accounting for it.

**Cross-tier behavior:** Untested cross-tier for cost magnitude (my reproduction used the deterministic test provider to prove the mechanism cheaply, per the project's probe-placement rules) — but the mechanism itself is calibration-gated the same way F6 measured it: `classifierReliability !== 'low' && !== 'skip'` must hold for `needsClassification` to fire, and no per-model calibration table currently sets `classifierReliability` for haiku or qwen3.5 (grepped `packages/llm-provider/src/calibration.ts` and all classifierReliability readers/writers — only the schema declares the field, no model table populates it), so it defaults to undefined, which passes both checks on both tiers identically. F6's own cross-tier ablation showed the classifier's overhead sign and magnitude were tier-independent (+25%..+167% on both haiku-4.5 and qwen3.5-9b), so this defeat-of-opt-in should reproduce on both tiers by the same evidence already in the catalogue.

### 2. `ToolsOptions.adaptive` (lazy-disclosure heuristic toggle) and `RequiredToolsOptions.adaptive` (classifier toggle) are two unrelated fields sharing the name 'adaptive' — `.withTools({adaptive:false})` cannot suppress the classifier default from Finding 1

🟠 **Severity:** high · **Confidence:** confirmed · **New this audit:** True

**Evidence:** packages/runtime/src/builder/types.ts:150-165 — `ToolsOptions.adaptive` ('Enable adaptive tool filtering... Default: false'), written to builder state `_toolsOptions.adaptive` via `applyWithTools` (packages/runtime/src/builder/withers/tools.ts:63-74) and surfaced as `config.adaptiveToolFiltering` (runtime-construction.ts: `adaptiveToolFiltering: state._toolsOptions?.adaptive`). Versus packages/runtime/src/builder/types.ts:271-278 — `RequiredToolsOptions.adaptive` ('Enable adaptive LLM inference of required tools'), written to the SEPARATE `_requiredToolsConfig.adaptive` slot only via `.withRequiredTools()` or `.withTools({required:{adaptive}})` (note: nested under `required`, not the top-level `adaptive` key). classifier.ts:120-122 ORs both: `(config.requiredTools?.adaptive === true && !hasStaticRequiredList) || config.adaptiveToolFiltering === true`. The doc for `RequiredToolsOptions.adaptive`'s parent field even states the honest default at types.ts:260-261 ('adaptive classification follows the reasoning-enabled default') but this sentence sits under `ToolsOptions.required`'s doc block, physically separated from `ToolsOptions.adaptive`'s doc block (150-165) that a caller reads when trying `.withTools({adaptive:false})`.

**Mechanism:** `.withTools({builtins:true, adaptive:false})` — the exact call signature used in disclosure-ablation.ts, abstention-cost.ts's `kernel+tools`/`inline+tools` arms, and the pinned regression test discover-tools-respects-surface.test.ts:62 — sets ONLY `_toolsOptions.adaptive = false` (→ `config.adaptiveToolFiltering = false`), which zeroes out just the second disjunct of `wantsClassification`. It does nothing to `_requiredToolsConfig`, so the first disjunct — `config.requiredTools?.adaptive === true` — is untouched and, per Finding 1, defaults to `true` anyway whenever reasoning+tools are both on and `.withRequiredTools()` was never called. A caller who reads `ToolsOptions.adaptive`'s doc in isolation ('Default: false (all tools shown)') has every reason to believe `adaptive:false` is a complete, no-classifier configuration; it silently is not.

**Downstream impact:** This is the specific mechanism that let every affected benchmark script in this session believe it had pinned out adaptive classification when it had only pinned out the unrelated lazy-disclosure heuristic — directly answering the audit's question ('do `adaptive:false` on `.withTools()` and `contract-tool-set.ts`'s default talk to each other') with: no, they are two different state slots with the same name, and none of this session's ablation harnesses controlled for the one that actually gates the classifier.

**Cross-tier behavior:** Untested cross-tier; this is a builder/config-wiring defect independent of model tier — it fires identically regardless of which provider or model consumes the resulting config.

### 3. F7's currently-standing '+168% matched-surface' figure and F9/F10's own verification harnesses are themselves running under the unaccounted classifier confound

🟠 **Severity:** high · **Confidence:** likely · **New this audit:** True

**Evidence:** packages/benchmarks/src/abstention-cost.ts lines ~150-158 (`kernel+tools`) and ~130-136 (`kernel`): both call `.withTools({builtins:[...], adaptive:false}).withReasoning({defaultStrategy:'reactive'})` with no `.withRequiredTools()` call, while the `kernel+required` arm (lines ~163-169) DOES call `.withRequiredTools({tools:['web-search']})` and is therefore correctly protected (a non-empty static list sets `hasStaticRequiredList=true`, which suppresses the classifier per classifier.ts:117-121, independent of Finding 1). `inline+tools` never reaches classifyTools at all — it is called only from packages/runtime/src/engine/phases/agent-loop/setup/pre-loop-dispatch.ts:135, part of the reasoning agent-loop setup phase the `_enableReasoning=false` inline path does not traverse. RUNNING-CATALOGUE F7's retraction (wiki/Failure-Modes/RUNNING-CATALOGUE.md, F7 section) reports the corrected 'matched surface' numbers as `inline+tools 2,244t / kernel+tools 6,020t`, i.e. +168%, presented as the residual, accounted-for kernel tax after fixing the earlier tool-surface confound. Separately, packages/runtime/tests/discover-tools-respects-surface.test.ts:62-63 (F9's own pinned regression test) uses the identical `withTools({...adaptive:false}).withReasoning(...)` pattern with no `.withRequiredTools()` call, and packages/benchmarks/src/disclosure-ablation.ts:125-134 (the harness underneath F9's fix-verification and F10's cache-churn diagnosis) does the same across all 4 of its reasoning-enabled arms.

**Mechanism:** Per Finding 1, each of these `kernel*` arms silently resolves `config.requiredTools={adaptive:true}` and fires the classifier — an LLM round trip `inline`/`inline+tools` structurally cannot incur — so the 'matched surface' claim in F7's retraction is not actually matched: `kernel+tools` pays for the tool surface AND an undisclosed classify() call that its `inline+tools` control never runs. This is the same failure shape as the O1/F8/F2/F9 retractions already logged in this session's own catalogue (arm comparisons that silently vary more than the one axis under test) — a fifth instance of the identical class, this time embedded in what the catalogue currently treats as the corrected, settled number rather than a retracted one.

**Downstream impact:** F7's '+168%, ordinary iteration overhead, not specific to abstention' conclusion needs re-measurement with the classifier genuinely pinned off (via `.withRequiredTools({adaptive:false})`, not `.withTools({adaptive:false})`) before it can be trusted as a clean number; the true kernel-loop-only tax is smaller than +168%. F9's regression test still correctly proves its own claim (tool-capability containment, not cost) so this doesn't reopen F9's verdict, but it means the CI-pinned suite is quietly spending an extra harness LLM call on every run. F10 — explicitly the catalogue's 'highest open item' with 'no accuracy risk' — is the most exposed: its entire measurement harness (disclosure-ablation.ts) runs every reasoning arm through this same unaccounted classify() call, on a metric (prompt-prefix cache stability) that classifier output has already been shown (F6) to influence via the lazy-disclosure allow-set.

**Cross-tier behavior:** untested cross-tier — the mechanism was traced statically plus reproduced on the test provider; no live haiku/qwen3.5 re-run was performed in this audit to quantify the exact pp of confound in F7's +168% figure.
