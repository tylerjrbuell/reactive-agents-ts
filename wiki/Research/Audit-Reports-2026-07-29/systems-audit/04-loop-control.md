# Subsystem Audit — Loop Control & Termination

**Date:** 2026-07-29. **Part of:** [[00-overview|Systems Audit — Root Cause Analysis]].

**Scope (as given to the auditing agent):**
> Loop Control & Termination — packages/reasoning/src/kernel/loop/ (runner.ts, react-kernel.ts, terminate.ts), arbitrator.ts, low_delta_guard, strategy-switching, and the 8 registered strategies

## System health summary

The kernel-internal termination machinery (terminate.ts as single caller of transitionState for status:done/failed, the PostCondition spine) is genuinely well-wired and does route through one owner *within a single ReAct kernel instance* — confirmed only react-kernel.ts/runner.ts import terminate.ts. But the 'single terminal owner' claim does not extend to the 7 non-reactive strategies' outer loops (plan-execute's allStepsCompleted, ToT/reflexion/adaptive's own exit checks are strategy-bespoke and never call terminate.ts directly), so the real cross-strategy success authority for declared deliverables lives one layer up, in the receipt-assembly boundary (computeDeliverableReport / goalAchieved in packages/runtime/src/builder/helpers.ts). That boundary trusts the SAME ledger-and-steps evidence terminate.ts trusts, and for plan-execute's direct tool_call steps that evidence is provably wrong in the false-met direction on at least one concrete, code-traced path (pre-heal path arguments vs. the healing pipeline's post-heal remap). This is the same shape of bug the framework has fixed four times already this cycle (F1, F2-original, the Wave C.2 delegated-deliverable fix, F8) — a state-grounded gate trusting evidence that was captured at the wrong point in the pipeline — landing on a fifth site that DEBT-REGISTER D-2026-07-28-D had scoped as replay-only. Separately, the arbitrator's steering-veto fix (65457ac7) is real and live in code but exactly as unpinned as its own commit message says, and a second gap it explicitly flagged was never carried into any tracked register.

## Findings

### 1. D-2026-07-28-D's pre/post-heal argsHash divergence is not replay-only: it reaches the real terminal PostCondition gate and the receipt's goalAchieved decision for plan-execute tool_call steps

🟠 **Severity:** high · **Confidence:** confirmed · **New this audit:** True

**Evidence:** packages/reasoning/src/strategies/plan-execute/step-executor.ts:237-238,348-355 stores PRE-heal `resolvedArgs` in the ledgerSteps action step's `metadata.toolCall.arguments`. packages/reasoning/src/kernel/capabilities/act/tool-observe.ts:268-293 heals internally for the real dispatch (reassigning `args` to the healed value) but the healed value only reaches `recordToolDispatch` (tool-observe.ts:548-557 -> kernel/ledger/emit.ts:41-55), which mints ONLY `tool-invocation`/`tool-result` -- never `kind:"artifact"`. `deriveArtifactEntries` (kernel/ledger/artifact-projection.ts:46-93) is the only artifact-minting path in the repo (grep-confirmed sole caller: act.ts:1155), so plan-execute's direct tool_call dispatch never produces an `artifact` ledger entry at all. `isArtifactProduced` (kernel/capabilities/verify/post-conditions.ts:257-329) therefore falls through its ledger-artifact-entries check (empty) to the steps-scan fallback at :279-303, which reads the PRE-heal path off `step.metadata.toolCall.arguments`. The healing pipeline (packages/tools/src/healing/path-resolver.ts:50-56, "Hallucinated absolute path -> remap filename to working dir") can change trailing path segments between the declared and actually-written location -- exactly the case `writtenPathSatisfies`'s suffix match cannot see through when it's comparing the wrong (pre-heal) string. This gate is called by name from `terminate.ts:106-165` (`applyTerminalPostConditionGate`, the documented single-owner terminal authority) via `state.ledger`/`state.steps`, and by `kernel/contract/deliverable-report.ts:52-65` (`computeDeliverableReport`), whose output directly flips `goalAchieved` in `packages/runtime/src/builder/helpers.ts:100-104` (`if (deliverables.some(d => !d.produced)) return false`). plan-execute.ts:931-938's own comment claims this ledger pair is "the ONLY shape isArtifactProduced's linkage scan can verify, so deliverable receipts tell the truth for plan-execute runs" -- an assumption this trace shows is false specifically because the stored args are pre-heal.

**Mechanism:** Two independent things both read `metadata.toolCall.arguments` off the plan-execute ledger action step and both assume it names the location the file was ACTUALLY written to: (1) `isArtifactProduced`'s no-ledger-artifact-entry fallback, and (2) nothing else -- there is no artifact entry to prefer instead for this dispatch path, unlike the reactive kernel (act.ts) where `toolCall.arguments` in the ledger IS post-heal (act.ts:345-346 assigns `tc = healResult.succeeded ? healResult.call : rawTc` BEFORE building every action step, e.g. act.ts:385). step-executor.ts never re-heals its own stored copy after calling executeToolAndObserve with `heal:{...}`. So when the healing pipeline's path-remap fires (a plan step's declared/hallucinated path resolves outside the sandbox root and gets rewritten to `resolve(workingDir, basename(path))`), the real write lands at a different trailing path than the one the ledger records, and post-conditions.ts's own no-false-met design (its DBC/docstring explicitly names false-met as the dangerous direction it exists to prevent) is defeated for this one dispatch shape.

**Downstream impact:** Directly reaches: (a) terminate.ts's terminal PostCondition hard-stop -- the mechanism built specifically to stop a stall/oracle/harness-deliverable exit from reporting false success (the cogito GitHub-MCP precedent the module's docstring cites); (b) the user-facing receipt's `goalAchieved` field via computeDeliverableReport, a single boundary shared by all 8 strategies. A plan-execute run whose planner emits (or the model hallucinates) a path outside the sandbox root for a `tool_call` step can be reported as having produced a declared deliverable it did not produce at the declared location -- the exact false-success class this framework has fixed four times this cycle (F1, the pre-second-retraction F2, the Wave C.2 delegated-deliverable close-out, and F8's inverse). It also means D-2026-07-28-D's own framing ("latent correctness bug in the replay/observability boundary, not in the kernel itself" / "discharge: reconcile in replay-agent.ts (or store post-heal args in step-executor.ts)") under-scopes the fix: storing post-heal args in step-executor.ts is not an optional replay-lane nicety, it is required for the live terminal/receipt gate to be sound on this strategy.

**Cross-tier behavior:** untested cross-tier -- this is a structural/code-path defect independent of model tier (the healing remap branch fires on any hallucinated or out-of-sandbox path regardless of which model produced it); no live-model reproduction was run in this audit, the finding is grounded in a full static trace across 9 files plus the DEBT-REGISTER's own confirmed 3/3 divergence on `planned-tool-loop` (packages/benchmarks/tests/replay-lane.test.ts, cited in D-2026-07-28-D) which already proves the args genuinely diverge in real runs, just not yet connected to the false-met consequence traced here.

### 2. The arbitrator's system-steering veto fix (65457ac7) has no unit test covering its actual carve-out, and the commit's own stated follow-up gap was never filed anywhere

🟡 **Severity:** medium · **Confidence:** confirmed · **New this audit:** True

**Evidence:** Commit 65457ac7's message states verbatim: "The veto fix is verified by live probe only -- a unit pin is OUTSTANDING... Two fixture attempts had `arbitrate` return \"escalate\" before the veto branch was reached... a naive fixture tests the escalation path and never exercises the failure-evidence filter at all." Current code still carries the fix at packages/reasoning/src/kernel/capabilities/decide/arbitrator.ts:891 (`if (toolName === "system") return false;`). The only test file referencing `shouldVetoSuccess`/veto behavior, packages/reasoning/src/kernel/control/from-arbitration.test.ts:105-115, has exactly one veto-path case and it uses `failedObs("web-search", "connection refused")` -- a genuine non-meta tool failure, not `toolName: "system"` -- so it pins the OPPOSITE case (veto should still fire on real tool failure) and does not exercise the carve-out this commit added. `git log` since 65457ac7 (11 subsequent commits through the current HEAD) shows no follow-up test commit touching this. Additionally, the same commit message states a second, unresolved fact as a known gap: "`status` is still `failure` on those runs... the arbitrator no longer vetoes, so the remaining failure comes from a second source downstream that I have not isolated." Grepping wiki/Failure-Modes/RUNNING-CATALOGUE.md, wiki/Architecture/DEBT-REGISTER.md, and wiki/Architecture/Specs/09-UNIFIED-PROGRAM.md for `controller_signal_veto`, "second source", "65457ac7", or "F3 wave" returns zero hits in all three canonical trackers.

**Mechanism:** The fix is a targeted carve-out (`toolName==="system"` short-circuits `shouldVetoSuccess`'s failure scan) added to stop the harness's own steering-nudge observations from being misread as a real tool failure. Because the two fixture attempts described in the commit message hit `arbitrate`'s escalate branch before reaching the veto branch, whoever wrote the fix could not construct a red-on-cut unit case and shipped on live-probe evidence alone -- and no one has since gone back to build the fixture context (a controller-decision-log + steps shape that specifically reaches the `controller-early-stop` veto branch with a `toolName:"system"` failed observation) needed to pin it.

**Downstream impact:** A refactor of `shouldVetoSuccess`, `META_TOOLS`, or the harness's steering-injection observation shape (e.g. renaming the synthetic tool name away from `"system"`) can silently reopen this exact defect (the harness's own nudges counted as tool failure, flipping healthy runs to `status:failure`/`controller_signal_veto`) with no test to catch it. Separately, the unisolated "second source" of downstream failure-status is a loose thread from a session that otherwise had rigorous tracking discipline (RUNNING-CATALOGUE, DEBT-REGISTER) -- it fell through because it was stated only in a commit message, not filed as a register row, so it cannot currently be distinguished from a fixed or an abandoned line of investigation by anyone reading the canonical trackers.

**Cross-tier behavior:** untested cross-tier -- the original fix was measured only on haiku (per the commit message's own trace); no evidence either way for local-tier models, and the gap (no unit pin) is model-independent since it is a test-coverage absence, not a behavioral one.

### 3. terminate.ts's 'single terminal owner' claim holds only inside one ReAct kernel instance; none of the 7 non-reactive strategies call it, so their outer-loop stop decisions and the state-grounded PostCondition hard-stop are structurally decoupled

🟡 **Severity:** medium · **Confidence:** confirmed · **New this audit:** False

**Evidence:** `grep -rln "from.*loop/terminate\|import.*terminate" packages/reasoning/src/strategies packages/reasoning/src/kernel/loop/react-kernel.ts packages/reasoning/src/kernel/loop/runner.ts` returns only `react-kernel.ts` and `runner.ts` -- zero strategy files import `terminate.ts`. Strategy registry (packages/reasoning/src/services/strategy-registry.ts:155-167) lists 8 strategies: reactive, reflexion, plan-execute-reflect, tree-of-thought, adaptive, direct, code-action, blueprint. Each of the 7 non-reactive strategies either has its own outer exit condition (e.g. plan-execute.ts:1041 `allStepsCompleted`) or calls `executeReActKernel` per-step/per-branch for composite work, where `state.meta.postConditions` is derived once at task-level and is typically empty for a narrow per-step task string (terminate.ts:136-137 short-circuits to pass-through when `!conditions || conditions.length===0`). The one place a deliverable check gets enforced for these strategies afterward is `computeDeliverableReport` (kernel/contract/deliverable-report.ts), called from exactly one non-test site, `packages/runtime/src/builder/helpers.ts`, which derives `goalAchieved` (helpers.ts:100-104) -- a receipt-assembly-time decision, structurally separate from `terminate.ts`'s `status:"done"/"failed"` transition.

**Mechanism:** terminate.ts genuinely IS the sole caller of `transitionState({status:"done"|...})` inside the kernel loop -- that invariant is real and CI-enforced (per wiki/Architecture/Specs/06-AUDIT-v0.10.0.md's `check-termination-paths.sh`, 9 paths / 2 authorized callers). But 'terminal owner for the kernel's own status field' and 'terminal owner for whether the declared deliverable actually got produced' are two different claims, and only the first is unified across strategies. The second is enforced by the PostCondition spine only when the terminating kernel instance itself carries a non-empty `postConditions` set derived from the FULL task -- true for `reactive` (task-level ReAct loop) but generally not true for a plan-execute composite step's narrow sub-kernel, whose conditions are typically unset. So for 7 of 8 strategies, deliverable-honesty enforcement migrates entirely to the post-hoc, receipt-only `computeDeliverableReport`/`goalAchieved` path -- which Finding #1 shows can itself be fed wrong evidence for plan-execute's tool_call steps.

**Downstream impact:** This is the structural reason Finding #1 exists at the terminal-authority layer rather than being caught by the kernel's own post-condition hard-stop for plan-execute: the sub-kernel that dispatches a plan-execute tool_call step never runs a deliverable check on itself (no conditions to check), so the ONLY backstop is the receipt-time report -- and that report's evidence source (steps[], since no artifact entry exists for this dispatch shape) is exactly what Finding #1 shows can be stale/wrong. A future strategy or a change to how composite steps derive their own `postConditions` could either double-enforce (harmless) or continue to rely solely on the receipt-layer check (status quo, fragile) with no single place documenting which strategies get kernel-level enforcement vs. receipt-only enforcement.

**Cross-tier behavior:** untested cross-tier -- this is a control-flow/architecture observation independent of model behavior; it manifests identically regardless of which model is driving the strategy.
