# v0.19.0 release retro (2026-11-19)

v0.19.0 shipped on 2026-11-20 (UTC): 35 public packages on npm at 0.19.0, tag `v0.19.0` at `772a9d2af`, GitHub release written by hand. A fresh `npm install reactive-agents@0.19.0` on Node loads the new cost exports, prices `claude-opus-4-7` at $5/$25 and completes a keyless test-provider run with `totalCost()` = `{ usd: 0, complete: true }`.

Gate record: [[2026-11-19-v0.19.0-release-gate]] (attempts 4 to 9). Warden bypass: the `bun-types` pin, logged in the pilot log.

## What went well

- **The warden loop held up under load.** Roughly 20 missions in two days (provider, cortex, ui-core, runtime, core, docs, tooling, release). Each brief named paths and gates, the parent re-ran the gates and committed per concern, and no warden commit or out-of-scope edit had to be reverted.
- **Instrument-first paid off twice.** The tooling-warden disproved my "warm bun cache hid the drift" theory with four cache variants before changing `repo ci`. The core-warden reproduced the src+dist double-load before rewriting the slot test. Both stopped a wrong fix.
- **Honest unknowns reached the user.** Costs absent instead of $0, `costComplete`, "live list unavailable: out of credits", "free" only where the price book says $0. The xAI out-of-credits case was found from a user screenshot and fixed at the framework boundary, with Cortex only rendering it.

- Install-only failure classes (owner, 2026-11-20: "prevent these failure classes so they never slip through a release again"). Repo tests resolve `src`, so neither class can fail them:
  - **Class A, a runtime-loaded file missing from dist** (0.19.0: Code Action failed for every npm user because `./sandbox-worker.ts` was not a tsup entry). Two gates. `test:install` smoke 9 runs a keyless code-action agent from the tarballs under Bun and Node. The new `shipped-assets` gate (`repo check`, pre-commit and ci) is a static scan of published packages' `src` for `new URL(<rel>, import.meta.url)` and `join(<module dir>, ...)`. It resolves each path from `dist/` and fails unless a tsup entry output, a non-dist `files` path or `package.json` ships it. A hardcoded `.ts` fails because dist emits `.js`. It fails on v0.19.0's `sandbox.ts` and on dev with the `sandbox-worker` entry removed. On landing it found 4 more loads that do not resolve from dist. They are listed in `KNOWN_UNSHIPPED` until 2026-12-20 for their owners: tools `docker-sandbox.ts` seccomp profile and Dockerfiles (an npm install runs the Docker sandbox without seccomp), testing `discoverScenarios()` and llm-provider `commitCalibration()`'s default write dir.
  - **Class B, Bun-only peer dependency warnings** (0.19.0: about 14 `incorrect peer dependency "@opentelemetry/api@1.10.0"` lines on every `bun add reactive-agents`). After the npm install, `test:install` installs the same tarballs with `bun install`. It fails on any `incorrect peer dependency` or `unmet peer` line and prints those lines. Reproduced on published 0.19.0 (14 lines, exit 0, so only matching the output catches it). On tarballs packed from the 2026-11-20 dev dists: 0 lines.
- pre-push skips the CI mirror for docs-only commits on a mirror-verified base and runs `check --all` instead; a failing check blocks the push; tag pushes always run the mirror (383271b8c; item 5). Caveat: `check --all` reads the working tree, not a clean clone of the pushed commit.

- Release-time and workflow-only paths now run before a tag (owner, 2026-11-20: "why do we keep getting failures in CI but not locally… be proactive not reactive"). This cycle had four failures that first ran in production: the release body over 125,000 chars (ran only at the tag), the v0.19.1 docs deploy, the nightly frozen-lockfile drift, and the src+dist double load in the CI clone. The local `repo ci` mirror runs only ci.yml's test steps, so workflow logic and GitHub-side rules were never exercised before a release.
  - **Docs deploy.** The `tags:` trigger from 4865039cb was never exercised before the tag. The `v0.19.1` run was rejected: `Tag "v0.19.1" is not allowed to deploy to github-pages due to environment protection rules`. The environment's only deployment branch policy is `main`. Through the shared `pages` concurrency group (with `cancel-in-progress: true`), that run also cancelled the main deploy. Fixes:
    - docs.yml deploys from main only. The deploy job carries `if: github.ref == 'refs/heads/main'`, so `workflow_dispatch` on a branch builds without deploying.
    - The concurrency group is `pages-${{ github.ref }}` with `cancel-in-progress: false`.
    - After the VERSION/CHANGELOG sync, publish.yml runs `gh workflow run docs.yml --ref main -f version=<version>`. The sync commit carries `[skip ci]`. A GITHUB_TOKEN-created `workflow_dispatch` does start a run. The explicit `RA_DOCS_VERSION` makes the version independent of tag reachability.
    - `tools/repo/tests/docs-workflow.test.ts` pins this. It is red with the tag trigger restored.
  - **Workflow gates in `repo check`.** `check-actionlint` runs actionlint 1.7.12 with SHA-256-pinned binaries for linux/darwin amd64/arm64, cached under `node_modules/.cache`. It skips with a warning locally when unavailable and fails in CI. shellcheck is off so that CI and local runs give the same result. `workflow-invariants` (pre-commit and ci) checks two rules: a deploy job is reachable only from refs its environment admits, and no concurrency group can cancel a deploy or be shared with another ref or workflow. The rules are recorded as constants in `tools/repo/src/lib/workflow-invariants.ts`. It returns 4 problems on the shipped v0.19.1 docs.yml (tag trigger, unguarded dispatch, cancelling group, unkeyed group). On today's docs.yml with only the tag trigger restored, it returns exactly the `push.tags` problem.
  - **Release rehearsal.** The pre-publish steps moved into the composite action `.github/actions/release-preflight` (install, build, typecheck, test, clean-install smoke, `release.ts --dry-run`). publish.yml and the new `release-rehearsal.yml` both call it. The rehearsal then runs `release.ts <next patch> --no-publish` (changelog, stamp, lockfile resync, build), `release-notes.ts` against the would-be section, and the docs build at that version. `release-notes.ts` now exits 1 when the body is over the limit. The rehearsal runs nightly against dev, on dev pushes that touch the release path, and by hand. It does not run on every push: ci.yml already runs build, typecheck and tests per push. `tools/repo/tests/release-rehearsal.test.ts` pins that neither workflow copies a preflight command. Not yet run in Actions: the first dev push of this change is its first run, and schedules fire only once the file is on main.
  - **Process.** The `prepare-release` and `repo-tool` skills now say: exercise a new or changed workflow trigger or deploy path with `workflow_dispatch` on a branch before anything relies on it. Check that the latest Release Rehearsal on dev is green before tagging.

- Resolved 2026-11-20, abort-signal flake: the test was at fault, not cancellation. Abort-to-end is 1 to 53 ms. The 559 ms came from the 50 ms abort timer firing late, because cold-start work blocked the event loop (about 75 ms idle, about 420 ms on a busy core). The test now measures abort-to-end against a 5 s scripted call; it fails when both interrupt paths are cut.
- New finding from that work, not yet investigated: the first run in a process blocks the event loop for about 75 to 420 ms, delaying any caller timers and abort handlers set during it.
