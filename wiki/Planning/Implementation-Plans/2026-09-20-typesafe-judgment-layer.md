# TypeSafe Judgment Layer Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Introduce fast, calibrated **typed judgments** (Choice / Score / Noul with probabilities) via the TypeSafe API (`jev` model) as a new inference primitive, and deploy it where it unlocks leverage the framework does not have today. There are **two deployment surfaces**, and their leverage/risk profiles are opposite:

- **Surface B — measurement instrument (FRONT-LOADED, highest leverage):** back the **eval/judge/benchmark** stack with Jev by default (LLM-as-judge kept as a secondary engine). This is off the agent hot loop, is a pure *replacement* of already-LLM-parsed verdicts, makes calibration the product rather than a nice-to-have, is inherently Rule-4-clean (Jev cannot share a code path with any SUT LLM), and **is a dev/CI dependency — never a framework-user runtime dependency**. It is also the *instrument that decides whether Surface A is worth shipping*: a trustworthy, low-variance judge must exist before we can ablate runtime changes. We take this opportunity to **overhaul the eval system end-to-end** so RA measurement is robust — real per-dimension variance, confidence intervals, minimum-detectable-effect, and calibration — instead of the current flat ±0.02 delta on noisy `parseFloat || 0.5` scores.
- **Surface A — runtime judgment tier (sequenced AFTER):** an **opt-in** `.withJudgment()` advisor for the agent hot loop (adaptive strategy selection, the `comprehend/` regex stack, guardrails, tool-name healing). Here Jev MUST be additive — like a paid provider, never required, always degrading to the existing heuristic. It is built second and ablated *using the Phase B instrument*.

**Why this order:** the original plan sequenced the four runtime sites first and left judge/eval as follow-up #3. That inverts the leverage. The runtime rollout gates on shadow/ablation evidence produced by the judge — but the judge is today the noisy `parseFloat || 0.5` instrument. We would be measuring Jev's runtime lift with a broken ruler. **Build the ruler first.**

**Architecture — own the primitive, not the vendor:** RA takes full ownership of the System One judgment *paradigm* as a first-class framework primitive, with TypeSafe/Jev as its first *provider* — exactly how RA already abstracts LLM providers behind `LLMService`/`ProviderAdapter`. A new leaf package `@reactive-agents/judgment` defines an Effect-TS `JudgmentService` (tag) exposing `askChoice() / askScore() / askNoul()` and a batched `ask()` (all questions over the same state in one request, per the parallel-questions cookbook), over a **`JudgmentBackend` interface** (the multi-backend contract; `translate.ts` is the per-backend adapter, the only module touching a vendor SDK). Two backends ship in this plan:

- **`jev` backend** — wraps `@typesafe-ai/sdk` (`TypeSafeClient.systemOne`). Calibrated probabilities, ~100 ms, cheap (see POC). The performance/cost tier.
- **`llm` backend** — the same `ask()` shape, backed by an existing RA `LLMService` provider using structured output to return Choice/Score/Noul (probabilities present but **uncalibrated**). Runs **keyless-relative-to-TypeSafe** (uses the user's existing LLM key) → zero adoption friction and a working default everywhere; Jev is the calibrated/cheap/fast upgrade.

A future **open-source System One model** plugs in as a third `JudgmentBackend` behind the same tag with no consumer change — RA owns the interface, the model swaps out. The service emits a structured EventBus event per call and degrades at every integration boundary. `JudgmentService` is consumed **two ways**: (1) Phase B wires it into the eval layer as the default judge engine (the existing `JudgeLLMService` stays as a secondary path); (2) Phase A threads it as an optional builder service via `.withJudgment()`, per-site gated, default-off. `packages/judgment` depends on `core` + SDK only.

**Strategic framing — take full ownership of the judgment paradigm.** Competitors offer "agentic structured output" (generate-then-validate, uncalibrated, LLM-priced). RA's differentiator is **judgment as a calibrated, provider-swappable primitive wired into the harness control flow** — routing, gating, escalation, verification — consumed by the kernel/policy layer that already exists. The framework does not merely *use* Jev internally; it exposes the judgment primitive as a public capability (`.withJudgment()` + a composable `Judgment` surface) so users compose calibrated Choice/Score/Noul themselves, and it maps the highest-leverage internal uses onto RA's existing packages: **Universal Verification** (`guardrails` + `verification`: screen tool calls / citations / jailbreaks at a fraction of LLM cost), **Harness Engineering** (`purpose-routing` + `trace`/`replay`: model routing, reasoning-trace classification), **Eval** (Phase B, the ruler). **Scope discipline (warden):** ship a bounded primitive + two backends + the 2–3 internal uses that already have package homes. Do NOT build a "judgment marketplace" or chase the docs' industry verticals — everything else is user-composable via the public primitive. The value is the *unified interface + harness integration*, not reimplementing use cases.

## Research basis

### Live TypeSafe facts (docs, 2026-09-22)

- System One / Jev: typed calibrated judgments, **~100 ms/query**, marketed **>100× intelligence-to-speed-and-cost** vs a reasoning LLM. Not an agent framework; does not generate text or choose its own next action. "Typed output guarantees the interface, not truth" — validate calibration on RA's own data.
- Three primitives: **Choice** (one of a set; distribution compares options; has `confidence`), **Score** (probability-weighted position on described ordered levels; has `confidence`), **Noul** (probability of yes; NO separate confidence — near-0.5 = split probability, not medium intensity). Independent questions over the same state run in parallel in **one** request.

### Verified against installed code (2026-09-20 / re-verified 2026-09-22)

**Surface B — eval/judge stack (the front-loaded target):**
- `packages/eval/src/services/eval-service.ts` — `scoreDimension` dispatches five dimensions; four (`accuracy`, `relevance`, `completeness`, `safety`) are each an LLM completion prompted "respond with ONLY a decimal 0.0–1.0" then parsed `Math.max(0, Math.min(1, parseFloat(response.content.trim()) || 0.5))`. **Parse failure silently scores 0.5** — a calibration lie fed straight into the aggregate. `cost-efficiency` is a magic formula `overallQuality / max(cost,0.0001) / 1000` (eval-service.ts:318), not a judgment.
- `packages/eval/src/dimensions/relevance.ts:52` is the template for all four (single float prompt, `|| 0.5`).
- `packages/judge-server/src/handler.ts` — full-verdict path: prompt asks for raw JSON `{passed, overallScore, recommendation:'accept'|'review'|'reject', layerResults[]}`, parsed by `parseJudgmentText` (`indexOf("{")` + `JSON.parse`), **degrading to `passed:false / overallScore:0.5 / recommendation:"review"` with a `judge_parse_failure` layer on any parse miss** (handler.ts:38-86). Verdict schema in `contract.ts` — the three fields map 1:1 to Noul (`passed`) + Score (`overallScore`, per-`layerResults[].score`) + Choice (`recommendation`).
- `packages/eval/src/services/judge-llm-service.ts` — `JudgeLLMService` is a `Context.Tag` with `complete(CompletionRequest) → CompletionResponse`, deliberately distinct from `LLMService` for **Rule 4 (frozen judge, `00-RESEARCH-DISCIPLINE.md §4`): the judge MUST NOT share a code path with the SUT.** `EvalService.runSuite` enforces `config.judge.model !== agentConfig` (eval-service.ts:201). A Jev judge is *inherently* Rule-4-clean (different engine, no shared provider/driver/healing path) — it strengthens the invariant.
- **Measurement is statistically weak:** `EvalService.compare` (eval-service.ts:342) flags improved/regressed on a flat **±0.02** delta of dimension averages; `checkRegression` (369) uses a single flat threshold. **No repeated-run variance, no confidence interval, no minimum-detectable-effect, no calibration tracking.** Bench cells are Bernoulli (per-run accuracy 0/1; ~13pp SE at 5 tasks × n≤5 — see MEMORY) so single-run deltas under noise are being read as signal. This is the core of "measuring is not top-notch."
- `packages/benchmarks/src/judge.ts` — `scoreWithJudge` traps judge outages into an `inconclusive` lane and carries `stub-judge` / `judge_parse_failure` guard lanes that exist ONLY because the text-verdict path is unreliable. A typed judge removes the parse-failure lane's reason to exist.
- Deps today: `packages/eval` → `core`, `llm-provider`, `runtime-shim`. `packages/judge-server` → `+ eval`. Adding `judgment` as an optional judge engine keeps `eval` buildable without it (engine resolved at layer construction).

**Surface A — runtime sites (unchanged from prior verification):**
- Cheap-tier seam exists: `packages/reasoning/src/kernel/policy/purpose-routing.ts:46-53` (`classify`/`extract` → cheap pool). Judgment is a tier *below* cheap; it does NOT extend `LlmCallPurpose` and must not consume the deterministic-test turn cursor.
- Adaptive strategy selection: `packages/reasoning/src/strategies/adaptive.ts` — `heuristicClassify` (line 672, keyword ladder), LLM fallback via `purpose:"classify"` (line 216) parsed by `parseStrategySelection` (line 546, `includes("BLUEPRINT")`-style substring). This site is **already an LLM call** → Jev Choice *replaces* it (net cost/latency neutral-or-down), the only self-paying runtime site.
- `comprehend/` stack: `task-classification.ts` / `task-complexity.ts` / `task-horizon.ts` / `task-intent.ts` / `task-shape.ts` = **907 LOC** of regex emitting synthetic 0.5/0.7/0.85 constants, consumed by `kernel/policy/harness-plan.ts`. Fires at run-start on the hot loop.
- Guardrails: `packages/guardrails/src/detectors/{injection,pii,toxicity}-detector.ts` = **153 LOC**, 100% pattern tables, first-match-wins; aggregated `score = 1 - violations*0.25`. Output-side replies unscreened.
- Healing: `packages/tools/src/healing/*` Levenshtein ≤2 ladders; Jev is a stage-3 fallback only on distance miss (rare).
- `packages/runtime/src/classifier-bypass.ts` — `literalMentionRequired` used when `classifierReliability === "low"`; the "third rung" Jev should replace.
- Versions: all workspace packages `0.16.0`; new package must match (`check-version-sync.sh`). 36 packages in `packages/` (a2a, benchmarks, channels, compose, core, cost, create-reactive-agent, diagnose, eval, gateway, guardrails, health, identity, interaction, judge-server, llm-provider, memory, observability, observe, prompts, react, reactive-agents, reactive-intelligence, reasoning, replay, runtime, runtime-shim, svelte, testing, tools, trace, ui-core, verification, vue + judgment = new).

### Design evidence from cookbooks (treat numbers as examples to re-validate)

- Parallel questions in ONE request: ~12× cheaper / ~10× faster vs per-question → the judge verdict becomes a single batched Noul+Score+Choice request; each eval dimension can also batch.
- Citation-check / extraction-cascade cookbooks: verify specific claims/fields against evidence, escalate uncertain cases → shapes the per-requirement `layerResults` scoring and future verification work.
- Classification-using-confidence: calibrated `confidence` gates behavior → the eval overhaul surfaces Jev `confidence` as per-dimension reliability and drives the variance/MDE math.
- Skill-suggestion cookbook: wrong loads 16.8%→7.3% but **7/315 regressed** → justifies shadow mode + confidence gating before any runtime inversion (Surface A).

## Global Constraints

- Strict TypeScript. No `any`, no new `as unknown as`. Effect-TS mandatory (`Schema.Struct` payloads, `Context.Tag`, `Layer`, no `throw`, no raw `await` outside Effect) — load `effect-ts-patterns` skill first.
- **Jev is never a framework-user runtime requirement.** Surface B (judge/eval) is dev/CI tooling; a `TYPESAFE_API_KEY` there is the same class of dependency as the LLM key the judge already needs. Surface A is opt-in `.withJudgment()`; without it, zero network, zero behavior change, zero new import side effects in any default path.
- **Jev default / LLM secondary in the judge:** the eval/judge engine resolves `judgeEngine: "jev" | "llm"` with **`"jev"` as the default**. The existing `JudgeLLMService` / `parseFloat` path is retained and selectable (`"llm"`) as the secondary engine, not deleted, so a keyless environment still measures (see fallback rule).
- **Degrade, never fail:** any judgment error (auth, timeout, rate-limit, malformed) is caught at the boundary and falls through — Surface A to the existing heuristic, Surface B to the `"llm"` engine (or, keyless, to a clearly-marked `inconclusive` verdict, never a fabricated 0.5). Emit `judgment:failed` each time.
- **Rule 4 preserved:** the Jev judge is a distinct engine from any SUT; `EvalService`'s judge≠SUT guard still applies and passes trivially. Never route the SUT through `JudgmentService`.
- **Observable:** every judgment call emits `{ site, questions, answers (values + probabilities + confidence), latencyMs, tokens, degraded? }`. This feeds both the eval variance layer and Surface A shadow measurement.
- **No secrets in logs/events:** API key read only from explicit `JudgmentConfig` or `TYPESAFE_API_KEY`; never attached to events or logs.
- `packages/judgment` deps: `core` + `@typesafe-ai/sdk` for the `jev` backend; **refined 2026-09-22** to also allow `llm-provider` (Layer 2, same tier as `eval`) for the `llm` emulation backend — it reuses `LLMService.completeStructured<A>()` (real Schema-validated structured output with parse-retry, already built) rather than duplicating that logic behind a hand-rolled structural type. It must NOT import `reasoning`, `tools`, `guardrails`, `runtime`, `eval`. Integration is inward: consumers accept an injected `JudgmentService`.
- Keep existing heuristics/LLM paths as the **fallback** at every site — no deletion of regex heuristics in this plan; retiring them is a post-inversion follow-up after ablation evidence. (The one exception is the judge-server `parseJudgmentText` degraded-`0.5` verdict, which is replaced — its whole purpose was to paper over unreliable parsing the typed path eliminates; the `"llm"` engine keeps a parser but returns `inconclusive`, not `0.5`, on miss.)
- All tests offline via a fake transport injected at the SDK boundary. No new Bun-specific APIs.
- Warden routing: `packages/judgment/**` = parent-dispatched (new package, `build-package` skill); `packages/eval/**` + `packages/judge-server/**` + `packages/benchmarks/**` = parent (eval overhaul); `packages/reasoning/src/strategies|kernel/**` = `kernel-warden`; `packages/tools/**` = `tools-warden`; `packages/guardrails/**` + runtime wiring = parent. New default-affecting mechanisms gated by `ablation-warden`. Surface-B judge-engine default flip is itself an eval-methodology change — validate it does not move measured scores beyond its own calibration study (Task 7).
- After each task: `bun test packages/<touched>`, `bun run typecheck`, `bun run build`. One concern per commit.

## Phase B — Measurement instrument overhaul (FRONT-LOADED)

> This phase is the highest-leverage, lowest-risk deployment: off the hot loop, a pure replacement of already-parsed LLM verdicts, no framework-user runtime dependency, and it produces the trustworthy ruler Phase A needs. Ship it as its own release before touching runtime sites.

## Risks

- **Judge default flip moves measured scores:** flipping `judgeEngine` to Jev is itself an eval-methodology change. Mitigated by Task 6 Step 5 (frozen-dataset LLM-vs-Jev agreement + variance study) and by keeping `"llm"` selectable — flip only on demonstrated agreement + variance reduction.
- **Calibration ≠ truth:** Jev is calibrated on its distribution, not RA's. Task 6 Step 3 calibration check is the guard; `confidence` weights, never blind trust.
- **Keyless/CI parity:** Surface B needs a `TYPESAFE_API_KEY` to run the Jev judge — same class as the LLM judge key the bench already needs (MEMORY: "CI has no keys"). Fake transport covers unit tests; the `"llm"` engine + `inconclusive` (never fabricated 0.5) covers keyless local/CI runs.
- **Confident-wrong Jev on runtime sites** regressed 7/315 in the cookbook — mitigated by shadow gates, per-site defaults-off, ablation requirement (Phase C), and now measured with a trustworthy judge.
- **Autonomy-gating (Task 11b) has an asymmetric downside** the other sites don't: a wrong classifier answer costs accuracy, a wrong auto-approval costs an unreviewed action. This is why Task 11b is shadow-only with no inversion step written — its exit gate produces a report, not a flip.
- **Latency creep** on the hot loop (Phase C, esp. Task 10 inversion is blocking): default 3 s timeout; measure via `latencyMs`; prefer fire-and-forget/shadow where inversion isn't justified.
- **Docs drift**: TypeSafe contracts move; every integration test uses the fake transport so a breaking upstream change surfaces as a red test at upgrade time, not at runtime.
